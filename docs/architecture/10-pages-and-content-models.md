# 10. Pages and content models

This chapter describes the page layer: namespaces as registry entries and their numbering, titles and the one resolver that handles them, redirects and moves, document pages and the namespaces that hold them, the content model registry, the wikitext subset, links, legacy categories and category mappings, page properties, and importing pages from another wiki. It holds the two tables other chapters add rows to: the namespace catalogue (§1.4) and the content-model catalogue (§4.4). It assumes the log and its records from [01](01-log-and-records.md), the `view` tables and projections from [03](03-storage-caches-and-search.md), entity IDs and identity clusters from [04](04-entities-and-identifiers.md), page statements from [06](06-statements-and-properties.md), and ACLs and deletion from [09](09-security-and-moderation.md). Templates, expansion and Lua are in [11](11-rendering-templates-and-modules.md), files in [12](12-files-and-media.md), page repositories and mirrored pages in [13](13-mirrored-pages.md), threads and talk pages in [14](14-discussions.md), and the definition-model pages (tables, scopes, sprints, queries, schemas) in [15](15-structured-pages.md). The registry files themselves are catalogued in [23](23-configuration-and-registry.md).

## 1. Namespaces

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §1, §2; [0009](../decisions/0009-keyed-entity-types-and-domain.md) §11; [0038](../decisions/0038-page-metadata-and-categories.md) §4, §8; [0041](../decisions/0041-content-models.md) §3, §4; [0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §1; [0061](../decisions/0061-sprints-and-tasks.md) §2; [0078](../decisions/0078-entity-sources.md) §5.*

### 1.1 A namespace is a registry entry

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §1; [0041](../decisions/0041-content-models.md) §4.*

Namespaces are configuration: data passed in by the caller and recorded in the log ([0004](../decisions/0004-identity-clusters-and-equivalence.md) §9, [0005](../decisions/0005-crate-organization.md) §3 rule 3). The entries are in `docs/registry/namespaces.toml` ([0015](../decisions/0015-record-format-and-partition-registry.md) §5; [23](23-configuration-and-registry.md)). Each entry records:

- the **MediaWiki fields**: numeric ID, canonical name, local name, aliases, the `case` rule, whether subpages are allowed, and the paired talk namespace;
- the **kind**, which says only whether the namespace holds pages (§1.2). A `pages` entry names the allowed content models and the default model (§4.5). A namespace whose pages may also carry uploads adds `uploads = true` ([0039](../decisions/0039-files-and-media.md) §2; [12](12-files-and-media.md));
- the **title normalizer** (§2.1);
- the **creation rule**, where the kind needs one (§3.4);
- **`enabled_by`**, where a namespace is implemented only while a tenant setting is on (§1.3, rule 1).

**An entity namespace is keyed by entity type, not by provider.** `Item` hosts every item type: local `Q`, Wikidata `WDQ`, OpenAlex `OAW` and the rest. `Property` hosts `P` and `WDP`. What makes a namespace an entity namespace is its model: the entity type's model (`wikibase-item`, `wikibase-property`, §4.4) names the type, so the entry carries no list of entity types; `entity_types` is not a field of the entry. This matches [0002](../decisions/0002-source-graphs-and-mass-ingest.md) §4, where the prefixed ID is the working name in a page title such as `Item:WDQ123`. Everything else in an entry stays (normalizer, `case`, subpages, paired talk, creation rule). The registry rejects a `pages` namespace whose allowed models mix sources, since a page can only change between models of the same source (§4.3).

### 1.2 Kinds

*Sources: [0041](../decisions/0041-content-models.md) §4; [0008](../decisions/0008-namespaces-and-document-pages.md) §1.*

A namespace's `kind` says only whether it holds pages:

| Kind | Meaning |
|---|---|
| `pages` | It holds pages. The entry names the **allowed models** and the **default model** |
| `reserved` | Listed in `meta=siteinfo`; holds no pages (§1.3, rule 1) |
| `virtual` | Its pages are generated by the server: `Special`, `Media` |
| `resolver` | Every title is a key that performs a lookup ([0029](../decisions/0029-resolver-namespaces.md) §2). It holds no pages, so it has no model |

`Special` and `Media` ([0039](../decisions/0039-files-and-media.md) §1) are virtual, and so is a namespace with **`forwards_to`**, every title of which resolves to the same title in the namespace it names (§2.2, [0049](../decisions/0049-boards.md) §2). A `resolver` namespace holds no records either: every title in it is a key, and viewing it performs a lookup ([0029](../decisions/0029-resolver-namespaces.md) §2–3; [06](06-statements-and-properties.md)). The name is `pages`, not `content`, because MediaWiki's siteinfo already uses `content` for a different flag: whether a namespace counts as article space.

**The five old kinds that held pages are models and one flag:**

| Old kind | Now |
|---|---|
| `entity` (entity view) | `pages`, with the entity type's model (§4.4) |
| `document` | `pages`, with text models |
| `file` | `pages`, with `wikitext` and **`uploads = true`**: a page in the namespace may carry upload records ([0039](../decisions/0039-files-and-media.md) §2) |
| `composite` (talk) | `pages`, with `triplespace-talk` |
| `thread` | `pages`, with `triplespace-thread` |

Where a later ADR still calls a namespace `document` or its talk namespace `composite` ([0038](../decisions/0038-page-metadata-and-categories.md) §4, §8), this table gives the registry reading.

### 1.3 Numbering

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §2.*

MediaWiki's canonical numbers are kept wherever a namespace has one, because clients hard-code them. Four rules govern every other number:

1. **Every number MediaWiki core or any Wikibase extension uses is reserved.** It is listed with kind `reserved`, is never given another meaning, and is not implemented unless an ADR says so. An ADR may implement one conditionally, by a tenant setting named in the entry's `enabled_by` ([0042](../decisions/0042-template-expansion-and-parsoid.md) §3). Turning the setting off keeps the namespace's pages readable and refuses writes with `ts-namespace-disabled`.
2. **Talk namespaces exist only for implemented subject namespaces,** at the next odd number. A talk namespace is a `pages` namespace with the model `triplespace-talk` ([0019](../decisions/0019-discussions.md) §2, [0041](../decisions/0041-content-models.md) §4). Where a page is its own talk page, as a board and a thread are, the talk number is `virtual` and forwards to the subject namespace ([0049](../decisions/0049-boards.md) §2). A resolver's talk number is `reserved` ([0029](../decisions/0029-resolver-namespaces.md) §2). A reserved, unimplemented subject namespace has no talk namespace.
3. **Triplespace's own namespaces take 210–219, then 310–319. Resolver prefixes ([0029](../decisions/0029-resolver-namespaces.md)) take 220–229, then 320–329.** A first block is used up before its second. All four blocks are registered on mediawiki.org's Extension default namespaces page, which listed nothing in 204–240 on 2026-09-27 and nothing in 310–329 on 2026-10-01. Allocation is a change to `namespaces.toml`, under the registry's rules ([0015](../decisions/0015-record-format-and-partition-registry.md) §5).
4. **A tenant's own namespaces take 3000 and above,** the numbers mediawiki.org's Extension default namespaces page leaves to system administrators, **or 100–199,** MediaWiki's block for site-specific namespaces, except the numbers `namespaces.toml` lists (120–125, 146 and 147 among them). An adopted wiki keeps the numbers it already gave its namespaces ([0035](../decisions/0035-adopting-a-wikibase.md); [08](08-tenants-and-instances.md)). A tenant `namespace` record with any other number not in `namespaces.toml` is refused with `ts-namespace-number`; one whose name or alias equals another namespace's name or alias on the tenant, or an interwiki prefix from its site aliases ([0026](../decisions/0026-sitelinks.md) §2), is refused with `ts-namespace-name-taken`. An entity source's namespace is one of these ([0078](../decisions/0078-entity-sources.md) §5; [05](05-providers-and-ingest.md)).

**Conditionally enabled namespaces.** Template (10) is a `pages` namespace and Template talk (11) is enabled while `wikitext.expansion` is on; while it is off, 10 is `reserved` and 11 is not registered (`enabled_by = "wikitext.expansion"`). Turning expansion off never removes pages: Template pages keep their records and history, the namespace refuses `create`, `edit` and `move` into it with `ts-namespace-disabled`, its existing pages stay readable at their titles and can be deleted, and `meta=siteinfo` lists a disabled namespace while it still holds pages ([0042](../decisions/0042-template-expansion-and-parsoid.md) §3). Module (828) and Module talk (829) are enabled while `wikitext.lua` is on (`enabled_by = "wikitext.lua"`); unlike core's reserved numbers, they are not listed in `meta=siteinfo` while disabled and empty, because MediaWiki without Scribunto does not list them and clients use their presence to detect Lua ([0043](../decisions/0043-lua-modules.md) §2). Both are described in [11](11-rendering-templates-and-modules.md).

## 2. Titles, redirects and moves

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §3, §4; [0044](../decisions/0044-tenant-relative-ids.md) §5; [0051](../decisions/0051-page-redirects.md) §1, §2, §3, §4.*

### 2.1 One resolver handles every title

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §3; [0044](../decisions/0044-tenant-relative-ids.md) §5.*

Page views, API `titles=` parameters, redirects and wiki links (§5.2) all go through one resolver. It works in three steps:

1. **Split** the namespace prefix, matching canonical names, local names and aliases without regard to case, as MediaWiki does.
2. **Normalize** the title with the namespace's normalizer:
   - `first-letter` (MediaWiki's default): underscores become spaces and the first letter is uppercased. Used by `User` and `Project`.
   - `entity-id`: parses an entity ID, uppercases its prefix and applies the ID grammar's canonical form to the rest ([0017](../decisions/0017-entity-id-grammar.md) §2; [04](04-entities-and-identifiers.md)), so `Item:q42` becomes `Item:Q42` and `Item:mbab10BBBFC-…` becomes `Item:MBAb10bbbfc-…`. It also accepts tenant-relative IDs: `Item:QQQ5` normalizes to `Item:Q5`, as `Item:q5` already does, and the resolver serves the canonical title. This is normalization, not a redirect record ([0044](../decisions/0044-tenant-relative-ids.md) §5).
   - `file-name`: `first-letter` with MediaWiki's file-name rules ([0039](../decisions/0039-files-and-media.md) §1; [12](12-files-and-media.md)).
   - A keyed type's own normalizer ([0009](../decisions/0009-keyed-entity-types-and-domain.md) §2; [04](04-entities-and-identifiers.md)).
   - A resolver's normalizer ([0029](../decisions/0029-resolver-namespaces.md) §2).
   - An entity source's ID normalizer, in its namespace ([0078](../decisions/0078-entity-sources.md) §2, §5).
3. **Resolve** the normalized title:
   - in an entity namespace, to an entity, following aliases and identity clusters to the canonical ID ([0004](../decisions/0004-identity-clusters-and-equivalence.md) §4), exactly as the API resolves IDs;
   - in a forwarding namespace, to the same title in the namespace named by `forwards_to` ([0049](../decisions/0049-boards.md) §2);
   - in a `resolver` namespace, by the resolver's lookup ([0029](../decisions/0029-resolver-namespaces.md) §3), or, in an entity source's namespace, by the source's ([0078](../decisions/0078-entity-sources.md) §5);
   - in any other `pages` namespace, to the **primary of the title's stack** ([0052](../decisions/0052-page-repositories-and-title-inheritance.md) §2; [13](13-mirrored-pages.md)): the local page ID, or, where no local page exists and a page repository in `pages.repos` serves the namespace and has the title, that repository's page ([0052](../decisions/0052-page-repositories-and-title-inheritance.md) §3). A primary that is a **redirect** (§2.3), local or foreign, is followed one hop, to the stack of its target title, unless the request says `redirect=no` (§2.4).

**`meta=siteinfo` reports only MediaWiki's two case values,** `first-letter` and `case-sensitive`. A namespace whose normalizer is neither reports `case-sensitive`, and the server normalizes. A client that believed `first-letter` would rewrite titles the server does not accept.

### 2.2 Titles that resolve somewhere else

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §3.*

**A title that resolves somewhere else redirects there.** `Item:P31` redirects to `Property:P31`, and `Item:WDQ123` redirects to `Item:Q456` once `WDQ123` belongs to a cluster whose canonical ID is `Q456`. `Special:EntityPage/{id}` resolves any entity ID to its page, as it does in Wikibase. A forwarding title is a permanent redirect: `Board talk:X` answers 301 to `Board:X`, and has no page ID ([0049](../decisions/0049-boards.md) §2; [14](14-discussions.md)).

**Thread titles are minted, not chosen:** the UTC date the thread was created and its subject, `Thread:2026-09-27/Why is P31 wrong here` ([0019](../decisions/0019-discussions.md) §3; [14](14-discussions.md)).

### 2.3 A redirect is a wikitext page whose text says so

*Sources: [0051](../decisions/0051-page-redirects.md) §1.*

**A page is a redirect when its content model is `wikitext` and its text begins with a redirect line,** `#REDIRECT [[Target]]`, exactly as MediaWiki decides it: the `redirect` magic word, with the localized synonyms MediaWiki's message files give it, followed by a wiki link, optionally with a fragment, `#REDIRECT [[Myocardial infarction#Signs and symptoms]]`. Whatever follows the first line is kept and shown on the redirect page itself (MediaWiki allows categories and `{{R from …}}` templates there) but has no other effect. The magic word is registered in `docs/registry/wikitext-functions.toml` with status `implemented`.

**Only `wikitext` pages can be redirects.** `markdown`, `json`, `yaml`, `text`, `Scribunto`, `triplespace-table` and `triplespace-board` pages never are, whatever their first line says, as MediaWiki's non-wikitext content handlers never produce one. Any namespace whose allowed models include `wikitext` may hold redirects: those the namespace catalogue (§1.4) lists with `wikitext` among their models, which includes the `/doc` pages of Module, Table, Scope and Query.

**The target may be any title.** A redirect may point into any registered namespace: another article, a Project page, a category, or an entity page, `#REDIRECT [[Item:Q42]]`. The target is resolved by the title resolver like any link, so a redirect to `Item:WDQ123` lands on the cluster's canonical page ([0004](../decisions/0004-identity-clusters-and-equivalence.md) §4). A target with an interwiki prefix, `#REDIRECT [[enwiki:Foo]]`, is an **external redirect**: it is recorded, listed and rendered as a link, and never followed automatically, as MediaWiki does not follow one unless `$wgDisableHardRedirects` is off and the prefix is marked local.

**A redirect is still a page.** It has a page ID, records, history, a talk page, statements and categories like any other page in its namespace. Being a redirect is a property of its latest text, read by the projection ([0051](../decisions/0051-page-redirects.md) §5; [03](03-storage-caches-and-search.md)), never a record of its own.

### 2.4 Following a redirect

*Sources: [0051](../decisions/0051-page-redirects.md) §2.*

**The title resolver follows one hop, and only to a target the principal may read.** When the target is under a confidential `read` restriction the principal does not satisfy, the resolver answers with the redirect page itself, whose text names the target as a link to a missing page ([0056](../decisions/0056-security-model.md) §6; [09](09-security-and-moderation.md)). The resolve step of §2.1 has a fourth rule: when a `pages` namespace title resolves to a page that is a redirect, the resolver resolves the target title and answers with *that* page, carrying the redirect's page ID alongside as `redirected_from`. It follows **exactly one** hop, as MediaWiki does: a redirect to a redirect is a **double redirect**, served as the second redirect page, and listed by the report of [0051](../decisions/0051-page-redirects.md) §6 ([21](21-special-pages.md)). There is therefore no loop to detect. A redirect whose target does not resolve is a **broken redirect**, served as the redirect page itself, with the target as a red link.

**`redirect=no` stops it.** A page view with `redirect=no`, the API's page-set parameters without `redirects`, `action=edit`, `action=move`, `action=delete`, `prop=info` and every write address the redirect page itself, as in MediaWiki. Only reads that ask to follow are followed.

**A followed view is the target with a notice.** The page view answers HTTP 200 with the target's content and a "(Redirected from *Old title*)" line under the title, linking to the redirect with `redirect=no`. It is not an HTTP redirect: the URL stays what the reader typed or followed, and a reader who wants the redirect page can reach it from the notice. This differs from a forwarding namespace (§2.2), which answers 301, because a page redirect is content that can change and be edited, and a forwarding title is a fixed rule with no page.

**Fragments compose.** A redirect with a fragment lands the reader at that section; a link with its own fragment keeps its own, as MediaWiki does.

**Links to redirects are marked.** The wikitext subset and the markdown model render a link whose target is a redirect with the class `mw-redirect`, and `prop=info&inprop=linkclasses` reports it, so Parsoid ([0042](../decisions/0042-template-expansion-and-parsoid.md) §8.1) and the site UI draw it as MediaWiki does. A link is never rewritten to its target; the stored source and the rendered `href` keep the redirect's title.

**Transclusion follows one hop too,** which [0042](../decisions/0042-template-expansion-and-parsoid.md) §4 already provides for `{{Foo}}` where `Template:Foo` is a redirect. `#ifexist` answers true for a redirect, as it does for any page. A redirect page itself is never transcluded as its target: `{{:Foo}}` with `Foo` a redirect transcludes `Foo`'s target, one hop, as MediaWiki does.

**Foreign redirects** are followed by the same rule, with the target looked up in the title stack: a redirect in a page repository's title index resolves to the stack of its target title, so a Wikipedia redirect lands on a local fork when one exists ([0052](../decisions/0052-page-repositories-and-title-inheritance.md) §4; [13](13-mirrored-pages.md)).

### 2.5 Moves leave a redirect

*Sources: [0051](../decisions/0051-page-redirects.md) §3; [0008](../decisions/0008-namespaces-and-document-pages.md) §4.*

**A move is one record on the moved page.** Moving a page appends a `move` record with its new title, and nothing else about that page changes. **A move leaves a redirect at the old title by default,** as MediaWiki's does. `action=move` and the Move form append, in one transaction with one base check:

1. the page's `move` record with the new title (§3.2);
2. a `create` record for a **new page** at the old title, model `wikitext`, text `#REDIRECT [[New title]]`, attributed to the mover with the move's summary.

The redirect is a second page, with its own ID and its own history, as it is in MediaWiki; nothing about the moved page is rewritten. The log event is one `move/move` ([0011](../decisions/0011-logs.md) §6.1; [16](16-logs-feeds-and-notifications.md)) whose parameters carry the old and new titles and, as MediaWiki's do, whether a redirect was left and its page ID. With `noredirect`, which needs `suppressredirect` ([0051](../decisions/0051-page-redirects.md) §8; [09](09-security-and-moderation.md)), only the `move` record is written and the event is `move/move` with `noredirect: true` in its parameters; `move/move_redir` keeps MediaWiki's meaning, a move onto an existing redirect (below).

**Exceptions:**

- **User renames leave no redirect** (§3.4): the batch of `move` records a rename or a vanishing writes carries no `create`, because names are erasable and a redirect would keep the old one visible. A user moving one of their own subpages by hand is an ordinary move and leaves one.
- **Talk pages do not move,** because they are composite and attached by identifier ([0019](../decisions/0019-discussions.md) §2): the threads of a moved page's talk page are already its new title's threads. `movetalk` is accepted and does nothing, and no talk redirect is created, since a talk title always resolves through its subject.
- **Thread renames leave none** ([0019](../decisions/0019-discussions.md) §3), for the reason user renames do.

**Subpages.** `movesubpages` moves every subpage under the old title in the same batch, each leaving its own redirect, in namespaces that allow subpages. It needs `move-subpages`.

**Moving over a redirect.** A move onto a title that is occupied is refused with `articleexists`, with one exception that MediaWiki makes and clients expect: when the occupying page is a redirect with **one revision** whose target is the page being moved, the move proceeds. The occupying redirect is deleted first, which here is a `read` ACL on its page ID ([0023](../decisions/0023-moderation.md) §4) written in the same transaction and logged as `delete/delete` with the move as its reason, so the title index frees the title before the `move` record takes it. This needs `delete-redirect`. A redirect with more history, or pointing elsewhere, is not displaced: the mover edits or deletes it first.

### 2.6 Category, File and entity redirects

*Sources: [0051](../decisions/0051-page-redirects.md) §4.*

**Category redirects.** A `Category:` page that is a redirect is followed when it is **viewed**, with the notice of §2.4, and nowhere else: membership is defined by the text of each member (§5.3), so the members of `Category:Old` stay in `Category:Old`, and a redirect page's own member list is shown beneath the notice when it has any, as MediaWiki shows it. Moving members is a job for a bot that edits their text, or for a category mapping's make-it-real job once the old category is mapped to the same statement (§5.4). Wikipedia's soft category redirects remain what they are there: a template, `{{Category redirect}}`, that expands to a notice. Hard redirects follow for viewing, soft ones stay templates, and neither moves a member.

**File redirects.** A `File:` page that is a redirect redirects its file too: the file lookup of [0039](../decisions/0039-files-and-media.md) §11 follows a local redirect page one hop before trying repositories, as MediaWiki's `RepoGroup::findFile` does, so `[[File:Old name.jpg]]` embeds the renamed file. `movefile` leaves a redirect as any move does ([12](12-files-and-media.md)).

**Entity namespaces have no page redirects.** `Item:`, `Property:` and the keyed-type namespaces hold composed views with no text, so §2.3 cannot apply, and ID aliases ([0004](../decisions/0004-identity-clusters-and-equivalence.md) §4) already do the work. `Special:Redirect/…` is unrelated: it maps IDs to pages ([0047](../decisions/0047-special-pages.md); [21](21-special-pages.md)).

## 3. Document pages and their namespaces

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §4, §6, §7; [0009](../decisions/0009-keyed-entity-types-and-domain.md) §11; [0038](../decisions/0038-page-metadata-and-categories.md) §4, §8; [0061](../decisions/0061-sprints-and-tasks.md) §2.*

### 3.1 A page is identified by a page ID

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §4.*

**A page is identified by a page ID, not by its title.** Page IDs are minted by the instance in sequence, start at 1 and are never reused. The title is an attribute of the page, in the same way a username is an attribute of an actor ([0007](../decisions/0007-actor-identity.md) §4; [07](07-actors-and-accounts.md)). This has three effects:

- **The log key is the page ID.** A log header key must be an identifier, never content ([0006](../decisions/0006-log-integrity-and-erasure.md) §3). A title is content, and a user page title contains a username.
- **A move is one record on the moved page** (§2.5). By default a second page is created at the old title, a redirect to the new one.
- **A title index is a projection.** It maps each current title to its page ID, and it is rebuilt from the log ([03](03-storage-caches-and-search.md)).

### 3.2 The `pages` partition and page records

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §4.*

**Pages live in their own partition.** A `pages` source partition is in the registry ([0005](../decisions/0005-crate-organization.md) §4.1; [01](01-log-and-records.md), [02](02-graphs-rdf-and-query.md)):

| Graph | Illustrative IRI | Kind | Written by | History | Integrity | Export |
|---|---|---|---|---|---|---|
| **Pages** | `{base}/graph/pages` | Source | Page edits, moves and imports | Full | `logged` | Public |

The partition holds page records, not quads. Its RDF output is revision metadata and page statements (§5.6).

**Page record payloads.** Each record's payload type is `scatter:v0/page`, and it carries one operation:

| Operation | Meaning |
|---|---|
| `create` | Mints the page ID, sets the title and content model, and stores the first text; may carry `forked_from`, naming the repository, page and revision a fork was taken from ([0054](../decisions/0054-forking-a-mirrored-page.md) §1; [13](13-mirrored-pages.md)) |
| `edit` | Stores the page's **complete new text**, optionally with a new content model |
| `move` | Sets a new title |
| `follow` | On a fork, whether its talk page follows the repository's (`follow`) or has been forked (`fork`); no text, so it is a null revision in the page's history, as MediaWiki writes for protection ([0069](../decisions/0069-synchronized-talk-pages.md) §7) |

**Deletion is an ACL, not a page operation** ([0023](../decisions/0023-moderation.md) §4; [09](09-security-and-moderation.md)). Deleting a page writes a `read` ACL on its page ID to the tenant `log` partition, and undeleting retires the ACL. The page and its history are hidden from everyone but administrators. This is hiding in the sense of [0006](../decisions/0006-log-integrity-and-erasure.md), not erasure.

**A page's statements are change sets** (`scatter:v0/changeset`), keyed by its page ID in the same partition and restricted to statements ([0038](../decisions/0038-page-metadata-and-categories.md) §1; [06](06-statements-and-properties.md)). They take revision IDs, so a page's history interleaves text and statement revisions.

**Each revision stores the full text, not a diff.** Pages are small. Diffs are computed when they are read, as MediaWiki computes them. Because each record is self-contained, erasing one revision with an `erase` record ([0006](../decisions/0006-log-integrity-and-erasure.md) §7; [01](01-log-and-records.md)) does not break the text of later ones.

**Edit conflicts use the base offset** ([0006](../decisions/0006-log-integrity-and-erasure.md) §8). An `edit` carries the offset of the page's latest record that the client saw. A mismatch is reported as `editconflict`. A base is required for `edit` and `move`.

### 3.3 Namespace 0 holds articles

*Sources: [0038](../decisions/0038-page-metadata-and-categories.md) §8.*

**The main namespace is implemented as a `pages` namespace with text models.** It is the second exception to the numbering policy's first rule (§1.3). Articles, including every page imported from a wiki's main namespace, go here.

| Field | Value |
|---|---|
| Normalizer and case | `first-letter` |
| Content models | `wikitext` (default), `markdown`, `json`, `yaml`, `text` |
| Subpages | No, as MediaWiki's default for namespace 0 |
| Creation | Anyone with `edit` |
| Talk | Talk (1), `triplespace-talk` |

**A bare title is a main-namespace title, in every content model.** With articles in namespace 0, an unprefixed title means a main-namespace page, as on MediaWiki: `[[Q42]]` links to the page titled `Q42`, in wikitext and in markdown alike, and an entity is linked with its namespace, `[[Item:Q42]]`, as the subset of §5.1 shows. One rule for every content model holds, in markdown posts too ([14](14-discussions.md)). Any valid title may be created, including one that looks like an entity ID: `Item:Q42` and `Q42` are different titles, as on any Wikibase that keeps items out of the main namespace.

**ID shortcuts are not title resolution.** `/resolve` and the search box's "Go to" ([0010](../decisions/0010-site-ui.md) §3; [19](19-site-ui.md)) still try entity IDs, keyed IDs and resolver strings first, and main-namespace titles last ([0029](../decisions/0029-resolver-namespaces.md) §6). When a main-namespace page has the same title as the ID, the search box offers it as the next suggestion ("Page titled Q42"), and `/resolve` returns it in an `also` field beside the entity.

### 3.4 The User namespace

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §6.*

**A user page belongs to a local user, identified by user ID.** The root title `User:Example` is resolved through the local actor records ([0007](../decisions/0007-actor-identity.md) §4; [07](07-actors-and-accounts.md)) to the actor key, such as `local:42`. The page's owner is that actor.

- **User pages can be created only for local users that exist.** The user must be registered, not temporary, and not vanished. `User:Nobody` cannot be created when no local user is called Nobody. Subpages follow the same rule, through their root.
- **Foreign actors have no user pages here.** Links to them go to their upstream page through the IRI in [0007](../decisions/0007-actor-identity.md) §2.
- **Titles follow renames.** When a user is renamed, every page under their root is moved to the new name by the same process, in one batch of `move` records. The same happens when a user vanishes: the pages move to the placeholder name. The content is not erased automatically. It can be erased on request with an `erase` record ([0006](../decisions/0006-log-integrity-and-erasure.md) §7).
- **Old names do not resolve.** A rename leaves no redirect from the old title. A redirect would keep the old name visible, and names are erasable ([0007](../decisions/0007-actor-identity.md) §4). This differs from MediaWiki, which leaves a redirect after a move.
- **Subpages with `json` or `yaml` content are editable only by their owner and administrators,** as MediaWiki protects `.json` user subpages. Other user pages follow the instance's ordinary edit permissions.

### 3.5 The Project namespace

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §7; [0061](../decisions/0061-sprints-and-tasks.md) §2.*

- **The canonical name is `Project`, and the local name is the site name,** as in MediaWiki. On the reference install that is `Triplespace Ref` ([siteinfo snapshot](../api/snapshots/mw-1.43.9-wb-REL1_43.siteinfo.json)). Both resolve.
- **Subpages are allowed.**
- **Pages can be created by anyone with the right to edit.** No owner is recorded.

`Project` (4) has `triplespace-sprint` among its allowed models; the default stays `wikitext`. **A `triplespace-sprint` page must be a subpage**: a title with no `/` in namespace 4, or any title in another namespace, is refused with `ts-sprint-title`. So `Project:WikiProject Women/Sprint March 2027` is a sprint; `Project:Sprint March 2027` is not; and a project's sprints sit under its page, where `Special:PrefixIndex` lists them. A sprint is created by `Special:CreateSprint`, which writes the page with the model set, or by creating a wikitext subpage and changing its model with `action=changecontentmodel` (§4.5). Both are page `create` records in `pages`. Sprints themselves are in [15](15-structured-pages.md). `Project` also allows `sanitized-css` for the site-styles page ([0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §1; [11](11-rendering-templates-and-modules.md)).

### 3.6 The Category namespace

*Sources: [0038](../decisions/0038-page-metadata-and-categories.md) §4.*

Category (14) is implemented as a `pages` namespace with text models. This is the exception the numbering policy's first rule allows ("not implemented unless an ADR says so").

| Field | Value |
|---|---|
| Normalizer and case | `first-letter` |
| Content models | `wikitext` only, since a category page's `__HIDDENCAT__` and parent categories are wikitext (§5.3) |
| Subpages | No |
| Creation | Anyone with `edit`, as `Project` (§3.5) |
| Talk | Category talk (15), `triplespace-talk`, under the policy's second rule |

**A category page shows its description and its members.** The members are listed in two groups, subcategories and pages, each sorted by sort key. The sort order is the `category.collation` `site` setting, whose default is MediaWiki's `uppercase` ([23](23-configuration-and-registry.md)). Moving a category page does not move its members, as on MediaWiki: the old name keeps its members until their text changes.

### 3.7 The Domain namespace

*Sources: [0009](../decisions/0009-keyed-entity-types-and-domain.md) §11.*

| Field | Value |
|---|---|
| Canonical name | `Domain` |
| Kind | `pages`, with the model `triplespace-domain` (§4.4) |
| Normalizer | The Domain normalizer ([0009](../decisions/0009-keyed-entity-types-and-domain.md) §2; [04](04-entities-and-identifiers.md)) |
| Reported `case` | `case-sensitive` (§2.1) |
| Subpages | No. A `/` is not valid in a key |
| Talk namespace | `Domain talk`, a `pages` namespace with the model `triplespace-talk` |
| Number | 210, with `Domain talk` at 211 |

The Domain entity type itself, its key and its IRIs are in [04](04-entities-and-identifiers.md).

## 4. Content models

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §5; [0041](../decisions/0041-content-models.md) §1, §2, §3, §5, §10.*

### 4.1 Every page has a content model

*Sources: [0041](../decisions/0041-content-models.md) §1; [0008](../decisions/0008-namespaces-and-document-pages.md) §5.*

**Every page, whatever its namespace, has exactly one content model in its main slot.** That includes entity pages, threads, talk pages and file pages, not only document pages. The model decides where the page's content comes from (§4.3), how it is serialized and validated, how it is rendered, and whether `action=edit` can change it. Models are registry data in `docs/registry/content-models.toml`, embedded by `scatter-pages` ([23](23-configuration-and-registry.md)).

**Where a page's model is recorded depends on its source** (§4.3):

- For a **text** model, the model is stored in the page's `page` records (§3.2) and can change with `action=changecontentmodel`.
- For every other source, the model is **fixed by the registry**: an entity page's model follows from its entity type, a thread's and a talk page's from their namespace. It is never stored in a record and never changes.

**Rendering code is per model.** Each model implements the content-model trait in `scatter-pages` ([0005](../decisions/0005-crate-organization.md) §2; [22](22-crates-and-stack.md)), so an instance can add models without changing the page format. In Scatterbase's terms, the stored text is the blob and the content model is the view.

### 4.2 Model IDs: generic, Triplespace, reserved

*Sources: [0041](../decisions/0041-content-models.md) §2; [0008](../decisions/0008-namespaces-and-document-pages.md) §5.*

| Kind of model | ID | Examples |
|---|---|---|
| **MediaWiki's or a Wikibase extension's** | Their ID, unchanged and with their meaning | `wikitext`, `json`, `text`, `wikibase-item`, `wikibase-mediainfo` |
| **Generic**: a format the wider world already names, with no Triplespace-specific meaning | The plain name, no prefix | `markdown`, `yaml` |
| **Unique to Triplespace** | `triplespace-` and a name | `triplespace-thread`, `triplespace-domain` |

**Every ID that MediaWiki core or any Wikibase extension uses is reserved**, as their namespace numbers are (§1.3, rule 1): it is listed in the registry, never given another meaning, and not implemented unless an ADR says so. Reserved and not implemented: `css`, `javascript` and `unknown` (core), and `wikibase-query`, Wikibase's never-shipped model ([0063](../decisions/0063-query-namespace.md) §3). `css` and `javascript` stay unimplemented for the reason §4.5 gives. `wikibase-lexeme` (WikibaseLexeme) and `EntitySchema` (EntitySchema) are implemented ([0066](../decisions/0066-lexemes.md) §3, [0064](../decisions/0064-entityschema-and-validation.md) §3).

IDs that other MediaWiki extensions use are not reserved. A generic ID is used only with the meaning the wider ecosystem gives it, so it cannot clash with another extension's use of it.

### 4.3 Sources, and what a model provides

*Sources: [0041](../decisions/0041-content-models.md) §5; [0008](../decisions/0008-namespaces-and-document-pages.md) §5.*

A model's **source** says where its content comes from and how it is written:

| Source | Content comes from | Written by | Revisions |
|---|---|---|---|
| **text** | The full text stored in each `page` record (§3.2) | `action=edit` and the page routes | Its own |
| **entity** | The fold of the entity's change sets, resolved across source graphs ([0002](../decisions/0002-source-graphs-and-mass-ingest.md), [0004](../decisions/0004-identity-clusters-and-equivalence.md); [04](04-entities-and-identifiers.md), [05](05-providers-and-ingest.md)) | Change sets: the Wikibase modules, ingest | Its own (mirrored entities' are provider-ranged, [0013](../decisions/0013-postgres-storage.md) §6) |
| **thread** | The fold of the thread's records ([0019](../decisions/0019-discussions.md) §1; [14](14-discussions.md)) | The thread routes | Its own: one per record |
| **composite** | Other pages: a talk page is the threads attached to it ([0019](../decisions/0019-discussions.md) §2) | Nothing; it changes when its members do | None of its own: its history is its members' ([0019](../decisions/0019-discussions.md) §7) |
| **statements** | A page's statement change sets ([0038](../decisions/0038-page-metadata-and-categories.md) §1; [06](06-statements-and-properties.md)) | The Wikibase modules on an `M` ID ([0041](../decisions/0041-content-models.md) §7; [12](12-files-and-media.md)), and the page statement routes | The page's own; a statement revision is a page revision |

**Direct editing follows the source.** Only text models support it. This is MediaWiki's `ContentHandler::supportsDirectEditing()` as one registry field, and it replaces the per-kind refusals earlier ADRs wrote one at a time ([0041](../decisions/0041-content-models.md) §8; [18](18-api.md)). Only text models are stored in the page's own records.

**The content-model trait in `scatter-pages`** covers what every source needs:

| Operation | text | entity | thread | composite | statements |
|---|---|---|---|---|---|
| Validate submitted content | §4.5 | — | — | — | — |
| Serialize as of a revision (`rvprop=content`, export) | The text | Wikibase JSON ([wikibase-compat.md](../api/wikibase-compat.md)) | The `GET /thread/{page ID}` body ([0019](../decisions/0019-discussions.md) §9) as of that revision | — | MediaInfo JSON ([0041](../decisions/0041-content-models.md) §7) |
| Plain text for search | [0014](../decisions/0014-caches-and-search.md) §7 `text` | The `entities` index fields | Subject and posts ([0019](../decisions/0019-discussions.md) §11) | — | `statement_keywords` ([0038](../decisions/0038-page-metadata-and-categories.md) §12) |
| Diff | Line diff | Wikibase's entity diff ([0012](../decisions/0012-api-requirements.md) §7) | Per post | — | Statement diff |

Rendering stays where earlier ADRs put it: text models in `scatter-pages` and `scatter-wikitext` (§5.1, [0033](../decisions/0033-backend-stack.md)), entity pages in the frame of [0010](../decisions/0010-site-ui.md) §2, threads in [0019](../decisions/0019-discussions.md) §8. The trait is implemented by the crate that owns each source ([0041](../decisions/0041-content-models.md) §12; [22](22-crates-and-stack.md)); `scatter-pages` holds the trait and the registry, and depends on none of them.

| `sanitized-css` | TemplateStyles | text | main | `text/css` | Yes | Template (10) for titles ending in `.css` | [0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §1; [11](11-rendering-templates-and-modules.md) |

The "Default in" column carries defaults only; where a model is *allowed* is said in one place, the namespace catalogue (§1.4): `markdown`, `json`, `yaml` and `text` in 0, 2 and 4, `json` also in Module (828), `triplespace-sprint` on Project (4) subpages, `sanitized-css` also in Project (4) for the site-styles page, and `wikitext` wherever §1.4 lists it.

The five text models of [0008](../decisions/0008-namespaces-and-document-pages.md) §5 validate and render as follows:

| Model ID | Validated as | Rendered as |
|---|---|---|
| `wikitext` | Any text | The subset in §5.1 |
| `markdown` | Any text | CommonMark with GitHub-style tables. Wiki links are resolved by the title resolver (§2.1), and raw HTML is sanitized to the allow-list of §5.1 ([0019](../decisions/0019-discussions.md) §5) |
| `json` | Well-formed JSON | Formatted, collapsible JSON |
| `yaml` | Well-formed YAML | Formatted YAML |
| `text` | Any text | Preformatted text |

**Five models hold a definition, not the page's content.** A `triplespace-table` page is a definition naming entities and properties, from which the grid is generated; a `triplespace-board` page is a definition, from which the thread listing is generated; a `triplespace-scope` page is a definition of a set of subjects, from which the member list is projected. A `triplespace-sprint` page is a definition of a scope, rules and a window, from which the task board is projected. A `triplespace-sparql` page is a parameterized query, from which the result table is computed. All five are text models: the definition is stored as text in the page's `page` records, revised and diffed like any text page, and `action=edit` can change it ([15](15-structured-pages.md), [14](14-discussions.md)).

**One model per entity type.** Every entity namespace hosts one entity type (§1.1), so it has one model, whichever provider the entity comes from: `Item:Q5`, `Item:WDQ42` and `Item:OAW123` are all `wikibase-item`. An entity type added by a later ADR takes a model in the same change: `wikibase-` and the type if a Wikibase extension already defines it, `triplespace-` and the type otherwise.

**An instance may add models**, as `config` records ([23](23-configuration-and-registry.md)). It may not reuse a reserved ID, or take the `triplespace-` prefix for a model the repository does not define.

### 4.5 Choosing, changing and validating a page's model

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §5; [0041](../decisions/0041-content-models.md) §1.*

- **The default comes from the namespace:** `wikitext` for `Project` and `User` (§1.4 for every namespace).
- **A title suffix overrides the default** when a page is created, as in MediaWiki: `.md` gives `markdown`, `.json` gives `json`, `.yaml` or `.yml` gives `yaml`, and `.txt` gives `text`. In Template, a title ending in `.css` takes `sanitized-css` by the same rule ([0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §1); in Module, Table, Query and Scope a title ending `/doc` is `wikitext` (§1.4).
- **The model can be changed** with `action=changecontentmodel`, which appends an `edit` carrying the new model. It moves a page only between text models its namespace allows ([0041](../decisions/0041-content-models.md) §8; [18](18-api.md)).
- **Content that fails validation is rejected** when it is saved.
- **Models whose code reaches the reader's browser unsanitized are not supported.** `css` and `javascript` are not registered: user-supplied scripts and unsanitized styles are an injection risk. `sanitized-css`, TemplateStyles' model, is supported, because every sheet passes a sanitizer that scopes it to rendered content before it reaches a browser ([0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §1–2; [11](11-rendering-templates-and-modules.md)). `Scribunto`, whose modules run on the server in a sandbox and return wikitext, is supported while a tenant has Lua on ([0043](../decisions/0043-lua-modules.md) §3).

### 4.6 Where the model is recorded and reported

*Sources: [0041](../decisions/0041-content-models.md) §10.*

- **`view.page`** ([03](03-storage-caches-and-search.md)): `content_model` holds registry IDs. Threads and talk pages are written as `triplespace-thread` and `triplespace-talk`. Entity pages keep no row in `view.page`, and their model is read from the registry by entity type. The `registry` projection has the kind `content_model`.
- **Search** ([0014](../decisions/0014-caches-and-search.md) §7; [03](03-storage-caches-and-search.md)): the `content_model` field of the `pages` index takes the same IDs.
- **Filters** ([0030](../decisions/0030-edit-filters.md) §2; [09](09-security-and-moderation.md)): `content_model` already has MediaWiki's meaning, so it takes the registry IDs: a filter on posts tests `content_model == "triplespace-thread"`.
- **RDF** ([0001](../decisions/0001-revision-metadata-rdf.md) §6; [02](02-graphs-rdf-and-query.md)): every revision node in the metadata graph carries `sw:contentModel`, not only document revisions; a statement revision of a File page carries `wikibase-mediainfo`.
- **UI** ([0010](../decisions/0010-site-ui.md) §4; [19](19-site-ui.md)): the Format selector and the model shown beside the title appear only for text models, and the selector only where the namespace allows more than one.

## 5. Wikitext, links and page metadata

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §8, §10; [0038](../decisions/0038-page-metadata-and-categories.md) §3, §5; [0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §6.*

### 5.1 The wikitext subset

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §8.*

Triplespace renders a fixed subset of wikitext. It does not implement MediaWiki's parser.

**Rendering has two stages** ([0042](../decisions/0042-template-expansion-and-parsoid.md) §1, §7; [11](11-rendering-templates-and-modules.md)). When the tenant's `wikitext.expansion` setting is on, templates, parser functions and variables are expanded natively first, and the subset renders the expanded text. A tenant may instead render through Parsoid ([0042](../decisions/0042-template-expansion-and-parsoid.md) §8). When expansion is off, the subset renders the stored text.

| Supported | Syntax |
|---|---|
| Headings | `== … ==` through `====== … ======` |
| Emphasis | `''…''`, `'''…'''` |
| Lists | `*`, `#`, `;` and `:`, nested |
| Internal links | `[[Title]]`, `[[Title\|text]]`, `[[Title#Section]]`, `[[/Subpage]]`, and links into any registered namespace, such as `[[Item:Q5]]` or `[[Domain:en.wikipedia.org]]`. An unprefixed title is a main-namespace title, so an entity is linked with its namespace (§3.3) |
| Categories | `[[Category:…]]`, `{{DEFAULTSORT:…}}` and `__HIDDENCAT__`; `[[:Category:…]]` is a plain link (§5.3) |
| Files | `[[File:…]]` embedding with MediaWiki's options and a caption, `[[:File:…]]` links to description pages, `[[Media:…]]` links to bytes, and `<gallery>` ([0039](../decisions/0039-files-and-media.md) §13; [12](12-files-and-media.md)) |
| External links | `[https://… text]` and bare URLs |
| Tables | `{\| … \|}` with header and data cells and simple attributes |
| Preformatted and code | `<pre>`, `<code>`, leading-space blocks, `<syntaxhighlight>` rendered as plain `<pre>` |
| Escaping | `<nowiki>` |
| Footnotes | `<ref>`, `<ref name=…>`, `<references />` |
| Page controls | `__NOTOC__`, `__TOC__`, `__FORCETOC__` |
| Signatures | `~~~~` and `~~~` are expanded when the page is saved, as in MediaWiki |
| Horizontal rule | `----` |
| Redirects | `#REDIRECT [[Target]]` as the first line makes the page a redirect (§2.3) |
| Safe inline HTML | An allow-list of formatting tags, such as `<br>`, `<span>`, `<div>`, `<sup>` and `<sub>`, with attributes restricted to `class`, `id` and a sanitized `style` |

**Everything else is kept and shown, not dropped.**

- Template calls (`{{…}}`) and parser functions that are not expanded render as a visible placeholder showing the call.
- External image URLs are never embedded.
- The stored source is never rewritten, so a page renders correctly if the subset grows later.

### 5.2 Links and the links projection

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §8, §10.*

**Links are resolved by the title resolver** (§2.1). A link to an entity that exists renders with its label, as Wikibase does. A link to a redirect carries the class `mw-redirect` (§2.4); a link to a title whose primary is a repository's page is an ordinary link carrying `ts-inherited`, and a link into a namespace no repository serves here leaves the wiki as an interwiki link ([0052](../decisions/0052-page-repositories-and-title-inheritance.md) §4; [13](13-mirrored-pages.md)).

**A links projection** records every link from a document page to a page or entity, after resolution ([03](03-storage-caches-and-search.md)). It serves "What links here" for both kinds of page. So `Item:Q5` lists the project pages that link to it, and `list=backlinks` works across namespaces. Links in thread posts are rows too, so it also lists the threads that discuss it ([0019](../decisions/0019-discussions.md) §5). On a tenant with expansion on, the projection reads the expanded text, so links that templates emit count, and its rows are written by the refresh job of [0042](../decisions/0042-template-expansion-and-parsoid.md) §10. A redirect's row points at its target, so "What links here" lists a page's redirects ([0051](../decisions/0051-page-redirects.md) §5); a link to a title whose primary is a repository's page is recorded by namespace and title, as a link to a missing page is, so a later fork inherits its backlinks ([0052](../decisions/0052-page-repositories-and-title-inheritance.md) §4).

### 5.3 Legacy categories are defined only in wikitext

*Sources: [0038](../decisions/0038-page-metadata-and-categories.md) §3; [0008](../decisions/0008-namespaces-and-document-pages.md) §8.*

**Membership is read from the text.** A page is in a category when the **latest revision** of a page whose content model is `wikitext` contains a category link:

| Syntax | Meaning |
|---|---|
| `[[Category:Name]]` | The page is in `Category:Name`, with the page's default sort key |
| `[[Category:Name\|key]]` | The same, with `key` as the sort key |
| `{{DEFAULTSORT:key}}` | The page's default sort key. `DEFAULTSORTKEY` and `DEFAULTCATEGORYSORT` are aliases, as in MediaWiki. This is the one parser function the projection recognises |
| `__HIDDENCAT__` | On a page in `Category`: the category is hidden |
| `[[:Category:Name]]` | A link *to* the category page, not membership, as in MediaWiki |

Names are normalized by the `Category` namespace's `first-letter` normalizer (§3.6). A category page's own category links make it a subcategory of those categories.

**Categories are a projection, never records.** Membership is a `view` table ([0038](../decisions/0038-page-metadata-and-categories.md) §10; [03](03-storage-caches-and-search.md)), like MediaWiki's `categorylinks`, rebuilt from the text. There is no API that adds a page to a category except editing its text, and there is no statement that means "member of a category". Removing a link from the text removes the membership at the next projection. This is the rule that keeps reconciliation out: **a category is defined in exactly one place.**

**Only `wikitext` has categories.** Pages in `markdown`, `json`, `yaml` and `text`, and threads, are never in a category. Native pages start with native metadata.

**A category needs no page.** A page can be in a category whose page does not exist, as on MediaWiki. The link renders red and the category still has members.

**Templates are not parsed while expansion is off.** For a tenant with `wikitext.expansion` off, categories that templates emit reach the text only through the flattening revision of §6 step 3, whose `action=expandtemplates` runs on the source wiki and writes the category links and `__HIDDENCAT__` into the flattened text. A template call added after an import renders as a placeholder (§5.1) and emits nothing, and categories MediaWiki's parser adds on its own, such as tracking categories for broken file links, are in no text. With expansion on ([0042](../decisions/0042-template-expansion-and-parsoid.md) §9; [11](11-rendering-templates-and-modules.md)), membership is read from the **expanded** text: categories that templates emit count, `<includeonly>` categories reach transcluding pages, and expansion adds MediaWiki's tracking categories for its own conditions.

**Rendering.** The foot of a page lists its categories as links to their pages in the `Category` namespace. Hidden categories are listed separately, collapsed. The source text is still never rewritten.

### 5.4 Category mappings

*Sources: [0038](../decisions/0038-page-metadata-and-categories.md) §5.*

**A mapping turns membership into a page statement.** Mappings are tenant configuration, `config` records of the kind `category-mapping`, whose code is the mapping's name ([23](23-configuration-and-registry.md)):

| Field | Meaning |
|---|---|
| `category` or `pattern` | An exact category name, or a pattern over category names with named captures (below) |
| `property` | The statement's property, local or mirrored |
| `value` | The main value, as a canonical JSON data value, or a capture |
| `qualifiers` | Optional: a list of `{property, value}`, where a value may be a capture |

Written as TOML for illustration, with illustrative local IDs:

```toml
[mapping.cleanup]
pattern    = "Articles needing cleanup from {when:month-year}"
property   = "P40"                      # maintenance tag
value      = { entity = "Q812" }        # cleanup
qualifiers = [ { property = "P41", value = "{when}" } ]   # point in time

[mapping.cleanup-undated]
category = "All articles needing cleanup"
property = "P40"
value    = { entity = "Q812" }
```

**Captures** are written `{name:type}`. Four types exist: `year` and `month-year` (time values with precision 9 and 10, reading month names in the site's content language), `date` (precision 11) and `text` (a string). A category name whose capture does not parse does not match. This covers MediaWiki's dated maintenance categories, which are the common case.

**Semantics.**

- **Each membership that matches a mapping yields one projected statement** ([0038](../decisions/0038-page-metadata-and-categories.md) §2; [06](06-statements-and-properties.md)) on the member page. A page in two matching categories gets two statements, which fuse if they are identical.
- **Hidden categories are mapped like any other.** Most maintenance categories are hidden.
- **Statement IDs are name-based UUIDs** of the page ID, the mapping name and the category name, following the rule of [0002](../decisions/0002-source-graphs-and-mass-ingest.md) §8.4 for sources with no IDs of their own. They stay stable across rebuilds.
- **A change to a mapping re-runs it** over the members of every category it matches, as a job with progress, as a constraint change re-checks a property ([0031](../decisions/0031-property-constraints.md) §2).
- **Mappings produce statements about the page only.** A category such as "1952 births" is a fact about the subject, and projecting it onto the linked item would let an article's text change the item's data. That boundary is not crossed until there is a UI that makes the difference plain.

**Migrating a page off a category is optional.** A page can keep its category and still have the native statement. When a tenant wants the text free of a category, the **make-it-real job** does it per mapping: for each member page, it appends a change set asserting the statement and a text revision removing the category link, in one transaction with one base check, grouped in history under the job ([0010](../decisions/0010-site-ui.md) §1, principle 3). Because the asserted and projected statements fuse, there is no moment at which the page shows two versions of the fact.

### 5.5 Page properties

*Sources: [0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §6.*

**Page properties are stored,** in the table MediaWiki has ([03](03-storage-caches-and-search.md)):

```sql
CREATE TABLE view.page_prop (                   -- MediaWiki's page_props (§6)
  page_id bigint NOT NULL REFERENCES view.page,
  name text NOT NULL,
  value bytea NOT NULL,                           -- text, or compact JSON for templatedata; compressed over 1 KB
  sortkey double precision,                       -- for numeric properties, as MediaWiki's pp_sortkey
  PRIMARY KEY (page_id, name)
);
CREATE INDEX page_prop_name ON view.page_prop (name, sortkey, page_id);
```

**Who writes which property:**

| Property | Set by | Written by |
|---|---|---|
| `templatedata` | `<templatedata>` ([0055](../decisions/0055-templatestyles-templatedata-and-page-properties.md) §5; [11](11-rendering-templates-and-modules.md)) | The page projection, in step 2, synchronously; copied to the transcluding template by the refresh job |
| `defaultsort` | `{{DEFAULTSORT:}}` (§5.3) | The page projection, in step 2, as the category sort key already is |
| `workspace.{role}` | `{{#workspace:}}` on a project page ([0062](../decisions/0062-workspaces.md) §2; [15](15-structured-pages.md)) | The refresh job, from the expander's page properties; read by blocks on the page and its subpages |
| `displaytitle` | `{{DISPLAYTITLE:}}` | The refresh job ([0042](../decisions/0042-template-expansion-and-parsoid.md) §10), from the expander's page properties, under MediaWiki's `$wgRestrictDisplayTitle` rule: the value must normalize to the page's title, else it is ignored |
| `wikibase-shortdesc` | `{{SHORTDESC:…}}`, the Wikibase Client magic word Wikipedia's `{{Short description}}` template wraps, `implemented` in the registry under origin Wikibase Client | The refresh job |
| `disambiguation` | `__DISAMBIG__`, status `implemented` | The refresh job |
| `noindex`, `index`, `notoc`, `forcetoc`, `noeditsection`, `newsectionlink`, `nonewsectionlink`, `nogallery`, `staticredirect`, `expectunusedcategory`, `hiddencat` | The behaviour switches, as MediaWiki stores each as a property | The refresh job (`hiddencat` also in step 2, as §5.3 reads it) |
| `wikibase_item` | The page's paired item ([0038](../decisions/0038-page-metadata-and-categories.md) §6; [06](06-statements-and-properties.md)), as Wikibase Client sets it, so tools that read `prop=pageprops&ppprop=wikibase_item` find it | The sitelink projection |

Properties the refresh job writes are written in the same transaction as the links, categories and transclusions of a render ([0042](../decisions/0042-template-expansion-and-parsoid.md) §10), and are therefore among the `view` tables that render re-creates rather than replays. A property the latest render did not set is deleted.

**What reads them.**

- **The frame** shows `displaytitle` as the page's heading, where set, and marks a `disambiguation` page as one; `noindex` sets the response's robots meta ([19](19-site-ui.md)).
- **`prop=pageprops`** with `ppprop`; **`list=pageswithprop`** and **`generator=pageswithprop`** with `pwppropname`; **`prop=info&inprop=displaytitle`**; **`prop=description`**, which returns `wikibase-shortdesc` where set and the paired item's description otherwise, as Wikipedia's does; **`action=templatedata`** ([18](18-api.md)).
- **`Special:PagesWithProp`** is served as a report over `view.page_prop`, with the extension's form: property name, then the pages carrying it ([21](21-special-pages.md)).
- **Search** ([0014](../decisions/0014-caches-and-search.md) §7): the `pages` index gains `short_description`, shown in the suggester beneath the title, as Wikipedia's suggester shows it.
- **RDF** ([0038](../decisions/0038-page-metadata-and-categories.md) §11; [02](02-graphs-rdf-and-query.md)): the page node gains `schema:description` from `wikibase-shortdesc`, in the content language, beside its `schema:name`. This gives the short description MediaWiki's shape, which is a page property set in the text, and leaves whether pages get terms of their own open.

**Foreign pages** have no rows here; their properties are in the bundle's metadata ([0053](../decisions/0053-mirrored-pages.md) §1; [13](13-mirrored-pages.md)), and `prop=pageprops` on an inherited title serves them from there.

### 5.6 Page revisions in RDF

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §10.*

**Page revisions get revision nodes** in the metadata graph, as entity revisions do ([0001](../decisions/0001-revision-metadata-rdf.md) §1, §6; [02](02-graphs-rdf-and-query.md)):

- The page's document node is `{base}/page/{page ID}`.
- Its revision nodes carry the actor, timestamp, summary, tags, flags, content model, size and hash, in the vocabulary of 0001.
- A page's statements go into the main graph, with the page's document node as subject ([0038](../decisions/0038-page-metadata-and-categories.md) §11). Page text and category membership are not RDF.

## 6. Importing pages from another wiki

*Sources: [0008](../decisions/0008-namespaces-and-document-pages.md) §9; [0042](../decisions/0042-template-expansion-and-parsoid.md) §13.*

Pages are imported from a MediaWiki XML export with full history. An import is a job ([0002](../decisions/0002-source-graphs-and-mass-ingest.md) §8.3; [05](05-providers-and-ingest.md)), and the procedure is:

1. **Import every revision** as page records, in order. Each revision keeps its original timestamp as upstream metadata. The time the record is appended is still the time of the import.
2. **Attribute each revision to its original author** under [0007](../decisions/0007-actor-identity.md) §5 ([07](07-actors-and-accounts.md)). An author on a registered issuer keeps that issuer's numeric ID. Any other author becomes an `imported` surrogate.
3. **Flatten templates in one extra revision, where the tenant does not expand them.** Where the latest revision uses templates, a bot fetches the expanded text from the source wiki with `action=expandtemplates` and saves it as a new revision. History stays faithful to the source, and the current text needs no template engine. With `wikitext.expansion` on, this step is optional: the importer may bring the Template and Module pages with full history, as ordinary pages, instead of flattening. Flattening remains the procedure for a tenant with expansion off, or by choice.

**A template census comes first.** Before an import, the pages are scanned for templates, parser functions and tags outside §5.1. The census decides whether step 3 is enough, or whether the subset should grow first. It also reports which templates and modules the pages use, and which of those the export contains, and which variables, functions and tags fall outside the registry ([0042](../decisions/0042-template-expansion-and-parsoid.md) §5; [11](11-rendering-templates-and-modules.md)).

**Page IDs on an adopted wiki.** When the source is the wiki the tenant adopted, imported pages keep their source page IDs, supplied in header field 9 as adopted entities' are, and the page-ID floor set at adoption already covers them ([0035](../decisions/0035-adopting-a-wikibase.md) §4; [08](08-tenants-and-instances.md)).

**Files.** Exports with `<upload>` elements import file versions, and `triplespace-cli files import` imports a directory as `importImages.php` does ([0039](../decisions/0039-files-and-media.md) §14; [12](12-files-and-media.md)).

**Talk namespaces are converted to threads.** A wikitext talk page in an export is imported as threads homed on its subject's talk page, split by level-two heading with the frontmatter first, each created closed with the `archived` status and holding its section's wikitext as the opening post ([0054](../decisions/0054-forking-a-mirrored-page.md) §5; [14](14-discussions.md)); a project-wide discussion page lands on a board the importer names.

**The forms.** `Special:Import` starts this job after showing the census. `Special:Export` is its counterpart: it writes MediaWiki XML of pages and local entities, and a verifiable `records` format ([0047](../decisions/0047-special-pages.md) §8; [21](21-special-pages.md)).
