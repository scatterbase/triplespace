## Context

MediaWiki keeps two kinds of history:

- **Revisions** record changes to a page's content.
- **Log entries** record actions that are not content changes. Examples are deleting and restoring a page, hiding parts of past revisions, protecting a page, importing revisions, and renaming a user.

Each log entry has these fields:

- an ID from one sequence per wiki;
- a type and an action, such as `delete/delete`;
- a timestamp;
- the performer;
- a target page, given as a namespace and title, and its page ID;
- a comment;
- parameters that depend on the type;
- visibility bits.

The visibility bits hide the action and target, the comment or the performer. A fourth bit marks the hiding as suppression.

On the reference install, `list=logevents` offers 16 log types and 44 actions ([mediawiki-compat.md](../api/mediawiki-compat.md), `letype` and `leaction`). Wikidata also has log types from its extensions.

**Logs hold facts that nothing else does.** After an entity is deleted, the deletion log is the only public record of who deleted it, when and why. Triplespace's mirror tombstone ([0002](0002-source-graphs-and-mass-ingest.md) §5) records *that* the entity went away, not *why*. The same holds for:

- revision deletion, which hides parts of past revisions;
- protection;
- user renames, which [0007](0007-actor-identity.md) needs to keep foreign actor records current.

To represent Wikidata's history faithfully, Triplespace has to carry its logs.

**No RDF vocabulary covers them.** Wikibase's RDF export describes entities only. [0001](0001-revision-metadata-rdf.md) §6 assigns log events to Activity Streams 2.0 in one table row. It says nothing about how logs are ingested, keyed, kept or erased. That row also lists merges as log events. On Wikibase they are not:

- `wbmergeitems` writes ordinary revisions to both items and turns one of them into a redirect.
- MediaWiki's `merge/merge` log records history merges, which are a different operation.

**Triplespace has log-like actions of its own:**

- erasures ([0006](0006-log-integrity-and-erasure.md) §7);
- retention changes and conversions ([0002](0002-source-graphs-and-mass-ingest.md) §5–6);
- account links ([0007](0007-actor-identity.md) §7);
- page moves and deletions ([0008](0008-namespaces-and-document-pages.md) §4);
- import jobs ([0002](0002-source-graphs-and-mass-ingest.md) §8.3).

The site UI shows all of these as log events ([0010](0010-site-ui.md) §5, §7). They need one model.

## Decision

### 1. Faithful to the public record

Triplespace mirrors what a provider publishes, and nothing more.

- **Some logs are never public.** The `suppress` log and CheckUser logs never are.
- **Hidden fields stay hidden.** A public entry whose performer, comment or target is hidden arrives with those fields empty.
- **Later hiding is followed.** When upstream hides something after the instance has mirrored it, the instance removes it too (§5). This follows the rule of [0002](0002-source-graphs-and-mass-ingest.md) §5: a faithful mirror forgets what upstream withdraws.

### 2. Log graphs

Log events that have no other home are written to log graphs. These are source graphs, like the actor graphs of [0007](0007-actor-identity.md) §8.

| Graph | Illustrative IRI | Kind | Written by | History | Integrity | Export |
|---|---|---|---|---|---|---|
| **Local log** | `{base}/graph/log` | Source | Jobs, and actions with no other record (§6) | Full | `logged` | Internal only |
| **Provider log**, one per provider | `{base}/graph/log/wikidata` | Source | That provider's log sync jobs | Full | `hashed` | Internal only |

**The history policy is always `full`.** A log event does not replace an earlier state, so compacting by key would destroy events. A provider log keeps full history even when its entity mirror is `latest`. Records leave a log graph only through `erase` (§5).

**The integrity policies follow the existing pattern.**

- The local log is instance data, so it is `logged`, like the local graph.
- A provider log is `hashed`, like the provider's mirror ([0006](0006-log-integrity-and-erasure.md) §4). Its completeness against upstream cannot be proved.

**Both are internal only.** Log events reach RDF only in the metadata graph (§8). Following [0001](0001-revision-metadata-rdf.md) §2, they are never exported to external stores. The API serves them (§9).

### 3. Log event records

Every record in a log graph has the payload type `scatter:v0/logevent`. Its payload holds:

> **Amended.** The log graphs now admit other payload types beside `logevent`: `upstream-revision` in a provider log ([0015](0015-record-format-and-partition-registry.md) §4); `acl` for moderation, `filter` and `filter-hit` in the local log ([0023](0023-moderation.md) §3, [0030](0030-edit-filters.md) §5); and `erase` everywhere. `docs/registry/graphs.toml` lists them. Comment, performer and hidden fields follow the part layout of 0015 §1, so the redacted-copy procedure of §5 below is replaced by per-part erasure (0015 §4).

- the log type and action, as MediaWiki strings;
- the time of the event at its source;
- the upstream log ID, for provider logs;
- the target: an entity ID, page ID, actor key or job ID;
- the performer's actor key ([0007](0007-actor-identity.md) §1);
- the comment;
- typed parameters (§7);
- the visibility bits, as upstream last reported them.

**The header key is the target's identifier, never a title or name** ([0006](0006-log-integrity-and-erasure.md) §3):

| Target | Key |
|---|---|
| Entity | The prefixed ID, such as `WDQ123` |
| Keyed entity, such as a Domain | Its surrogate ([0009](0009-keyed-entity-types-and-domain.md) §7) |
| Document page | The page ID ([0008](0008-namespaces-and-document-pages.md) §4) |
| Account | The actor key, such as `wikidatawiki:12345` |
| Job | The job ID |
| Hidden or unresolvable | `null` |

Upstream titles are mapped to keys when the adapter reads them.

- **Entity pages** go through the provider registry, which maps each entity namespace to a type code. On Wikidata, `Q42` in the main namespace becomes `WDQ42`, `Property:P31` becomes `WDP31`, and `Lexeme:L1` becomes `WDL1`.
- **User titles** are resolved to numeric IDs with the issuer's API, as [0007](0007-actor-identity.md) §5 does for imported edits.
- **Titles in namespaces the provider does not mirror** are skipped.

### 4. Which upstream logs are mirrored

The provider registry lists the log types each provider mirrors. It is configuration, recorded in the log ([0004](0004-identity-clusters-and-equivalence.md) §9). The default for Wikidata:

| Log | Mirrored | Why |
|---|---|---|
| `delete/delete`, `delete/restore` | Yes | Who deleted or restored an entity, when and why |
| `delete/revision` | Yes | Triggers redaction of held revisions (§5) |
| `delete/event` | Yes | Triggers redaction of held log events (§5) |
| `protect/*` | Yes | Protection history |
| `import/*`, `create/create`, `contentmodel/*` | Yes | Page provenance |
| `renameuser/*` | Consumed (§6.2) | Updates foreign actor records. Stored without names. |
| `move/*`, `merge/merge` | No | Entity pages cannot be moved. They become relevant only if non-entity pages are mirrored. |
| `block/*`, `rights/*`, `newusers/*`, `patrol/*`, `tag/*`, `managetags/*`, and extension logs such as thanks and AbuseFilter | No | They describe people and moderation, not the data. Mirroring them would raise the privacy stakes without adding to any entity's history. |

**The backfill covers events whose target lies in a mirrored entity namespace, whether or not the instance holds the entity.** The deletion log of an item that was deleted before the mirror began still answers "what happened to Q123?". An instance may narrow the backfill to entities it holds.

**Sources:**

| Purpose | Source |
|---|---|
| Backfill and periodic reconciliation | The provider's XML logging dump (`pages-logging`) |
| Filling gaps | `list=logevents`, paged by time |
| Live updates | The EventStreams `recentchange` stream, which carries log events with their IDs, types, actions and parameters. `revision-visibility-change` is also used. |

Parameters in dumps come in two formats: PHP-serialized arrays in newer entries, and newline-separated values in older ones. The adapter parses both.

**Each log sync is a job** ([0002](0002-source-graphs-and-mass-ingest.md) §8.3). An event is identified by its upstream log ID, so re-reading an event the instance already holds changes nothing.

### 5. Following upstream when it hides something

Three upstream actions withdraw public data. Triplespace follows each of them.

**A log event's fields are hidden.** This is announced publicly as `delete/event`, or discovered during reconciliation. The sync job:

1. appends a redacted copy of the event, with the same upstream log ID, the hidden fields removed and the new visibility bits;
2. erases the original record with an `erase` record ([0006](0006-log-integrity-and-erasure.md) §7) whose reason class is `upstream`.

Projections use the newest record for each upstream log ID.

**A log event is suppressed outright.** It then vanishes from the API and the dumps without any public announcement.

- Each reconciliation against a new logging dump erases held events that the dump no longer contains, with reason class `upstream`, and appends no copy.
- The sweep aborts if the number of erasures exceeds a configured threshold, as the `snapshot` sweep does ([0002](0002-source-graphs-and-mass-ingest.md) §8.4). A truncated dump must not wipe the log.

**Parts of past revisions are hidden** (`delete/revision`, or a `revision-visibility-change` event). The affected revision IDs are in the event's parameters.

- For each affected revision the instance holds, the sync fetches the revision's current metadata and redacts it in the same way: a redacted copy, then erasure of the original.
- This covers backfilled upstream revisions of retained entities ([0002](0002-source-graphs-and-mass-ingest.md) §5) and observed states that carry the revision's ID.
- If the revision's content is hidden, the mirrored state for that revision is erased. MediaWiki does not allow hiding the content of an entity's current revision, so the entity's current mirrored state is never affected.

**Retention does not override upstream hiding (amends [0002](0002-source-graphs-and-mass-ingest.md) §5).** `retain` keeps an entity that upstream deletes. It does not keep fields that upstream hides for privacy or legal reasons. Once a retained entity has been deleted upstream and materialized into the local graph, it is local data. Upstream can no longer change it, and hiding within it becomes a local decision.

**`upstream` joins the reason classes** that [0006](0006-log-integrity-and-erasure.md) §7 leaves open.

### 6. Local log events

#### 6.1 Projected, not written twice

Most local actions already have a record elsewhere: an erase record in its target's partition, a page record, an actor record, a change set. Writing a second log record for the same action would mean:

- two writes that cannot be made atomic across partitions;
- two places to erase.

**A log event for such an action is a projection of its record.** The log graph holds only actions that have no other record.

| Log type/action | Comes from | Visible to |
|---|---|---|
| `create/create` | The first record of a local entity or document page, unless it was adopted (next rows) | Everyone |
| `delete/delete`, `delete/restore` | A `read` ACL on a page, thread or local entity, and its retirement ([0023](0023-moderation.md) §3–4; formerly a page `delete` or `undelete`, [0008](0008-namespaces-and-document-pages.md) §4) | Everyone |
| `delete/revision`, `delete/event` | A `record` ACL on a record's parts ([0023](0023-moderation.md) §5) | Everyone |
| `suppress/*` | The same ACLs naming the suppression group ([0023](0023-moderation.md) §7) | The suppression group |
| `patrol/patrol`, `patrol/unpatrol` | A patrol or unpatrol record in the local log ([0023](0023-moderation.md) §6, as amended 2026-09-27) | Everyone |
| `abusefilter/create`, `abusefilter/modify` | A filter record in the local log ([0030](0030-edit-filters.md) §5) | Everyone, or the filter's viewers if it is private |
| `abusefilter/hit` | A filter-hit record ([0030](0030-edit-filters.md) §5) | Everyone, or `abusefilter-log-private` for a private filter's hits |
| `move/move` | A page `move` | Everyone |
| `thread/attach`, `thread/detach` (new) | A thread `attach` or `detach` record, and each `also` entry of a thread `create` ([0049](0049-boards.md) §9) | Everyone |
| `contentmodel/change` | A page `edit` that changes the model | Everyone |
| `import/interwiki`, `import/upload` | A page import job ([0008](0008-namespaces-and-document-pages.md) §9) | Everyone |
| `import/upload`, `import/interwiki` (entities) | The first record of an adopted entity, from a dump or from the live API ([0035](0035-adopting-a-wikibase.md) §6) | Everyone |
| `upload/upload`, `upload/overwrite`, `upload/revert` | An `upload` record ([0039](0039-files-and-media.md) §2); `import/upload` for one with action `import` (0039 §14) | Everyone |
| `takedown/takedown`, `takedown/reinstate` (new) | A `blob` ACL in the instance `log` and its retirement ([0039](0039-files-and-media.md) §10), projected into each affected tenant's log | Everyone; no reason or notice when confidential |
| `newusers/create` | The first actor record of a registered local user. Temporary accounts are not logged. | Everyone |
| `newusers/create2` | The first actor record of a subsidiary account; the performer is its operator ([0024](0024-subsidiary-accounts.md) §2) | Everyone |
| `bot/transfer` (new) | An actor record that changes a subsidiary's operator ([0024](0024-subsidiary-accounts.md) §2) | Everyone |
| `renameuser/renameuser` | An actor record with a new name ([0007](0007-actor-identity.md) §4) | Everyone |
| `renameuser/vanish` (new) | The placeholder record written by a vanish | Everyone, with no past name |
| `link/link` (new) | A `link-account` record ([0007](0007-actor-identity.md) §7) | Everyone, while the link exists |
| `retention/set` (new) | A `retain` operation | Everyone |
| `convert/convert` (new) | A `convert` operation | Everyone |
| `erase/erase` (new) | An `erase` record in any partition | Administrators. Whether any reason class is shown publicly is open in [0006](0006-log-integrity-and-erasure.md). |
| `job/start`, `job/finish`, `job/fail`, `job/revert` (new) | Job records in the local log (§6.3) | Everyone |
| `protect/*` | An `acl` record in the local log ([0023](0023-moderation.md) §3) | Everyone |
| `managetags/create`, `/delete`, `/activate`, `/deactivate` | A `tag` config record ([0030](0030-edit-filters.md) §5, as amended) | Everyone |
| `key/register`, `key/rotate`, `key/revoke` (new) | A `key` record in `actors` ([0015](0015-record-format-and-partition-registry.md) §1 and [0024](0024-subsidiary-accounts.md) §4, as amended) | Everyone |
| `tag/update` | A record whose attestation tags were changed by `action=tag` (0030 §5) | Everyone |
| `block/*`, `rights/*` | `block` and `membership` records in the `actors` partition ([0016](0016-permissions-and-access-control.md) §3) | Everyone |

**Erasure propagates automatically, because events are projections.**

- When a vanish erases a user's actor records, every rename event that showed a past name loses it.
- When an unlink erases a `link-account` record, the `link/link` event goes too. What remains is the erase record, which only administrators see, as [0007](0007-actor-identity.md) §7 intends.

#### 6.2 Upstream renames (amends [0007](0007-actor-identity.md) §4)

An upstream `renameuser` event does two things.

1. **It updates the foreign actor's record** in `actors/{provider}`, with the new name. Compaction under `latest` then removes the old name, as [0007](0007-actor-identity.md) §4 already describes.
2. **It is kept in the provider log without names.** The key is the actor key, and the parameters that carry names are dropped. The UI shows "Renamed on Wikidata", with a link to the upstream log entry. Keeping the names would put every past name of every renamed account into a graph that is never compacted, which [0007](0007-actor-identity.md) avoids on purpose.

#### 6.3 Jobs live in the local log (amends [0002](0002-source-graphs-and-mass-ingest.md) §8.3)

- **A job record is appended to the local log** when a job starts. It holds everything [0002](0002-source-graphs-and-mass-ingest.md) §8.3 lists.
- **The job ID is minted by the instance** in sequence and is the record's key.
- **Further records under the same key** mark the job's finish, failure or revert.
  - The finish record carries the job's counts by outcome: created, merged, unchanged and rejected; and, since 2026-09-28, the count of upstream snak and reference hashes kept because the recomputation differed, by value type ([0006](0006-log-integrity-and-erasure.md) §2, as amended).
  - It also carries the checkpoint written at the end of the job ([0006](0006-log-integrity-and-erasure.md) §6).
- **Records a job writes in other partitions** carry the job ID in their attestation ([0006](0006-log-integrity-and-erasure.md) §3).

A mirror sync is a local action, even though it writes to a mirror. Its job record is therefore in the local log.

> **Amended by [0040](0040-instance-prerogatives.md) §4 and §7.** A job that writes instance acts into tenants (a reclamation run, an expunge's propagation, a deleted tenant's erasure, a cascade of renames) records its job record in the **instance `log`**, and that record is the authority its writes cite. Log events projected from instance acts keep their own types, with the operator actor `instance:{farm slug}` as performer and `instance: true` in their parameters.

> **Amended by [0046](0046-primary-tenant.md) §4.** A mirror sync is an **instance** action: its job record is appended to the instance `log`, keyed by job ID, not to any tenant's `log`, so the instance's job history does not depend on which tenant is primary. Tenant bulk jobs stay in the tenant's `log`.

### 7. Parameters

Each log type's parameters are typed in the payload. The raw parameters are never the only form stored.

| Log | Typed parameters |
|---|---|
| `delete/restore` | The number of revisions restored |
| `delete/revision`, `delete/event` | The affected revision or log IDs; the fields hidden and the fields revealed |
| `protect/*` | For each restriction (such as edit or move), the level and the expiry; whether protection cascades |
| `import/*` | The interwiki prefix or the upload, and the number of revisions |
| `contentmodel/*` | The old and new models |
| `retention/set` | The old and new policies |
| `convert/convert` | The local ID that was minted |
| `erase/erase` | The reason class and the authority reference ([0006](0006-log-integrity-and-erasure.md) §7) |
| `job/*` | The job's source, version, mode and outcome counts |

A parameter the adapter does not recognize is kept as a raw key–value pair. Nothing is dropped, except names (§6.2).

### 8. RDF (amends [0001](0001-revision-metadata-rdf.md) §6)

Log events are projected into the **metadata graph** only.

**IRIs:**

| Event | IRI |
|---|---|
| Upstream | `{article path}Special:Redirect/logid/{id}` on the provider's wiki, for example `https://www.wikidata.org/wiki/Special:Redirect/logid/{id}`. This parallels the upstream actor IRIs of [0007](0007-actor-identity.md) §2. |
| Local | `{base}/record/{partition}/{offset}`, the IRI of the record the event comes from |

Local event IRIs do not wait for the global revision and log ID question ([0008](0008-namespaces-and-document-pages.md), open questions). Partition numbers and offsets are fixed at append time and never reused. They are the same coordinates that inclusion proofs use ([0006](0006-log-integrity-and-erasure.md) §9).

**Types.** Every log event is a `prov:Activity`. Activity Streams 2.0 types are used where they fit, and `scatter:` subclasses of `as:Activity` are minted where they don't:

| Log | Type |
|---|---|
| `delete/delete` | `as:Delete` |
| `delete/restore` | `as:Undo`, whose `as:object` is the deletion when the instance holds it |
| `create/create`, `newusers/create` | `as:Create` |
| `move/move` | `as:Move` |
| `thread/attach` | `as:Add`, with `as:target` the talk page or board ([0049](0049-boards.md) §9) |
| `thread/detach` | `as:Remove`, with `as:origin` the talk page or board |
| `contentmodel/*` | `as:Update` |
| `protect/*` | `scatter:Protect` |
| `delete/revision`, `delete/event` | `scatter:ChangeVisibility` |
| `import/*` | `scatter:Import` |
| `renameuser/*` | `scatter:Rename` |
| `link/link` | `scatter:LinkAccount` |
| `retention/set` | `scatter:SetRetention` |
| `convert/convert` | `scatter:Convert` |
| `erase/erase` | `scatter:Erase` |
| `job/*` | `scatter:JobEvent`. The job itself is a `prov:Activity` at `{base}/job/{id}`. |

**Properties:**

- `as:actor`: the performer's actor IRI. It is omitted when the performer is hidden, and the event then carries `scatter:attributionHidden` ([0007](0007-actor-identity.md) §9).
- `as:object`: the target's **document node**, as [0001](0001-revision-metadata-rdf.md) §1 requires. That is `data:Q123` for an entity, `{base}/page/{id}` for a document page, and the actor IRI for an account. For `delete/revision`, it is the affected revision nodes.
- `as:result`: for `convert`, the minted entity's document node.
- `as:published`: the time of the event at its source.
- `scatter:logType`, `scatter:logAction`: the MediaWiki strings, always kept.
- `scatter:comment`: omitted when hidden.
- The typed parameters of §7, as `scatter:` properties or blank nodes. Each protection restriction is a node with a restriction, a level and an expiry.

```turtle
# graph <{base}/graph/metadata>
<https://www.wikidata.org/wiki/Special:Redirect/logid/{id}>
    a as:Delete, prov:Activity ;
    as:actor <https://www.wikidata.org/wiki/Special:Redirect/user/{uid}> ;
    as:object <https://www.wikidata.org/wiki/Special:EntityData/Q123> ;
    as:published "…"^^xsd:dateTime ;
    scatter:logType "delete" ; scatter:logAction "delete" ;
    scatter:comment "…" .
```

**The correction to [0001](0001-revision-metadata-rdf.md) §6:** merges are removed from its list of log events. A Wikibase merge is represented by its revisions and by the redirect ([0002](0002-source-graphs-and-mass-ingest.md) §8.2).

### 9. What reads log events

- **The activity projection** ([0010](0010-site-ui.md) §13) indexes events from both log graphs and the projected local events.
  - An entity's history shows upstream log events keyed to any member of its cluster, and local events keyed to the entity.
  - Recent changes shows local events only. Upstream log events stay out of it, as mirror syncs do.
- **`list=logevents`** serves the same events. MediaWiki's type and action strings are kept, and the new types in §6.1 are added. A provider filter defaults to local events. The API details are in [0012](0012-api-requirements.md).
- **A deleted entity's page** can still say what happened, for example "Deleted on Wikidata on {date} by {admin}: {reason}". The event is in the provider log, which `cascade` does not touch.

## Consequences

- **Deletions, protections and revision hiding on Wikidata become visible on the instance,** with who, when and why, as far as Wikidata makes them public.
- **The mirror follows upstream hiding.** Revision deletion now reaches backfilled data, and retained entities no longer keep what upstream hid.
- **Provider logs grow without compaction.** They grow with the provider's log volume for the mirrored types, not with the number of entities. The backfill audit should measure Wikidata's volume for the default types before a full backfill is run.
- **Names stay out of permanent storage.** Upstream rename events are stored without names, so the provider log never becomes an archive of past usernames. Readers who want the details follow the link upstream.
- **One model covers local and upstream events,** so the UI, `list=logevents` and the metadata graph all read the same projection.
- **Reconciliation depends on dumps.** Outright suppression upstream is noticed only at the next logging dump. Until then, a suppressed event stays on the instance.
- **The local log becomes the home of jobs,** so job pages ([0010](0010-site-ui.md) §9) read their counts from the job's finish record.
