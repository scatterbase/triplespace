# 0000. Triplespace

- **Amended by:** [0002 — Source graphs and mass ingest](0002-source-graphs-and-mass-ingest.md), [0006 — Log integrity and erasure](0006-log-integrity-and-erasure.md), [0013 — Postgres as the log store and serving model](0013-postgres-storage.md), [0015 — Record format and partition registry](0015-record-format-and-partition-registry.md), [0022 — Federation: verified data sync and ActivityPub](0022-federation.md) (§3 realises §3 between instances: foreign entities verified against their home instance)
- **Author:** James Hare / Claude Opus

## Context

Wikibase stores each entity as a MediaWiki page. Every edit is a new page revision holding a full JSON serialization of the entity. Query-oriented views, such as the SPARQL triplestore and search indexes, are filled in afterward by separate update pipelines. This design inherits MediaWiki's strengths (history, attribution, a mature editing UI), but it fits two workloads badly:

1. **Bulk ingest.** Loading a large external dataset means pushing every change through the MediaWiki edit pipeline, one revision at a time.
2. **Talking about things that live elsewhere.** To make statements about a Wikidata item or an OpenAlex work, a Wikibase first needs a local item to stand in for it. For sources the size of OpenAlex, that means mass-reifying tens of millions of pointers as local items whose only job is to point somewhere else.

## Decision

We will build **Triplespace**, a reimplementation of Wikibase in Rust organized around an append-only log.

### 1. The log is the source of truth

Every change is appended to the log as a record. Nothing is updated in place. Current entity state, RDF output, and query indexes are all projections derived from the log.

### 2. High-speed ingest is a primary workload

Bulk loading is a first-class path, not a long series of individual edits. Ingesting a dataset means appending to the log at whatever rate the storage can sustain.

### 3. Foreign entities sit alongside local ones

A foreign entity can be referenced directly, without first being reified as a local item. Identifiers distinguish the two:

- **Local entities** keep Wikibase's single-letter prefixes (`Q`, `P`, and so on).
- **Foreign entities** use a three-letter prefix: a two-letter provider code followed by a one-letter type code.

| Provider | Code | Types |
|---|---|---|
| Wikidata | `WD` | `WDQ` Item, `WDP` Property `WDL` Lexeme `WDM` Commons MediaInfo |
| Librarybase | `LB` | `LBQ` Item, `LBP` Property |
| OpenAlex | `OA` | `OAW` Work, `OAA` Author, `OAS` Source, `OAI` Institution, `OAT` Topic, `OAK` Keyword, `OAP` Publisher, `OAF` Funder, `OAG` Award |

### 4. Hardest realistic case first

The design target is Wikidata-scale data and query load. Smaller Wikibase deployments should follow as corollaries and should not need separate design work.

## Consequences

- **History comes built in.** Every past state can be recovered by replaying the log, and any projection can be dropped and rebuilt.
- **Removing data is hard.** An append-only log does not naturally support revision deletion, suppression, or legal takedowns. Triplespace needs an explicit mechanism for these.
- **Most of MediaWiki has to be replaced or delegated.** Triplespace does not come with MediaWiki's editing UI, accounts, permissions, or watchlists. Each of these has to be rebuilt or left to a downstream MediaWiki.
- **Foreign references can drift.** Upstream sources merge, redirect, and delete entities (Wikidata merges and OpenAlex merges, for example). Foreign IDs can go stale, and Triplespace has to reconcile them.
