# Review: 04 Entities and identifiers, 05 Providers and ingest

Scope: chapters 04 and 05 in full, with 00, 01 §1–2, §6–7, 03 §2, §4, §6–7, 08 §2, §4 and `docs/registry/providers.toml`, `keyed-types.toml`, `README.md` read where the two chapters depend on them. Findings are ordered by how much they threaten the first milestone (a Wikidata-scale mirror plus local data plus OpenAlex, on Postgres, with the resolved view, clusters, the Action/REST API and the site UI), not by chapter order.

## Overall judgement

The identity model is sound and unusually well thought through: the separation of "who minted" from "who asserts", the one-to-one cluster rule with held conflicts (which does make the result arrival-order independent), the keyed types with surrogate log keys, the `adopt` operation and its sequence floors, and the entity-source mechanism are all things I would build as written. The ID grammar and the registry are stable commitments and the chapter is honest about which ones are permanent. The ingest side has the right shape too: one change-set type, three entry points, bootstrap mode that defers projections, deterministic statement IDs for sources that have none, and `snapshot` sweeps guarded by a threshold.

Where it will hurt is at the seams the chapters hand to each other and do not close. Three of those seams sit directly on the core use case. First, the resolved view is specified as *stored* JSON with canonical IDs rewritten in, which makes every cluster change a write fan-out over `entity_ref` and makes a tenant's overlay grow to the size of the mirror slice that references anything the tenant has linked; the "shared view + tenant overlay" model is right, but the rewrite-on-write decision undermines it. Second, the only bulk path is bootstrap into an *empty* partition, while the documented incremental path (`linked` → `all`, re-syncs, a second dump) is the serialized-append path with per-record projections; there is no bulk path for a live Wikidata-sized partition, and that is the path the first milestone will actually walk. Third, every non-Wikibase provider (OpenAlex, GDELT, OSM) maps onto "local properties by role", but mirror graphs are instance partitions and roles and local properties are tenant data, so the shared OpenAlex mirror cannot be written as specified on an instance with more than one tenant. Below those are a cluster of underspecified cross-partition mechanisms (retention fan-out, who writes `cascade` retractions, surrogate minting and erasure across tenants, tier-2 link scope) that a programmer would have to decide alone and that are permanent once records exist. The chapters are also carrying two "Not yet"s that are not optional for the milestone: what `view.term` holds under a full mirror, and shallow-mirror eviction. I would resolve the first before any mirror projection code exists.

### F-04-1. Canonical-ID rewriting is done on write, so a cluster change is a fan-out over `entity_ref` and the tenant overlay grows to the referencing slice of the mirror

**Chapter §:** 04 §4.4, §4.9; 03 §4.2, §4.3, §6.2, §7.
**Severity:** blocker for the core use case.

**What the text says.** "The resolved view rewrites subjects and entity values to the canonical ID" (04 §4.4); "the projection computes the resolved canonical JSON whenever any contributing record changes" and materializes it when it differs from the source (03 §4.2); `entity_ref` "is required: a change of cluster membership must find every referrer" (03 §4.3); fan-out "to other entities, meaning referrers re-resolved by a cluster change" runs under a 1,000-row / 250 ms budget and the rest is queued (03 §6.2); a tenant "that has local assertions about the entity, a cluster link touching it, or a correction on it gets its own `(tenant, id)` row" (03 §7).

**Why it is a problem.** Put those together for the first realistic tenant action: an editor writes `same-as` between a local `Q12` and `WDQ5` (human), or `convert`s any widely cited Wikidata item. The canonical ID of the cluster is now the local member. Every mirrored entity whose statements have `WDQ5` as a value now differs from its source payload once rewritten, so each gets a `materialized` row *in the tenant overlay*, with its full canonical JSON stored (for `WDQ5` that is on the order of 10^7 entities, each tens of KB). The overlay stops being an overlay and becomes a tenant-private copy of a large slice of the mirror, re-materialized on every one of those entities' upstream syncs for as long as the link exists; the delta projection emits a delta per referrer too. The "shared view + tenant overlay" model does not survive a second tenant doing anything ordinary with clusters. It is also what forces `entity_ref` to exist at 10^9 rows: the table is required only because the rewrite is done on write.

The same design makes resolution order matter in a second way: provider order is tenant configuration (04 §4.4, §4.10), so a tenant whose `reconcile` order differs from the instance default has a different canonical member for every shared cluster, and therefore an overlay row for every clustered entity *and* for everything that references one, before it has edited anything.

**Suggestion.** Make canonical-ID rewriting a read-time transform. The cluster map is small by construction (04 §4.2: at most one member per namespace, so the number of non-canonical IDs is bounded by the number of links, not by the number of entities); keep it in L0/L1 per tenant and apply it when a resolved body is served, when RDF is emitted, and when the search document is built. Then: a cluster change touches the cluster's members and nothing else; `resolved_kind = 'source'` survives for every mirrored entity that merely references a clustered one; the overlay holds only entities the tenant has asserted something *about*; the RDF update stream emits the member `owl:sameAs` triples and the referrers' `wdt:` triples through the quad store's own rewrite or a dump-time pass rather than 10^7 deltas; and `entity_ref` becomes what "Links here" needs rather than what correctness needs, which lets the Wikidata-scale profile serve "Links here" from the query service and drop the table. Statement-GUID rewriting (04 §4.9) is already a read-time rule and shows the shape. Decide this before the `entity` projection is written; it changes `view.entity`, `view.rdf_delta` and the cache keys.

### F-04-2. There is no bulk path into a live partition; the incremental route to a full Wikidata mirror is the serialized-append path

**Chapter §:** 05 §3.7, §3.8, §5.9, §3.4 (re-import); 03 §2.1, §6.2.
**Severity:** blocker for the core use case.

**What the text says.** Bootstrap mode creates "the target child tables ... with the primary key only" and builds every index and `view` table after the load (05 §3.8). "Appends to one partition are serialized by that lock. This is the correct behaviour for the local partition ... and irrelevant for bulk ingest, which uses bootstrap mode" (03 §2.1). "Moving a type from `linked` to `all` starts a dump sync, which continues from the shallow records" (05 §5.9). "A re-import appends only the entities that changed" (05 §3.4). Bulk jobs "apply projections in batches behind the append, and report lag" (03 §6.2).

**Why it is a problem.** The milestone will not start from an empty `mirror/wikidata`: the design's own recommended path is shallow first, then `all`; and after the first full load every weekly dump re-sync is a re-import of 5–15 million changed entities into a partition that already has its `(key, offset)` index, its Merkle nodes and its projections. None of that is bootstrap mode, and the chapter gives it no other mode. As written, every such record goes through the per-partition row lock one appending transaction at a time, with leaf hashing, header column denormalization and projections 1–5 applied "behind the append" by a single worker in append order. That is the write path designed for an editor, not for ten million records a week, and it is also the path 05 §2.6's `changes` summary and `delta` computation lands on (read previous body, diff, write). Nothing in the text says what batch size an append transaction may hold, whether a bulk job may take the partition lock for a block of N offsets, or whether projections for a mirror partition may be rebuilt per segment rather than per record.

**Suggestion.** Specify a third mode between interactive and bootstrap, "bulk append", for a live partition: a job takes the partition lock once per block of offsets (05 §3.8's `ops.bootstrap_block` already has the shape), `COPY`s the block, folds the block's leaves into the tree, and the projection worker applies steps 2–4 per block, not per record, with `ops.projection_state` advancing per block. State explicitly that `put` skipping (version cursor) is evaluated in bulk against `view.entity_source` before the block is written, so a re-sync's unchanged 100 million entities never reach the lock. Say which of these also applies to a local bulk job (`stream` jobs "apply each entity independently", 05 §3.5: one transaction each, or one per block?). And make the version-cursor read tolerate projection lag by comparing against the partition's newest record for the key when `entity_source` is behind, or accept duplicate `put`s under `latest` and say so.

### F-04-3. Non-Wikibase adapters map onto "local properties by role", but mirror graphs are instance partitions and roles and local properties belong to tenants

**Chapter §:** 04 §4.6; 05 §3.4, §8.4, §8.8, §8.11–8.12; 08 §2.1, §2.5 (`role` is tenant `config`).
**Severity:** blocker for the core use case (OpenAlex is in the milestone).

**What the text says.** The OpenAlex adapter maps each field "onto a Wikidata property, where one fits; otherwise onto a local property. ... Local targets are named by role. ... Each instance binds the roles to its own entities, and the adapter can create them on first import" (04 §4.6). GDELT documents and events carry statements "by role" (`document-url`, `theme`, `event-actor`, …; 05 §8.11–8.12) and OSM tags take `osm-tag`, `osm-tag-text`, `osm-key` (05 §8.8). `mirror/{provider}` is an instance partition (08 §2.1); `role` is a tenant `config` kind (08 §2.5); a local `P12` "means a different entity on each tenant" (04 §2.3).

**Why it is a problem.** An instance has no entities and no role bindings; tenants do. A record in `mirror/openalex` with predicate `P12` is meaningless to a second tenant and wrong on the first the moment the primary tenant changes hands or a tenant creates its own `P12`. "The adapter can create them on first import" cannot be done by an instance job: `create` writes to a tenant's `local` partition and mints from that tenant's `log.property_id`. So the OpenAlex, GDELT and OSM adapters, as specified, can only be written against a single-tenant instance, which is exactly the case the architecture says it does not special-case. OpenAlex is the milestone's third source, and a large part of its value (authorships, topics, keyword scores, open-access status, citation counts) has no Wikidata property.

**Suggestion.** Decide the scope of adapter-created vocabulary, and the options are few: (a) every mapped target must be a registry-provider entity (`WDP…`), and fields with no Wikidata property are dropped or carried as `string` under a generic property, which loses data; (b) reintroduce a property type for providers that need one (`OAP`), minted by the adapter under deterministic IDs with the mapping versioned with the adapter, as 04 §4.6 already says it is; or (c) bind the adapter's roles to the *primary tenant's* properties and write the mirror records with that tenant's provider-form IDs (`LBP12`), which requires the primary tenant to be a provider and makes the mirror unreadable to tenants that do not list it. (b) is the one that keeps the mirror shared and the adapter instance-scoped, and it is a registry change plus one `[[provider.type]]` row. Whatever is chosen, the same decision covers the `role` lookup: an instance job must not read a tenant's `role` records, so adapters need either instance-scope role bindings (a new config scope) or none.

### F-04-4. Tier-2 links are instance-wide by one chapter and tenant-configured by another, and the cluster tables have no tenant column

**Chapter §:** 04 §4.3, §4.10; 03 §4.4, §4.1, §7; 08 §4.1.
**Severity:** design debt that will be expensive later (it decides the key of three tables).

**What the text says.** Tier 2 is "a mirrored statement of a configured link property", "On for configured properties" (04 §4.3), and "the link properties for each provider" are the *tenant's* `reconcile` settings (04 §4.10: "the first, second and fourth are the tenant's"). But "on a farm, tier-2 and tier-3 links come from shared graphs and are instance-wide" (04 §4.3; 03 §7). A provider tenant's `same-as` records "are tier-1 links for Librarybase and tier-2 links for everyone else" (08 §4.1), yet they come from a tenant partition only the tenants that list `LB` read. Tier-3 infers from "two entities from different namespaces" sharing a value, one of which may be local, yet is "instance-wide". `view.cluster_member` has `entity_id text NOT NULL UNIQUE` and no `tenant` column, and the tenant-column rule of 03 §4.1 lists `entity` and its dependents but not `cluster`, `cluster_member`, `link` or `different_from`.

**Why it is a problem.** These cannot all be implemented. If link properties are per tenant, the shared clusters (`tenant = ''`) cannot be computed. If clusters are instance-wide, a tenant's tier-1 `same-as` on `WDQ42` cannot be stored, because `WDQ42` is already a member of the shared cluster and `entity_id` is unique. A programmer will pick one and the choice is baked into the primary keys of `cluster`, `cluster_member` and `link`, and into the `canonical_id` of every shared `view.entity` row.

**Suggestion.** Decide: tier-2 link properties and provider order among *registry* providers are instance configuration (the instance `reconcile` record, as inference properties already are); a tenant's `reconcile` may only add link properties for providers that are tenants (whose graphs are read per tenant anyway) and may not reorder shared providers. Then the shared cluster set is well defined, and the overlay is exactly: tier-1 links, `different-from`, and links through provider-tenant graphs. Give `cluster`, `cluster_member`, `link` and `different_from` the `tenant` column with the same `''`-then-tenant lookup as `entity`, and change `cluster_member.entity_id UNIQUE` to `UNIQUE (tenant, entity_id)`. While there, fix 04 §4.4's "a cluster's members share a type, so the order is always defined": the chapter's own example is a cluster of an item and a Domain, so `order_by_type` needs a rule for mixed clusters (key on the canonical candidate's Wikibase type, or drop `order_by_type`).

### F-04-5. Retention, `cascade` and tombstones cross the instance/tenant boundary in ways no section specifies

**Chapter §:** 05 §2.1, §2.2, §2.3, §5.3, §5.5; 01 §6; 08 §8.
**Severity:** design debt, expensive later, and dangerous in one case.

**What the text says.** A tombstone in the mirror graph applies "the entity's retention policy"; "each tenant sets a default ... and editors can override it for individual entities"; under `retain` "its last state is materialized into the local graph in the same log record as the tombstone"; under `cascade` local-graph assertions are "Retracted" (05 §2.1); `retain` "exempts the entity from compaction" (05 §2.2). Shallow mirroring: "Validation at save time checks only the ID's grammar and its provider" (05 §5.3) and a fetch of "a missing entity [becomes] a `tombstone`" (05 §5.5).

**Why it is a problem.**
- A tombstone is one record in a shared instance partition; retention is a per-tenant, per-entity choice. "The same log record" cannot hold a materialization into N tenant `local` partitions. Who writes the N records, under which attestation (an instance act under 08 §8.3? the tenant's sync subsidiary?), and in which order relative to compaction, is unstated.
- `cascade` "retracts" a tenant's local assertions. The log is append-only, so that is a `remove` record in the tenant's `local` partition written by the instance on an upstream signal. That is an instance act in 08 §8's sense and needs an authority record and a visible log event; nothing says so.
- Compaction is a partition-level action; `retain` is a tenant-level exemption. The exemption has to be the union over every tenant's policy rows, which means the compactor reads every tenant's overlay before deleting, and the mirror can never compact an entity any tenant on the farm has retained. That is probably right, but it should be said, and it means the `(key, offset)` compaction query in 01 §6 is not the whole story.
- The dangerous case: an editor saves a statement pointing at `WDQ9999999999` (a typo), validation passes on grammar alone, the shallow fetch finds nothing and writes a `tombstone`, the tombstone applies the tenant's default policy, and under `cascade` the editor's statement is retracted by the instance. A never-present entity should not be tombstoned at all, and a typo should not trigger retention machinery.

**Suggestion.** (1) Make the mirror tombstone carry nothing about retention; have the *entity* projection, per tenant, apply the tenant's policy when it sees a tombstone for an entity the tenant has an overlay for, writing the materialization or the retraction as a tenant-partition record attested by the instance with an authority record (08 §8.4) and a `retention/apply` log event. (2) Define the compaction exemption as "any tenant's `retain` row", and say the compactor reads it. (3) A fetch miss for an entity with no prior `entity_source` row writes no record; it marks the `ops.entity_fetch` row failed and the referring statement's value renders as unresolved. (4) Consider making `cascade` never the default: `orphan` keeps the editor's work recoverable and costs nothing.

### F-04-6. What `view.term` holds under a full mirror is "Not yet", and it is the largest open cost in the milestone

**Chapter §:** 05 §5.8; 03 §4.3, §4.1 (term is an `entity` dependent with a tenant column); 00 §2.8.
**Severity:** blocker for the core use case (it is the wb_terms problem).

**What the text says.** "A mirrored entity's terms populate `view.term` in `entities.term_languages` only ... A shallow mirror holds thousands or millions of entities, not 117 million, so the rows are affordable. Not yet: what a full mirror (`all`) writes to `view.term` is an open question" (05 §5.8). `term` "serves label lookups, which every entity page does in bulk" (03 §4.3). At Wikidata scale `term_prefix` is absent and OpenSearch serves suggest (00 §2.8).

**Why it is a problem.** Wikidata's term store is on the order of 10^9 rows, and Wikibase's own history with `wb_terms` is the cautionary tale this project exists to avoid. Leaving the rule open means the term projection will be written for the shallow case and then discovered to be unaffordable at the first full load, after the table's shape, the label-lookup API and the search projection all depend on it. The setting that bounds it is per tenant (`entities.term_languages` is a `site` setting) while the rows it bounds are shared (`tenant = ''`), so even the shallow rule is underspecified: whose language list governs the shared row?

**Suggestion.** Decide now, and the decision that fits the rest of the design is: `view.term` holds rows for local entities, for entities in any tenant overlay, and for mirrored entities only in the *instance's* `term_languages` (an instance setting; tenants may only narrow their own display); every other label lookup reads the record body at `entity_source.offset` through the L1 label cache that 05 §5.6 already defines for unmirrored entities. The label cache and the term table then serve the same API, and the search index, not `term`, is the path for `wbsearchentities` at scale, as 00 §2.8 already says. State the size budget: rows ≈ mirrored entities × |instance languages| × term kinds.

### F-04-7. Keyed-type surrogates are minted through one instance partition and erased instance-wide

**Chapter §:** 04 §3.4; 03 §2.3, §6.1; 01 §5.
**Severity:** design debt, with one correctness hole.

**What the text says.** "The instance mints the surrogates in sequence, one per keyed type, the first time a key is written to"; the mapping record is "in the instance `log` ... appended before the first record under the surrogate"; "surrogates are instance-wide"; "Erasing a Domain by key erases the mapping record along with everything else keyed to the surrogate" (04 §3.4). "Appends to one partition are serialized by that lock" (03 §2.1).

**Why it is a problem.**
- Every first write of a new Domain, Keyword or Notation on any tenant, and every key-mapped mirror `put` for a new key (internetdomains, OSM wiki, OpenAlex keywords, GDELT `source-domain`), appends one record to the single instance `log`. A key-mapped bootstrap of a few million keys becomes a few million serialized appends to a `logged`, `full` partition that also holds OAuth events and job records, and it cannot use bootstrap mode because that partition is live.
- Two writers meeting a new key at once (an editor and a bulk job, or two tenants) race on "the first time a key is written". The text gives no lock and no unique constraint on the *log* side; `view.keyed_surrogate`'s `UNIQUE (keyed_type, key)` is a projection and arrives after the append. Two mapping records for one key is permanent.
- The surrogate is shared, so one tenant's privacy erasure of `domain:johnsmith.example` erases the mapping every other tenant's records, and the shared mirror's key-mapped records, depend on; the resolution projection then "fails rather than guess" for all of them. A tenant can blank a key on the whole farm.

**Suggestion.** Allocate surrogates from the sequence under an advisory lock keyed by `(keyed_type, key)` taken in the appending transaction, and write the mapping record in the same transaction as the first record that uses it; say that bulk jobs reserve surrogate blocks the way they reserve ID blocks. Decide erasure scope explicitly: either the mapping is erased only when no live record in any partition is keyed to the surrogate (which makes a single tenant's erasure a per-tenant erasure of its own records, and the key survives), or the mapping is per partition. The first is consistent with 04 §3.3 ("Two different keys are two different names"; a key is not personal data on its own, its association with a tenant's assertions is).

### F-04-8. `snapshot` mode cannot tell "unchanged" from "absent", because unchanged entities append nothing

**Chapter §:** 05 §3.2 (`put`), §3.4 (import modes).
**Severity:** design debt (a correctness trap in the re-sync path).

**What the text says.** A `put` "is skipped when the upstream version is not newer or the content hash is unchanged" (05 §3.2). In `snapshot` mode, "Entities the job did not see are tombstoned. This sweep runs only after the job completes successfully, and it aborts if the tombstone count exceeds a configured threshold" (05 §3.4).

**Why it is a problem.** Skipped entities leave no trace in the log, and `view.entity_source.job_id` is updated only by a projection of an appended record. So the sweep has nothing to diff against: either it tombstones every unchanged entity (the threshold catches that, and the sync never completes), or the ingester keeps a "seen" set per job somewhere the text does not name. At 117 million keys the seen set is itself a design decision (a Postgres unlogged table, a bitmap keyed by `entity_source` row, an on-disk hash set in the ingester), and it has to survive a job restart since 05 §8.13 makes a slot the unit of resumption for GDELT but says nothing for dumps.

**Suggestion.** Add `ops.sync_seen (job_id, entity_id)` or a `seen_job` column on `view.entity_source` written by the ingester directly (it is `ops`/cursor state, not a projection of the log, like `ops.entity_fetch`), and define the sweep as `entity_source` rows for the graph whose `seen_job` is older than the job. State that the sweep is itself resumable and that a job that did not complete leaves `seen_job` as is.

### F-04-9. Hosting a provider as a tenant is specified from the tenant side only; the registry row still describes a remote mirror

**Chapter §:** 05 §8.3; 08 §4.1, §4.4; `providers.toml` (`LB`).
**Severity:** design debt (it is the owner's own first case).

**What the text says.** A tenant becomes a provider by taking a code; "there is no sync job and no mirror partition, because the tenant's `local` partition is the source" (08 §4.1). The registry's `LB` row carries `adapter = "scatter-adapter-wikidata"`, `api = "https://librarybase.org/w/api.php"` and `article_path`, and 05 §8.3 describes `LB` as "any MediaWiki+Wikibase mirrored through `scatter-adapter-wikidata`". A provider tenant that moves away is "switched from the first to the second with no change in what its readers see" (08 §4.4).

**Why it is a problem.** Nothing says how an instance knows which of the two `LB` is: a remote wiki to sync, or a tenant on this instance. The registry cannot say, since it is shared by every instance and Librarybase is remote to most of them. If an instance mirrored `librarybase.org` and later adopts Librarybase as a tenant (the likely sequence for a staging instance), `mirror/librarybase` holds `LBQ6` records and the tenant's `local` holds `Q6`, both readable as `LBQ6` by other tenants, with no rule for which wins or how the mirror partition is retired, and the version cursor rows in `view.entity_source` for graph `mirror/librarybase` now shadow a graph that no longer syncs.

**Suggestion.** Make it instance configuration: the tenant's `tenant` record, or the instance `providers` config, states `hosted = true` for a provider code, and the instance refuses to run a sync job for a hosted provider and refuses to host a tenant under a code that has a live mirror partition until that partition is frozen (as 05 §6.8 freezes `source/{name}` on promotion). Describe the freeze: the mirror partition is kept, its `entity_source` rows are dropped, and resolution reads the tenant's `local` instead. Say it in 05 §8.3, since that is where someone building Librarybase will look.

### F-04-10. The edit-conflict check for local assertions about foreign entities spans the mirror partition

**Chapter §:** 01 §7; 05 §2.5, §5.10.
**Severity:** minor, but it bites bots on the milestone's main workload.

**What the text says.** "For a write to a foreign entity, `baserevid` is decoded to a partition and offset, and the check runs against the newest record for the key across the source partitions, not only the local one" (01 §7).

**Why it is a problem.** A local `add` on `WDQ42` is a local-graph record; a Wikidata `put` for `WDQ42` landing between the client's read and its save changes nothing the client's edit depends on, yet the save fails with `editconflict`. Wikidata's edit stream runs at several edits per second across the whole graph, and on hot entities (countries, `human`, big journals) a WikidataIntegrator run that reads, computes and writes will retry forever. A base is also impossible to supply meaningfully for a mirrored state that compaction may have replaced.

**Suggestion.** The base for a local-graph operation is the newest *local* record for the key; a mirror record never conflicts with a local assertion. Keep the cross-partition check only for operations whose semantics depend on the mirrored state (`override` of a specific upstream statement, which already names the statement ID and can be checked for existence instead).

### F-04-11. Deterministic statement IDs for sources without them are keyed on too little

**Chapter §:** 05 §3.4, §8.4.
**Severity:** minor.

**What the text says.** OpenAlex statement IDs "are derived from the entity, property and value, as a name-based UUID for example, so that they stay stable across re-imports."

**Why it is a problem.** OpenAlex keywords become one statement per keyword with the score as a qualifier (04 §3.7); authorships carry position and institution qualifiers; topics carry scores. Two statements with the same main snak and different qualifiers (the same institution twice with different roles, the same funder with two award IDs) collide on `(entity, property, value)` and the second overwrites the first in the mirrored JSON. Including qualifiers makes every score change a new statement ID, which detaches local overrides exactly as the text fears; excluding them loses data.

**Suggestion.** Hash the main snak and the *identifying* qualifiers (adapter-declared per property: position, institution, award ID), never score-like ones. The adapter mapping already has a per-field table; add a column. Say it in 05 §3.4 so GDELT and OSM follow the same rule.

### F-04-12. Registry commitments: two contradictions and one unstated permanence

**Chapter §:** `docs/registry/README.md` Rules; 05 §8.1; 04 §2.2; `providers.toml`.
**Severity:** minor, but permanent once records exist.

**What the text says.** "Nothing is allocated at runtime" and, four lines later, an instance's config "may add providers" (README). The `XD` registry row has `actor_model = "provider-only"`; 05 §8.1's table says `individual` (the registry is authoritative, so the chapter's attribution of internetdomains edits to individual accounts is wrong, or the registry is). A grammar "is added by ADR, as a value the registry accepts" but the normalizers and grammars are "a closed set" in code (04 §3.8).

**Why it is a problem.** A provider added at runtime takes a code and a number that end up in record keys and in `revid = number << 40 | n` inside hashed headers; if two instances do that independently, the registry's reason for existing ("IDs and revision IDs computed from them are shared between instances") is gone. The attribution flag decides which actor records a sync writes, and those are permanent. The slug and the per-type `iri` template are also permanent commitments the README does not list: the slug is in every partition name and checkpoint origin line, and the IRI template is the matching key for entity-source promotion and cross-tenant rewriting (05 §6.7–6.8), so changing Wikidata's template would silently unbind every tenant source that matched it.
