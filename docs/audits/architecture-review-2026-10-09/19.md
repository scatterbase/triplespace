# Review: chapters 19 (Site UI), 20 (Web tier), 21 (Special pages), 22 (Crates and stack), 23 (Configuration and registry)

## Overall judgement

As a description of a finished product these five chapters are coherent and unusually disciplined: the site is an API client, the web tier holds no state and the API alone judges forwarded headers, every special page is a registry row with a backing, every setting has one home, and the crate map says where every line of code goes. The parts that are pure design, not scale, are sound and I would not reopen them: the statement UI and its prototyping path against live Wikidata (19 §4, §5.8) is the right first thing to build; the proxy-trust model and the deployment-boundary checklist (20 §5) are better than what MediaWiki has; the special-page registry with `served`/`deferred`/`declined` and report backings (21 §1–2) is the right shape; the licensing, toolchain and testing choices in 22 §3–4 are conservative and correct. Where I push back is on what these chapters cost the first milestone and what they do to a Wikidata-scale mirror once a second tenant exists.

Three things worry me most. First, the crate map and build order in 22 are not yet a build plan: the layer rule is already broken by the table itself, the first milestone cannot compile `triplespace-projections` as "every `view` projection" or `triplespace-server` as "any crate", and adding a projection later means replaying the whole mirror log, which the chapters state but never price. Second, the web tier's decision to compose every page from N public-API calls, each through the full middleware and each contributing cache tags, is correct in principle and expensive in practice; nothing in 20 or 19 bounds N, and the provenance response the entity page depends on carries an O(referrers) count. Third, 23 lets a tenant set resolution policy (`reconcile` order, `providers`, `sitelink-policy`, `entities.term_languages`) while 03 §7 computes the shared view once and overlays only where a tenant's own partitions change the result; a tenant whose policy differs from the shared default is an overlay of every entity with more than one source, which is the shared-view model failing on the second tenant. Below, 22 and 23 get the hardest findings; 19, 20 and 21 mostly need bounds and named backings rather than redesign.

## 22. Crates and stack

### F-19-1. The crate table violates its own layer rule, so CI's dependency check fails on day one or the rule is fiction

**Chapter §:** 22 §1.1, §1.2 rule 1, §2.1. **Severity:** design debt that will be expensive later (it is also a day-one blocker for `cargo xtask deps` as specified).

**What it says.** "Dependencies point only downward. No crate below the surfaces layer names Triplespace... CI checks the dependency graph against the table in §2." Layer 1 "Knows nothing about Wikibase."

**Why it is a problem.** The table itself does not satisfy this:

- `scatter-extract` sits in the Substrate block and depends on `scatter-wikibase-model` (layer 2). That is an upward edge. §2.3 says only "neither depends on Triplespace" and never assigns it a layer.
- `scatter-pages` (substrate) holds "the `terms` operation on File page change sets ([0065])", "the `Scribunto` model entry and its syntax-check hook", and the `page-repo` config kind. Terms on MediaInfo are Wikibase; Scribunto is Triplespace's Lua host.
- `scatter-log` (substrate) holds the five-part `mirrored-page` payload, the `derivation` payload, the `tenancy`, `template` and `provider-readers` config kinds, `fragments.toml`, and the instance attestation. These are Triplespace features; §2.1's own `scatter-threads` row argues the opposite rule ("a payload type is a value the log stores, as `scatter-pages` already shows"), so the chapter has two placement rules for payload types and follows neither consistently.
- `scatter-wikibase-model` depends on `scatter-pages`, which depends on `scatter-css`; the Wikibase data model now transitively links a CSS parser.

None of this breaks compilation; it breaks the thing the rule exists for, which is that Scatterbase can take layer 1 without Wikibase and the WCD can take `scatter-extract` without a page model. If CI really checks the table, the check fails; if the table is what CI checks against, the rule has already been amended by accretion.

**Suggestion.** Put `scatter-extract` in layer 2 (it is a Wikibase-shaped extractor; that is fine). Decide one rule for payload types: a `scatter:v0/*` payload type lives in the lowest crate whose *product* needs it, and Triplespace-only payloads (`mirrored-page`, `derivation`, `upload`, `expunge`) live in a small `scatter-payloads` or in the `triplespace-*` crate that writes them, with `scatter-log` generic over the payload as its row already claims. Strip the `page-repo`, Scribunto and MediaInfo rows out of `scatter-pages` into the crates that own those features. Then run the dependency check against the corrected table before any more rows are added.

### F-19-2. The first milestone cannot compile the crates as described, and adding a projection later costs a full replay of the mirror

**Chapter §:** 22 §2.1 (`triplespace-projections`, `triplespace-api-action`, `triplespace-server` rows), §3.1 build order; 03 §6.1 as read from here. **Severity:** blocker for the incremental path as written.

**What it says.** `triplespace-projections` holds "Every `view` projection, in the order of [0013] §7"; `triplespace-api-action`'s dependencies are "Any lower crate"; `triplespace-server` "Any crate". Build step 6 says "`triplespace-server`. This is the first point at which the statement UI can be pointed at Triplespace." And 03 §6.1: "`ops.projection_state (projection, partition, applied_offset)`... A rebuild truncates the projection's tables and replays from offset 0."

**Why it is a problem.** Two things. (a) Nothing in 22 says what a *subset* of the crate map is. Rule 6 forbids Cargo features from switching product behaviour, so step 6's server cannot be "the server without accounts, render, search, files" by feature; it has to be a server whose crates simply do not exist yet, which means the `projections` crate at step 5 is "some projections", the write path's tower stack (§4.3: "auth → grants → rate limit → ACLs → filters → base offset → append → projections") has a `filters` layer with no filter crate, and the projection order of 03 §6.1 has holes. That is fine in practice, but the chapter should say so, because otherwise the first engineer either builds stubs for 30 projections or argues about whether the order table is normative. (b) The more expensive consequence: a projection that arrives in milestone 3 (constraints, reports, scopes, `entity_usage`) starts at `applied_offset = 0` on every partition, so bringing it up on an instance that already mirrors Wikidata means reading the whole mirror partition (hundreds of millions of records, terabytes once packed) to produce a few rows about local entities. 21 §2.3 already quietly makes the right exception for reports ("`projection` entries are a function of the `view` tables they read, and are rebuilt with them"), but 03 and 22 have no such category.

**Suggestion.** Add to 22 §3.1 a one-paragraph definition of milestone 1's crate set and projection set (registry, surrogates, actor, group/membership/acl/block, entity_source, cluster/link, entity+term+identifier+entity_ref, activity, job) and state that the projection order is a partial order over whatever projections are registered, with `ops.projection_state` rows only for those. Then make "derived-from-`view`" a projection class in 03 §6.1 / `scatter-projection`: a projection declares whether it replays from the log or rebuilds from named `view` tables, and a newly added view-derived projection is populated by a scan of those tables, never by a log replay. Reports, constraints, `site_stats`, scopes, tasks and schema reports are all in that class.

### F-19-3. Three store abstractions share one transaction and no transaction type; sync I/O inside futures on tokio is a trap

**Chapter §:** 22 §1.2 rule 2, §1.3 ("whose methods return `Send` futures"), §2.1 (`scatter-projection` "a transactional variant that applies inside the appending transaction"; `scatter-ingest` "the `IngestStore` trait... appending inside the unit of work"). **Severity:** design debt that will be expensive later.

**What it says.** `LogStore` (substrate, async signature, "its file backend does synchronous I/O inside those futures"), the projection `Backend` with a transactional variant (substrate, depends on `scatter-log` only), and `IngestStore` (ingest layer, implemented "over Postgres in the surfaces and in memory here for tests"). 03 §6.2 requires the append, ID allocation and projections 1–5 to commit together.

**Why it is a problem.** "Inside the appending transaction" is a Postgres fact expressed by two substrate traits that cannot name a `tokio_postgres::Transaction`. The programmer has to invent the unit-of-work type that crosses `scatter-log` → `scatter-projection` → `scatter-ingest` → `triplespace-db`, and the three traits as listed will not agree on it. Separately, "synchronous I/O inside those futures" is fine for a synchronous caller and wrong the moment the file backend is driven by tokio inside `triplespace-cli verify`, `export` or bundle import, where it blocks a worker thread; and `Send` futures from trait methods without a runtime dependency means RPITIT with explicit `+ Send` bounds (or `trait_variant`), which is a Rust-edition decision the chapter should make rather than leave to whoever writes `scatter-log` first.

**Suggestion.** Give `LogStore` an associated `Uow` (unit of work) type; `append`, `Backend::apply_in` and `IngestStore` all take `&mut Self::Uow`; the Postgres implementation's `Uow` wraps a transaction, the file backend's is a segment writer, the in-memory one a `Vec`. State that file-backend futures are always driven through `spawn_blocking` when a tokio runtime is present, and that `LogStore` uses RPITIT with `impl Future<Output = _> + Send`. Put the conformance suite's first case on "append + projection in one `Uow` is atomic".

### F-19-4. The build order front-loads cost the core use case does not need

**Chapter §:** 22 §3.1 steps 1–4; §2.1 `scatter-ingest` row. **Severity:** minor (sequencing), but it is the difference between a first milestone in months and one in quarters.

**What it says.** Step 1 includes `scatter-actors` whole (permissions, ACL enclosure, tenancy policy, farm evaluation, prerogatives, visibility sets), `scatter-mwlog`, `scatter-pages`, `scatter-wikitext`. Step 2 builds "`scatter-log` with the `segments` backend, `scatter-integrity`, then `scatter-log-postgres` and the `LogStore` conformance suite" before Postgres exists. `scatter-ingest` depends on `scatter-filter`, which depends on `scatter-threads`, `scatter-pages`, `scatter-normalize` and the `cel` interpreter.

**Why it is a problem.** The core use case is a Postgres-backed Wikidata mirror. The file backend is needed for export bundles, not for the mirror; building and conformance-testing it first is a quarter of work with no user. `scatter-actors` as listed is the whole permission model; step 6 needs only "resolve a credential to an actor with `read`/`edit`". Bulk ingest of a Wikidata dump compiling a CEL engine and the thread model because edit filters are a hard dependency of the ingester is a dependency, not a feature; filters apply to local jobs only (0030 §7).

**Suggestion.** Reorder: step 2 is `scatter-log` record/hash/segment *format* and `scatter-log-postgres`; the file `LogStore` backend and the shared conformance suite follow once bundles are needed (step 7 or 9). Split `scatter-actors`'s step-1 scope to actor keys, issuers and the pure permission check over memberships; the rest lands with moderation. Make per-operation filtering an injected trait (`FilterHook`) on `scatter-ingest` rather than a crate dependency, so the bulk path links no CEL.

### F-19-5. The wasm rule names nine crates and ignores their closure; no size budget exists

**Chapter §:** 22 §1.2 rule 7, §2.1 `scatter-wasm`; 19 §5.4. **Severity:** design debt.

**What it says.** Nine crates "must build for `wasm32-unknown-unknown`... CI builds that target." `scatter-wasm` is "Lazy-loaded by editors only, never needed for reading."

**Why it is a problem.** `scatter-wikibase-shape` pulls `scatter-wikibase-model` (PHP-`serialize` emulation, SHA, `oxrdf` via `scatter-providers`), `scatter-scope` (SPARQL compilation), `scatter-pages` (content-model registry, `comrak` + `ammonia` behind a feature), `scatter-normalize` (`idna`'s Unicode tables, and per §4.6 ICU4X case mapping and plural rules, which in wasm means `compiled_data` baked into the binary). None of these is on the list, all are built for wasm by transitivity, and the resulting editor bundle is plausibly 5–10 MB before `wasm-opt`. Two concrete traps: `getrandom` on `wasm32-unknown-unknown` needs the `js` feature wherever a GUID or salt is minted (statement IDs in the model crate), and `oxrdf`'s `oxsdatatypes` pulls time/decimal code that is fine but not free. "Lazy-loaded by editors" does not make a 10 MB download acceptable for someone fixing one label.

**Suggestion.** State the closure rule ("every transitive dependency of a rule-7 crate builds for wasm; CI builds `scatter-wasm`, not the nine crates separately") and a byte budget for `scatter-wasm` (say 2 MB gzipped, checked in CI). Split `scatter-wasm` into two lazily loaded modules, classifier+normalize and wikitext+markdown+css, since the term editor needs the first and the source editor the second. Move ICU4X case mapping out of `scatter-normalize`'s wasm path (the DOI case rule is ASCII folding) or feature-gate it.

### F-19-6. The deployment profile table says the opposite of its own rule, and defaults the Wikidata profile to an impossible query store

**Chapter §:** 22 §6; §4.1 principle 1. **Severity:** minor.

**What it says.** "they drop services, not tables", next to a row that drops the `term_prefix` index at Wikidata scale. "the query service... runs embedded in the binary by default, moving to QLever only when an instance chooses"; the Wikidata-scale row says "Quad store: Optional; QLever from dumps".

**Why it is a problem.** An index is schema; a profile that drops it needs a conditional migration and a `view` whose shape differs by profile, which the same paragraph forbids. And an embedded Oxigraph over RocksDB cannot hold a `full` Wikidata mirror (the order of 10^10 quads; load rates in the 10^5/s range at best, so days of load and terabytes of store inside the server's own process). "Optional" is right; "embedded by default" is only right for the small profile.

**Suggestion.** Keep the index everywhere and let the large profile simply not read it (or make `term_prefix` a partial index on local entities only, which is what 21 §2.2's "local by default" wants anyway). Add to §6: embedded backend is refused above a configured triple count, and `query.enabled` on the large profile requires `query.backend = remote`.

## 20. Web tier

Sound: §1 principles, §2.1 routing, §3.1 forms, §5 proxy trust and the boundary checklist. I would ship those as written. The findings are about what the chapter does not bound.

### F-19-7. A page is N API calls through the full middleware, and nothing bounds N

**Chapter §:** 20 §1.1 principle 3–4, §2.2; 19 §3.1, §4.2, §5.1 principle 5; 03 §10.2 ("The cache saves the API building and sending the body... not the round trip"); 18 (`GET /entity/{id}/provenance` "...and the backlink count"). **Severity:** design debt that will be expensive later; a blocker for `triplespace-web` as the HA mode at Wikidata scale.

**What it says.** "The renderer is an API client. It reaches the instance only through the public HTTP API, with the viewer's own credentials." "Both send the same requests through the same middleware." The UI needs, per 19 §4.2, "the labels of the entities and properties it links to", fetched per the prototyping path in batches of 50; the About panel wants "the revision count by origin", "the backlink count", "In 3 scopes", "2 proposals"; the frame wants the inbox count and watch state.

**Why it is a problem.** Count the calls for a logged-in reader opening a large item: `wbgetentities` for the entity; provenance; labels in batches of 50 for every linked entity, property, unit and qualifier value (a country or a chemical element links to hundreds; thirty calls is normal); `meta=userinfo`; `meta=tokens`; inbox count; scopes; proposals; history head for the identity line. Every one of those resolves the session (`private.session` or Valkey), checks a `read` rate counter (07 §6.2: "API requests of any kind, by key or session"), and evaluates visibility. Over HTTP/2 from `triplespace-web` that is 10–40 round trips per page; in embedded mode it is the same middleware cost without the network. The `read` class is 5,000 per minute per session or per IP, so a reading room behind one NAT address is rate-limited after a few hundred page views, by a limit designed for API clients. The backlink count is `COUNT(*)` over `entity_ref` for the target; for `WDQ5` on a full mirror that is tens of millions of rows per first render, and the L1 key (`resolved_version` of Q5) does not change when referrers change, so it is both slow to compute and never correctly invalidated.

**Suggestion.** Decide a per-page budget (for example: at most 4 API calls to first byte) and meet it with two routes in 18: a labels route that takes up to 1,000 IDs and returns only `labels` in the viewer's language chain (cacheable by language, not by viewer), and a `GET /entity/{id}/page` bundle that returns entity JSON, provenance and the identity-line facts together. Make the in-process transport exempt from rate counting and resolve the session once per page, passing the resolved principal to sub-requests (the rule "same middleware" can hold for everything except the counter and the session lookup). Replace the exact backlink count with a counter column maintained by the `entity_ref` projection, or with a bounded count ("10,000+") from `SELECT ... LIMIT 10001`.

### F-19-8. Cache-Tag union on composed pages has no cap and will exceed header limits

**Chapter §:** 20 §3.2 "a region carries the same ETag, Cache-Tag and redaction as its page"; 03 §10.3 "Its `Cache-Tag` is the union of theirs"; 03 §9.6 "a cache tag for each entity and page it drew on". **Severity:** design debt that will be expensive later.

**Why it is a problem.** The entity page of a large item draws labels from hundreds or thousands of entities; by the stated rule it carries a tag per label source. Tag headers are capped by every CDN and proxy that implements tag purging (single-digit KB to a few thousand tags) and by the proxy's own header-size limit. The page either fails to cache, is truncated silently (losing purges, which is the correctness property §9.6 exists for), or forces the web tier to invent a policy nobody wrote down. The same union makes a mirror sync that touches a million labels purge every page on the site.

**Suggestion.** Make the rule two-tiered in 03 §10.3 and repeat it in 20: a composed page carries exact tags for its subject(s) and for every page in its render manifest, and label-only dependencies are not tagged; label staleness is accepted up to a short `s-maxage`, which is what MediaWiki does with its label cache. Cap the tag list and record the cap as a stated limit.

### F-19-9. The web tier may share the instance's L1 Valkey, which gives it the credential to read sessions

**Chapter §:** 20 §1.1 principle 1, §5.3 line 12, §5.5; 22 §1.2 rule 10. **Severity:** minor, but it makes a stated security property unenforceable.

**What it says.** The web tier's only secrets are a forwarder key "and the password of the Valkey its optional response cache may use... which may be the instance's L1 Valkey". Rule 10: `triplespace-client`'s "Valkey client holds public API responses only." Line 12: the web tier "reads no other store of it".

**Why it is a problem.** L1 holds sessions, rate counters and restricted forms (line 3). A web tier with that password reads all of it; "holds public responses only" is a promise of the code, not a property of the deployment, and 20 §5.3 is explicitly a list of properties that have to be true for the model to mean anything. One compromised `triplespace-web` replica is then every session.

**Suggestion.** Drop "which may be the instance's L1 Valkey". Require a separate Valkey, or a Valkey ACL user restricted to the `web:` key prefix, and make `instance check` fail when `web.cache.valkey_url` resolves to the instance's L1 with an unrestricted user.

## 21. Special pages

Sound: the registry, aliases, scope and the `index`/`projection`/`batch` backings; local-graphs-by-default (§2.2) is exactly the rule that keeps reports off the mirror. I'd sequence the whole of §3–§6 after milestone 1 except `EntityData`, `EntityPage`, `Search`, `RecentChanges`, `Contributions`, `Log`, `Jobs`, `Version`, `SpecialPages`, `UserLogin`, `CreateAccount`, and the Wikibase forms that Pywikibot tests touch.

### F-19-10. "Served records a decision, not an implementation", but the API reports served pages as existing

**Chapter §:** 21 §1.1 statuses; §1.2 "`siprop=specialpagealiases` reports one entry per served page"; §8 (169 served). **Severity:** design debt; a compatibility trap in milestone 1.

**Why it is a problem.** Pywikibot and other clients read `specialpagealiases` and `siprop=statistics`/`querypage` to decide what a site has. If the registry's `served` set (169 pages) drives that response from day one, a client that asks for `Special:Nuke` or `list=querypage&qppage=Wantedpages` gets a 404 or an empty page instead of MediaWiki's "no such special page", and the compatibility CI of 22 §4.2 either lies or fails. `Special:SpecialPages` would list 169 links of which a milestone-1 build serves a dozen.

**Suggestion.** Derive the API listing and `Special:SpecialPages` from what the binary compiled, not from the registry's `served` field: each served page registers a handler, and `triplespace-titles` (or whichever crate ends up owning it; see F-19-11) intersects the registry with the handler set at startup, reporting the difference on `server.admin_listen`. Keep `served` as the design decision it is and add a `milestone` field for planning.

### F-19-11. The site's crates cannot embed the registries they need under rule 10

**Chapter §:** 21 §1.1 "embedded by `triplespace-titles`"; 23 §4.1 table (`namespaces.toml`, `special-pages.toml` embedded by `triplespace-titles` only); 22 §1.2 rule 10; 22 §2.1 `triplespace-titles` row (depends on `triplespace-db`). **Severity:** design debt; blocks milestone 1's UI as drawn.

**Why it is a problem.** `triplespace-ui` must route `Special:*` names and aliases, draw the namespace selector, normalize titles for links and the `[[` autocomplete, and list `Special:SpecialPages`. The only crate that embeds those registries also opens Postgres, and rule 10 forbids the UI from depending on it. So the UI either calls `siprop=namespaces|specialpagealiases` on every request (adding to F-19-7), re-embeds the TOML files in violation of "embedded by the crates that need them... one file, one crate", or the rule bends. The same split hurts 19 §2.1's claim that search input "uses the title resolver": the resolver is DB-backed and lives behind the API.

**Suggestion.** Split `triplespace-titles` into a pure `scatter-titles` (namespace registry, special-page registry, title normalization, alias resolution; wasm-capable) and the DB-backed resolver that stays in layer 4. The UI, the API and `scatter-wasm` all take the pure crate; 23 §4.1's "Embedded by" column moves two rows.

### F-19-12. Entity reports "evaluated on the resolved view" fan mirror changes through the report projection; per-tenant rebuilds have no primitive

**Chapter §:** 21 §2.2 ("Conditions are evaluated on the **resolved view**"), §2.3 ("Each change to an input key recomputes only the entries that key affects"; "When it moves from batch to live, the `report` projection rebuilds its rows for that tenant"), §2.4 (`EntitiesWithoutLabel` over `view.entity, view.term`). **Severity:** design debt.

**Why it is a problem.** `EntitiesWithoutLabel` lists local entities, but whether local `Q5` has a label depends on whether its cluster has a Wikidata member with one. So every term change in the mirror is an input to a report about local entities: the projection must, per mirror term row, look up the cluster and ask whether a local member exists. That is cheap per row and millions of rows per sync, inside "0013 §7's synchronous budget" for interactive writes and in the projection worker's queue for syncs; the report's lag is then the mirror's lag. Separately, 03 §6.1 defines rebuild as "truncates the projection's tables and replays from offset 0"; 21 wants "rebuilds its rows for that tenant" for one report, which is a different operation that neither 03 nor `scatter-projection`'s row in 22 provides.

**Suggestion.** Make entity reports consume the output of the resolution projection (resolved terms per canonical ID, which already exist in `view.term`) with a trigger only when the canonical's resolved row changes and the cluster has a local member (an index on `cluster_id` restricted to local IDs). Add "rebuild projection P for tenant T from `view`" as a named operation (this is F-19-2's view-derived class again). State that a report's freshness is bounded by the resolution lag of the mirror, and show it on the page beside "computed at".

### F-19-13. Three pages imply O(history) or O(entities) work without a named index

**Chapter §:** 19 §2.5 / 21 §8 (`Contributions/{issuer}:{id}` for a foreign actor: "upstream revision records keyed to that actor in `log/{provider}`"); 21 §4.1 (`Special:Nuke`: "the window can be extended to the target's whole history"); 21 §4.2 (`Special:Export` of a local entity: "its text is the canonical JSON of the entity's **local-graph** state at that revision"). **Severity:** minor each; together a pattern.

**Why it is a problem.** A full Wikidata mirror with history holds on the order of 10^9 upstream revision records; "keyed to that actor" needs an index `(actor, time)` over them that 03 does not list and that costs a large fraction of the record table. Nuke over "the whole history" reads `view.activity` by actor, which is fine, but for a change-tag target (`oauth:{slug}`) it is a scan of `tags` unless there is a GIN index, also unlisted. Export's "state at that revision" is a fold of every change set from the entity's first record, per exported revision, up to `export.max_history` = 1,000 per page; it needs either stored per-revision JSON (not in `view`) or a fold routine nobody has named.

**Suggestion.** Bound the foreign-actor view to what `view.activity` already holds (upstream *log* events keyed to the actor) plus an explicit "this instance does not index upstream revisions by actor" note, or list the index in 03 with its size. Add the GIN index on `activity.tags` to 03. Say in 21 §4.2 that per-revision entity state is folded from the log by the export job (so it is `ops` work, never streamed), and cap `export.max_history` for entities lower than for pages.

## 23. Configuration and registry

Sound: the record shape (§1.1), the first-records order (§1.2), the four-places rule (§3.1) as a classification, and the "names are never reused" registry discipline (§4.1). The problems are what the chapter leaves to the implementer, and they are permanent because the partition is append-only.

### F-19-14. Tenant-scoped resolution policy defeats the shared view on the second tenant

**Chapter §:** 23 §2.2 (`reconcile`: "Tenant... Provider order, an optional `order_by_type` override..."; `providers`: "Tenant... The providers whose graphs contribute to this tenant's resolved view"; `sitelink-policy` `mode`/`list`: tenant; §3.2 `entities.term_languages`, `entities.mirror`); 03 §7 as read from here ("Everything derived from shared source graphs alone is computed once... Everything a tenant's own graph changes is an overlay"); 03 §6.2 ("a record in a tenant partition therefore re-runs steps 3–5 for that tenant's overlay"). **Severity:** blocker for the core use case ("shared view + tenant overlay surviving a real second tenant").

**Why it is a problem.** 03's overlay model keys overlays on *records in the tenant's partitions*. A tenant `reconcile` record is one record in the tenant's `config`, and it changes the resolved result of every entity that has two or more contributing graphs, which on a Wikidata+OpenAlex+Librarybase instance is most of the scholarly graph. Likewise a tenant that opts out of a provider (`providers:list`), denies a sitelink host, or wants terms in a different language set. There are only two implementations: materialize the whole resolved view per such tenant (O(entities) rows per tenant, the thing the overlay model exists to avoid), or re-resolve on read for every entity with more than one source (O(sources) per read, uncached across tenants). The chapter does not say which, and the settings catalogue presents these as ordinary tenant settings an administrator writes with `ts-config`.

**Suggestion.** Decide now, in 23 and 03 together. The cheap decision: provider order, provider list, denied hosts and term languages are instance-scoped (or tenancy-template provisioned and locked) for the shared view; a tenant may *narrow* (hide a provider in its UI and API, which is a filter on read) but not reorder. The expensive-but-honest decision: introduce "resolution profiles", a shared view computed once per distinct (order, providers, policy) tuple, with tenants bound to a profile and the operator deciding how many profiles the instance can afford. Either way, state in 03 §7 which config kinds are allowed to change the shared result and that a write to any other is refused at tenant scope.

### F-19-15. "Starts from the registry" is undefined, and config content has no per-kind versioning

**Chapter §:** 23 §4.1 ("They are defaults, not state: an instance's `config` partition starts from them and may diverge"); §1.1 ("`view.registry` is the projection of the latest record per key"); §1.4 (templates "each a tenant-config record new tenants start from"); §2.1–2.2 (one payload type `scatter:v0/config`, thirty-odd kinds). **Severity:** design debt that will be expensive later, and permanent (the log is append-only).

**Why it is a problem.** Two readings of "starts from" lead to different logs. *Copy on create*: `instance create` and `tenant create` append one record per registry entry (providers, issuers, keyed types, namespaces per tenant, groups, content models...), `view.registry` is exactly the latest record per key, and a later binary that adds `GD` to `providers.toml` does nothing for an existing instance until someone appends a record, which no command in 22 §2.1 or 23 §5 does. *Overlay at read*: the partition holds only divergences, `view.registry` is not "the latest record per key" but a merge with the embedded defaults, a retired default needs a null record, and two binaries with different embedded registries compute different `view.registry` from the same log, which breaks "rebuildable from the log". Separately, each kind's entry schema will change across releases (`page-repo` already "replaces `template-repo`"; `namespace` kinds were redefined by 0041), and the only version on the record is the payload type's `v0`. A `provider` record written in 2026 must parse in 2030; nothing says how.

**Suggestion.** Choose copy-on-create plus an explicit `registry sync` command (listed in 22 §2.1 under `triplespace-cli`) that appends records for registry entries newer than the instance's, under the instance attestation, and that `instance check` warns about when behind. Add a `schema` integer to the content part of every config record, per kind, and the rule that `view.registry` stores the entry as opaque JSON with its schema number and that kind-specific parsing happens at use with an upgrade function per (kind, schema). State explicitly that an unknown kind or schema is projected opaquely and never fails replay, so an older binary can replay a newer log.

### F-19-16. The "by rule" scoping hands instance resource bounds to tenant administrators

**Chapter §:** 23 §3.1 ("A dotted setting key an ADR names without saying which `config` holds it is a tenant `site` setting"); §3.2 rows marked "`site` (by rule, §3.1)". **Severity:** design debt; a farm-safety hole.

**What it says.** Under that rule: `projections.sync_budget` and `projections.sync_time` (how much fan-out runs inline in the write transaction), `files.thumb_concurrency` ("Size of the thumbnail rendering pool"), `repo.concurrency` and `repo.fetches_per_minute` (upstream budget), `federation.clock_skew`, `files.orphan_grace`, `updates.batch_interval`, `notifications.fediverse_interval`, `scopes.max_members`, `sprints.max_tasks`, `query.max_results`, `query.timeout`. `query.max_concurrent` is marked "instance-wide" but sits in the tenant table; `query.isolation` is "a tenancy switch; a tenant `config` setting overrides", which lets a tenant demand its own embedded store on a shared farm.

**Why it is a problem.** These are capacity knobs. A tenant administrator on a `community` farm can set `projections.sync_budget = 10^9` and hold the append lock for every other tenant, or set `files.thumb_concurrency` to the host's core count. The rule was written to settle citations, not to allocate authority, and it has allocated it wrongly for about a quarter of the rows. 23 §1.4 already has the right mechanism for one case (`wikitext.ceiling`).

**Suggestion.** Add a column "bound" to §3.2: `tenant` (free), `tenant ≤ instance ceiling` (tenant may lower, instance sets the cap; the cap is a tenancy switch), or `instance` (deployment or farm-base only). Move the pool sizes and intervals to §3.6 deployment configuration; make the budgets and limits ceiling-bounded with the ceilings listed in §3.4; keep `query.isolation` instance-only.

### F-19-17. Two small gaps a programmer would have to fill alone

**Chapter §:** 23 §1.2–1.3 and 05 §6.4; 23 §3.2 after the table. **Severity:** minor.

- "Every other partition is created by a `graph:` record in `config`" and `graph` is an instance kind written "with `ts-config` at the farm base"; a tenant's `entity-source` (tenant kind) "adds one `source/{name}` partition". Nothing says who appends the instance `graph:` record when a tenant administrator declares a source. Suggest: it is an evaluated-then-written instance act triggered by the tenant record, with the authority record pointing at the `entity-source` record.
- "Turning `wikitext.expansion` off also turns `wikitext.lua` off and `wikitext.renderer` back to `builtin`": is that three records appended, or a derived effective value while `view.registry` still shows `wikitext.lua = on`? Suggest: effective values are never derived; the API refuses the write unless the dependent records are included in the same request, and the UI writes all three.

## 19. Site UI

Sound and, for the first milestone, the right order: §4 (statement UI) and §5.8 (prototype against Wikidata, then the reference install) can start before any Triplespace server exists, and §5.1–5.3 (server-rendered Codex, components over regions) are the cheapest frontend this project could choose. The two findings are bounds.

### F-19-18. The entity page asks for aggregates that are O(n) per view

**Chapter §:** 19 §3.1 ("the revision count by origin (imported, bot, local)... the backlink count, and the page-statement count"; "In 3 scopes"; "2 proposals"); §1.3 ("Links here"); 18's `GET /entity/{id}/provenance` carrying "the backlink count". **Severity:** design debt that will be expensive later (it lands on the hottest page of the site).

**Why it is a problem.** On a `full` Wikidata mirror, the backlink count of a hub item is tens of millions of `entity_ref` rows; the revision count by origin for a mirrored item with retained history is a scan of its records across partitions; the scope count is a lookup over `view.scope_member` by subject (fine) but every scope refresh changes it. None of these is cheap on first render, and the L1 cache key for the entity (its `resolved_version`) does not change when a referrer, a scope or a proposal changes, so the count is either recomputed on every miss or served stale under the wrong key. (See F-19-7 for the same number arriving through the provenance route.)

**Suggestion.** Maintain `ref_count` and `revision_counts` as columns on `view.entity`, updated by the `entity_ref` and activity projections in batches (never one `UPDATE` per referrer row during bootstrap; 05 §3.8 already builds `view` after the load, so the counts come from one aggregate at the end), and give the About panel its own small API response with its own short `max-age`, independent of the entity's `ETag`. Render "10,000+" above a threshold rather than the exact number.

### F-19-19. The history of a mirrored entity has no single backing, and three chapters describe its rows differently

**Chapter §:** 19 §3.3–3.5 ("one row per observed state"; "covers records in every source partition"; a switch "one entry per mirror that contributes"); 19 §5.2 (`view.activity` "grows with local activity and the number of jobs, not with the size of the mirrors"); 16 §3.2 ("The activity projection... indexes events from both log graphs"); 03 §4.6 ("per-entity mirror history is served from `entity_source` and the record itself"). **Severity:** minor, but it is a missing decision on the second-most-visited page.

**Why it is a problem.** The page is a time-ordered union of (a) local activity rows for the entity and its cluster members, (b) mirror records by key across every member's partition, read from `log.record` which the API's role is not otherwise said to read, (c) upstream log events from `log/{provider}` which 16 puts in `view.activity` and 03 says never grow it, and (d) live-fetched upstream edits folded under (b). Keyset paging across a four-way merge by time, with the cluster expansion done per request, is a query someone has to design; the `GET /entity/{id}/history` row in 18 says "Activity rows across the whole cluster" and nothing about (b). Under `latest` there is exactly one row of kind (b), so most of the design is for retained entities and `full` mirrors, which is the core use case.

**Suggestion.** Name the backing in 03 and cite it from 19: a `view.entity_history (canonical_id, time, partition, offset, kind, member)` projection row per mirror record and per relevant log event, written by the resolution projection (it already has the record in hand), so that history is one keyset query over one index, bounded by the entity's own record count. Decide whether upstream log events are activity rows (16) or not (03) and fix the losing sentence.
