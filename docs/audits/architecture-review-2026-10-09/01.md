# Review: 01 Log and records, 03 Storage, caches and search

Scope: chapters 01 and 03 in full, with 02 §6–7, 04 §4, 05 §1–3, 06 §2.2 and 08 §2, §4, §9–10 read where 03 stores what they define. Lens: the first milestone (Postgres log, resolved view over a Wikidata-scale `full` mirror plus local data plus OpenAlex, identity clusters, Action/REST API, site UI).

## Overall judgement

The log layer (01) is sound and conventional where it matters: canonical CBOR as preimage, RFC 6962 tree with domain-tagged SHA-256, C2SP checkpoints, salted erasable parts, compaction that keeps leaves, global IDs inside the hashed header. None of that will hurt, and most of it can be built once and left alone. The storage layer (03) is also right in its big choices: log and projections in one database and one transaction, "the blob serves the page; tables serve queries", keys that name versions, erasure as the only purge, packed storage deferred behind a measurement. Where 03 will hurt is not in any table but in two mechanisms the chapters inherit from 04 and 02 and then store: canonical-ID rewriting *into* the materialized resolved view, and the delta stream computed *inside* the write transaction. Together with the per-tenant overlay rule, rewriting turns a single `same-as` or `convert` on a popular entity into a re-resolution of every referrer, per tenant, which is the one O(entities) fan-out the design cannot bound; and the chapters never say where the current state of a locally edited entity's *own graph* lives, which every re-resolution and every delta needs.

For the first milestone I would build 01 as written (plain storage, no packing), the `log` schema and the `view.entity`/`entity_source`/`term`/`identifier`/`entity_ref`/`activity`/`page` tables, bootstrap, and the resolution projection, and explicitly defer `rdf_delta`, the constraint projection over mirrored data, packed storage, per-tenant clusters and the Postgres search fallback. Before writing the resolution projection, three decisions need making that no programmer should make alone: whether entity *values* are rewritten to canonical IDs at projection time or at read time (F-01-1), where per-graph current state is kept (F-01-2), and which sequence mints a mirrored entity's page ID (F-01-3). The findings below are ordered by how much they block that milestone.

---

### F-01-1. Canonical-ID rewriting in the stored resolved view is the unbounded fan-out, and the overlay rule multiplies it per tenant

**Where:** 04 §4.4 ("The resolved view rewrites subjects and entity values to the canonical ID"; "The canonical ID is chosen when the resolved view is projected"), 04 §4.9 (statement GUIDs rewritten), 03 §4.2 ("for most entities in a full mirror, exactly one graph contributes and no value refers to a clustered entity"), 03 §6.2 ("referrers re-resolved by a cluster change … a link to a heavily cited author shows its effect on referrers within lag"), 03 §7 ("a tenant that has … a cluster link touching it … gets its own `(tenant, id)` row").
**Severity:** blocker for the core use case.

**Why it is a problem.** Because values are rewritten into the stored JSON, the set of entities whose resolved form differs from their source is not "entities in a cluster" but "entities in a cluster plus every entity that references a non-canonical member". With OpenAlex as the second provider, nearly every work references authors, institutions and sources, and most institutions and many sources are clustered with Wikidata items (tier 2 via `ids.wikidata`, with Wikidata canonical by provider order). So most OpenAlex works become `materialized`, which is exactly the doubling of the largest table that §4.2 says the `source` kind exists to avoid. Worse, tier-1 links are per tenant (03 §7, 04 §4.3): a Librarybase `convert` of `WDQ5` (human) makes `Q{n}` canonical *for Librarybase only*, so every one of the ~10M items with `P31=WDQ5` needs a Librarybase overlay row in `entity`, `entity_ref` and its materialized JSON. One edit, ten million rows, per tenant, queued as fan-out "within lag". The 250 ms / 1,000-row budget bounds the editor's latency, not the work.

**Suggestion.** Adopt Wikibase's own precedent for redirects: do not rewrite entity *values* or statement GUID prefixes in stored or served data. Emit `owl:sameAs` for each non-canonical member in RDF (which 04 §4.4 already does), resolve a non-canonical ID to the canonical entity on request (which the API already does), and let the UI label a value by its cluster's canonical member through the L0 "canonical ID of each cluster member" map at render time. Then a cluster change touches the members' rows and nothing else; `materialized` is reserved for entities with two or more contributing graphs or local deltas; and the overlay rule is bounded by what a tenant actually edited. If value rewriting is kept for some output (dumps), make it a serialization-time transform over a canonical map, never a stored form. Decide this before the resolution projection is written; it changes `entity_ref`, the delta contract (02 §6.2 "one delta per referrer") and the search `incoming_links` count.

### F-01-2. The current state of an entity in its own source graph is stored nowhere, and three mechanisms need it

**Where:** 03 §4.2 (`view.entity_source."offset"` is "the graph's current record for the entity"; "A local entity that has been edited with `add` or `remove` is materialized even when it is the only graph, since no record holds its state"), 02 §6.2 (delta old state for `local`: "the graph's previous state for the entity, which the ingester reads to compute `changes`"), 03 §6.2 (re-resolution on a new mirror `put` for an entity with local assertions), 01 §2.5 and 18 (`oldid=N` for local revisions).
**Severity:** blocker for the core use case (underspecification in the write path).

**Why it is a problem.** Resolution is a function of each contributing graph's *current state*. For a mirror graph that state is the latest `put`, which `entity_source.offset` names. For the local graph on a foreign entity (scenario D, 05 §2.5) and for any local entity edited with deltas, no record holds the state: it is the fold of every local change set for the key. The chapter stores only the *fused* result in `view.entity.resolved`, which cannot be un-fused when the mirror side changes. So every re-resolution of an entity with local edits, and every delta on the `local` graph, must replay the key's local history from the log, O(local revisions), inside the write transaction. For bot-edited entities with thousands of revisions that is the whole edit budget. The same gap makes `oldid=N` content for a local revision an O(N) replay, where MediaWiki reads one row.

**Suggestion.** Add a per-graph state table to the catalogue, `view.graph_state (tenant, entity_id, graph, state bytea, "offset", version)` or equivalent, written by the step-2 projection for every graph whose records are deltas (`local`, `derived/*`, `source/*`), and name it as the "old state" the delta projection reads. Decide separately whether per-revision state for local entities is stored (`view.revision_state`, MediaWiki's model, cheap under lz4 and fragment packing) or `oldid` is served by replay with a cap; say which in 03 and 18.

### F-01-3. Mirrored entities and local pages take page IDs from different sequences and are declared to share one space

**Where:** 03 §2.3 ("A mirrored entity's page ID is taken from `log."instance.page_id"` the first time its key is written, since it belongs to no tenant"), 03 §4.5 ("Entity pages get their `page_id` from the same sequence as document pages (§2.3), so `view.entity.page_id` and `view.page.page_id` never collide and one `pageid` space covers both kinds of page"), 01 §2.5 ("Page IDs are carried forward … taken from one sequence"), 03 §4.2 (`page_id bigint NOT NULL UNIQUE` on `view.entity`).
**Severity:** blocker for the API compatibility the milestone depends on.

**Why it is a problem.** `log."instance.page_id"` and `log."{tenant}.page_id"` are two sequences starting at 1, so a tenant's local page and a mirrored `WDQ` entity will share `pageid` values; `pageids=`, `prop=info` and every Pywikibot/WDI call that keys on `pageid` becomes ambiguous. The value is in header field 9, so it cannot be fixed after the first mirror record is written. Separately, `page_id UNIQUE` on `view.entity` cannot hold once `tenant` leads the primary key: the shared row and every tenant overlay row for one entity carry the same `page_id`.

**Suggestion.** Decide one of: (a) mirrored entities get a provider-ranged page ID, `provider_number << 40 | n`, exactly as repository pages do (the mechanism exists, and it also removes the lookup every bootstrap writer must make to carry a page ID forward); or (b) every tenant's page sequence starts above a reserved instance range. (a) is cleaner and needs no projection read to mint a hashed header field. Change the unique constraint to `(tenant, page_id)` or drop it.

### F-01-4. The shared/overlay tables are incomplete and the lookups over shared rows are unspecified

**Where:** 03 §4.1 (list of tables gaining `tenant`: `term, sitelink, identifier, entity_ref, statement_assertion, correction, constraint_violation, value_key`), 03 §4.2 (`view.entity_source` PK `(entity_id, graph)`), 03 §4.4 (`view.cluster_member … entity_id text NOT NULL UNIQUE`; `view.link`, `view.different_from` without tenant), 03 §7 ("A tenant's clusters are the shared clusters with its overlay applied"), 03 §11.4 ("where a tenant document and a shared document share an ID, the tenant's wins").
**Severity:** blocker for a second tenant; design debt for one.

**Why it is a problem.** Three things cannot be implemented as written. (1) `view.entity_source` holds `local` and `source/{name}` rows, which are per tenant, but has no tenant in its key: two tenants with local assertions on `WDQ42` collide on `(WDQ42, local)`. (2) Tier-1 links are per tenant, so an entity can be in different clusters for different tenants, but `cluster_member.entity_id UNIQUE` and the tenant-less `cluster`/`link`/`different_from` tables can hold one answer only; 03 §7 describes per-tenant clusters and 03 §4.4 stores none. (3) The read rule "one lookup with the viewer's tenant, falling back to `''`" is correct only for primary-key reads. Every query over shared rows by a *non-primary* key (`identifier` by `(property, value_key)`, `sitelink` by `url_key`, `entity_ref` by `target_id`, `term` by prefix) must also exclude shared rows whose source entity the viewer's tenant has overlaid, since the overlay may have suppressed the statement; that anti-join is nowhere stated, and OpenSearch cannot express it at all, so "the tenant's wins" across two indexes is a post-query dedup that breaks paging and scoring and cannot represent "the tenant suppressed this entity from search".

**Suggestion.** Add `tenant` to `entity_source` (or key it by partition rather than graph name). Either give the cluster tables a `tenant` column with the same `''`/overlay rule, or decide that clusters are instance-wide and tier-1 links are instance acts (simpler, and enough for milestone 1 with one tenant). Write the overlay-exclusion rule once in §7 ("a read over shared rows by any key other than the entity excludes rows whose `source_id`/`entity_id` has an overlay row for the viewer's tenant") and note which tables carry an index to make that cheap. For search, state that a tenant overlay document *replaces* the shared one by deleting the shared doc's visibility for that tenant (a `tenant_overlaid` filter term on the shared doc, maintained by the overlay projection), or accept dedup after retrieval and say so.

### F-01-5. The delta projection is mandatory inside every write, and its cursor is not safe under concurrent transactions

**Where:** 03 §6.1 step 7 ("The delta projection … runs inside steps 2, 4 and 7 … and writes `view.rdf_delta` in the same transaction"), 03 §6.2 ("A write's own rows are always synchronous: … its delta"), 03 §4.11 (`seq bigint GENERATED ALWAYS AS IDENTITY`; "it is monotonic in the order deltas were produced, which is the order projections applied them"; "A transaction is one event … whose cursor is the transaction's last `seq`"), 02 §6.2 (old and new states each "rendered to triples … and the delta is the set difference").
**Severity:** design debt that will be expensive later; blocker for the stream when it ships.

**Why it is a problem.** Two separate things. First, cost: every mirror `put` renders the old and new entity to RDF twice (`mirror/{provider}` side and `resolved` side), diffs, compresses and inserts, inside the ingest transaction, whether or not any consumer exists. For a steady-state Wikidata sync (millions of changed entities per week) that is the single largest per-record cost in the projection chain, paid for a feature the milestone does not use. Second, correctness: `seq` comes from a sequence taken *inside* concurrent transactions, so commit order is not `seq` order. A consumer polling `seq > cursor` can see a committed row with `seq = 7` while `seq = 5` belongs to a transaction still open, advance past 5, and never see it. The chapter's "never see two events for one entity out of order" is false in exactly the case it claims to cover (two appends to different partitions touching one entity's shared and overlay rows). The `txn` grouping has the same hole: rows of one transaction are not contiguous in `seq`.

**Suggestion.** Make the delta projection a configured consumer (`updates.enabled`, default off) that runs in the projection worker behind the append, reading old state from F-01-2's state table, not inline in the write. For the cursor, either serialize delta emission (one advisory lock per instance around the `rdf_delta` insert, which is cheap once it is off the interactive path) or make the cursor the commit position (publish from a single worker that assigns `seq` as it reads committed rows in `xmin`/LSN order). State which; "the order projections applied them" is not a Postgres guarantee.

### F-01-6. Bootstrap assumes an empty instance and rebuild assumes downtime: there is no path for adding a provider to a live instance or rebuilding a projection online

**Where:** 05 §3.8 step 1 ("The target child tables are created with the primary key only. The mirror partition's `(key, offset)` index and every `view` table are absent"), 03 §6.1 ("A rebuild truncates the projection's tables and replays from offset 0"; "One projection may own several tables"; the rebuild "orders partitions by dependency"), 03 §9.3 (`resolved_version` "monotonic; bumped on every re-resolution").
**Severity:** blocker for the core use case as a sequence (Wikidata, then local, then OpenAlex).

**Why it is a problem.** The milestone's own order is: mirror Wikidata, adopt or create local data, add OpenAlex. Step three happens on a live instance with every `view` table populated, which bootstrap as written forbids. What is needed is per-partition catch-up: load one partition in bootstrap mode, then run projections 2–7 *over that partition only* against existing tables, with the cross-partition effects (tier-2 links into Wikidata entities, fusion) handled as fan-out. `ops.projection_state` is already per (projection, partition), so the shape is there, but the chapter describes only the empty-instance case. Likewise a rebuild of `entity` (which owns `term`, `identifier`, `entity_ref`) is a days-long job at Wikidata scale, and "truncate and replay" takes the site down for its duration; nothing describes a shadow-table rebuild and swap. Finally, after a rebuild `resolved_version` restarts, so an L1 key `e:{id}:{gen}:{ver}` from before the rebuild can match a different body after it; `generation` is not bumped by rebuild and nothing flushes L1.

**Suggestion.** Specify bootstrap as per-partition (it already is at the log level) and add a "catch-up" mode: indexes and projections for one new partition against a live `view`, with its tier-2 and fusion fan-out queued in `ops.projection_work`. Specify rebuild as build-into-`view_next`-and-swap per projection, and have every rebuild bump an instance-wide cache epoch that is part of every L1 key (the delta `epoch` in `ops` can be that number). For milestone 1, say which projections are rebuildable in place (small ones) and which only by swap.

### F-01-7. The constraint projection runs over all mirrored data by default

**Where:** 03 §6.1 step 4 (`constraint_violation` after `entity`), 03 §4.4 (constraint tables carry the tenant column; "synchronous for the changed entity's own statements"), 06 §2.2 ("Mirrored data is checked as local data is"; "changing an item's `P31` re-checks *type* constraints on statements that point at it"; "Bootstrap … runs the constraint projection last, and a Wikidata-scale instance may run it for a chosen set of properties first").
**Severity:** blocker for bootstrap time; design debt otherwise.

**Why it is a problem.** Wikidata has thousands of constraints and Wikidata's own checker is a WDQS-backed, days-long, sampled job. Here it is a step of the default projection chain over 110M entities, with *type* checks walking class chains and *inverse/symmetric* checks reading referrers, and with a `P31` change on a popular class fanning out to every instance of it. "May run it for a chosen set of properties first" is a hint, not a mechanism. Nothing in 03 makes the projection skip shared rows.

**Suggestion.** Make the constraint projection scoped by `site` configuration with a default that checks the local graph and overlay entities only (`constraints.scope = local | overlay | all`), and make `all` a batch job with progress rather than a projection step. Record that the shared-row constraint rows are empty unless `all` is on. This removes it from the milestone without changing any table.

### F-01-8. The partition row lock is held across the synchronous projections, which caps interactive write throughput per tenant

**Where:** 03 §2.1 ("The transaction locks the partition's row in `log.partition`, takes `next_offset`, inserts, and advances it. A rollback releases the offsets, so the sequence stays gapless … Appends to one partition are serialized by that lock"), 03 §6.2 ("applies projections 1–5 for the affected keys" before commit; `projections.sync_time` default 250 ms; "The append lock of §2.1 is released at commit").
**Severity:** design debt that will be expensive later.

**Why it is a problem.** Gapless offsets force the lock to be held until commit, and commit comes after resolution, terms, identifiers, `entity_ref`, own-statement constraint checks, the delta, the activity row and up to 250 ms of fan-out. Every interactive write to a tenant's `local` partition therefore waits for the previous one's projections. The ceiling is roughly 1/(transaction time) edits per second per tenant: single digits under load, and a bot batch from WDI or Pywikibot (which already serialize per client) will sit behind UI edits and vice versa. MediaWiki does not serialize edits to a wiki this way; its revision table takes a sequence value, not a row lock, and tolerates gaps. The chapter documents the lock as "correct behaviour for the local partition, where edits must be ordered", but ordering by offset and serialization through projection time are different requirements.

**Suggestion.** Decide explicitly. Options: (a) accept the ceiling, measure it, and publish it in the profile table; (b) keep gapless offsets but shrink the critical section: allocate the offset and append the record under the lock, commit, then apply projections 1–5 in a second transaction keyed by the record, with read-your-writes served by the version the response returns (the API already tells clients "wait for the version its write returned") and the base-offset check still against the log; (c) allow gaps and use a sequence. (b) keeps every invariant in 01 and moves the budget out of the lock. Whatever is chosen, say which projections may run after the append commits and which must not (the ACL projection and `filter` are read by the write path and must stay inline).

### F-01-9. Concurrency between the synchronous path and the projection worker, and the L1 write before commit, are unspecified

**Where:** 03 §6.2 ("The remainder is queued in `ops.projection_work` … applied in append order by the worker that serves bulk jobs"), 03 §9.3 ("the write path also writes the new resolved JSON into L1 so the editor's next read hits"), 03 §4.2 (`resolved_version bigint … monotonic; bumped on every re-resolution`), 03 §6.1 (`ops.projection_state (projection, partition, applied_offset)`).
**Severity:** design debt; a correctness bug the first time it is hit.

**Why it is a problem.** (1) Two writers can resolve one key: an interactive edit to referrer R re-resolves R inline while the worker is re-resolving R for an earlier cluster change. Both read "current state", but a worker transaction that read before the edit committed and writes after it overwrites the newer result; nothing says the resolution row is locked per key or compared by version. (2) If the resolved JSON is written to L1 before commit and the transaction rolls back, L1 holds a body under a `resolved_version` that the next successful write will reuse, since the version is per row, not a global sequence; the key is then poisoned for 24 h. (3) `applied_offset` per partition is meaningless when interactive records are projected inline at offset 1005 while a bulk job's 900–1000 in the same partition are still "behind the append"; lag reporting and rebuild resume both read it.

**Suggestion.** State three rules: resolution of a key takes `SELECT … FOR UPDATE` on its `view.entity` row (shared or overlay) in both paths; L1 is written after commit, or `resolved_version` is drawn from one instance-wide sequence so a rolled-back version is never reused; `ops.projection_work` is the unit of truth for lag and `applied_offset` records the contiguous prefix, with inline-projected records recorded as work already done. These are three sentences in §6.2 and they save a week of debugging.

### F-01-10. `entity_ref` and `term` will be the largest tables by bytes, and their keys make them larger than they need to be

**Where:** 03 §4.3 (`view.entity_ref … PRIMARY KEY (target_id, source_id, statement_id, role)` with text IDs and statement GUIDs; "`entity_ref` is the largest table after `record` … on the order of 10^9 rows"; `view.term … PRIMARY KEY (entity_id, kind, lang, ordinal)`), 05 §5.8 and 03 §5 ("`term` rows of mirrored entities in `entities.term_languages` only" for *shallow* mirroring; `entities.term_languages` is a tenant `site` setting), 22 §6 ("`entity_ref` … the largest `view` table").
**Severity:** design debt that will be expensive later (the kind that is cheap now and a migration at 10^9 rows).

**Why it is a problem.** A Wikidata full mirror has well over a billion entity references (main snaks, qualifiers and references with item values). Each `entity_ref` row as specified carries two text IDs (~8–12 bytes each) and a statement GUID (~45 bytes) in the primary key, so the index alone is a few hundred GB; every re-resolution of an entity deletes and reinserts its rows. `statement_id` is needed only for "which statement" on the provenance panel, which the resolved JSON already answers. `view.term` at full language coverage is the same order of magnitude in rows (Wikidata's term store was over a billion rows before normalization) and the chapter calls `entity_ref` the largest, which suggests `term` has not been sized. The one relief, `entities.term_languages`, is written for shallow mirrors and is a *tenant* setting, while the `term` rows of a full mirror are *shared* (`tenant = ''`), so it cannot apply as written.

**Suggestion.** Key `entity_ref` on integers: `view.entity.page_id` is already a unique `bigint` per entity, so `(target_page_id, source_page_id, roles smallint)` with roles as a bitmask, and drop `statement_id` (recover it from the JSON when a panel asks). Make the language restriction an *instance* setting that applies to shared `term` rows of every mirror, full or shallow, and serve other languages from the record, as 05 §5.8 already describes; the Wikidata-scale profile then lists `view.term` beside `entity_ref` with its expected size. Flag now that both tables are candidates for their own tablespace in the profile.

### F-01-11. Four things in the record format lock in more than they should

**Where:** 01 §2.5 (provider-ranged IDs; entity-source numbers "from 2^22 to 2^23 − 1"), 01 §2.5 ("Page IDs are carried forward … taken from one sequence the first time a key is written"), 01 §3.2 (the hash guard: "upstream's hash is kept in place"), 01 §1.2 and §3.3 ("named in the partition's genesis record"), 03 §2.2 (`log.segment_manifest … replaces bigint[] … manifests this one supersedes after compaction`; PK `(partition, segment, sealed_at)`).
**Severity:** minor each, but each is permanent once a record is written; one is a client-visible bug.

**Why it is a problem.** (1) `revid = provider_number << 40 | n` with entity-source numbers at 2^22 gives revision IDs around 2^62, above JavaScript's 2^53 safe integer; `lastrevid`/`baserevid` on any entity-source record will be mangled by every JSON client that parses numbers as doubles (browsers, many bots). Registry providers above number 8191 hit the same wall. (2) A mirror record's page ID (header field 9) is minted by consulting a projection (`view.entity`) to see whether the key was written before; a hashed header field that depends on mutable `view` state is a trap for bootstrap writers and for any re-import after a tombstone-and-compact (the entity gets a new `pageid`). F-01-3's option (a) removes this. (3) The hash guard makes the content bytes of a `put` depend on whether the ingester's hash emulation agreed with upstream at write time: the same upstream revision re-imported after a fix produces different bytes and a different content hash, so the version cursor sees a change that is not one. Acceptable, but say so, and say that `content_hash` comparison for skip-if-unchanged must ignore kept `hash` fields. (4) The genesis record that names a partition's hash function, `k`, policies and name is cited twice and specified nowhere: without it a bundle's partition is only interpretable through `log.partition`, which the bundle does not carry, and the partition's own policy is not committed under its tree. (5) `segment_manifest.replaces` and a `sealed_at` in the key contradict 01 §6 and PENDING A1 ("no manifest is re-signed and none lists a manifest it replaces").

**Suggestion.** Move entity-source numbers below 2^13 (there is no need for 2^22 of them per tenant) and add "every ID a client sees is below 2^53" to 01 §2.5 as a rule. Specify the genesis record as offset 0 of every partition, payload type `scatter:v0/partition`, carrying name, tenant, policies, `k` and hash, and list it in the bundle contents of 01 §8. Drop `replaces` and `sealed_at` from the manifest key.

### F-01-12. `hashed` partitions: whether they have checkpoints and a partition root is said three ways

**Where:** 01 §1.2 ("`hashed` … one Merkle tree for each sealed segment, with a signed manifest for each segment"), 01 §4.1 ("In bootstrap mode … The partition root is then folded from the segment roots"; "In a `hashed` partition, each segment's tree stands alone"), 01 §4.2 (checkpoints written "at the end of every job"), 05 §3.8 step 5 ("Checkpoints are signed and the partition goes live" for a mirror bootstrap), 03 §2.2 (`log.checkpoint` keyed by `tree_size`).
**Severity:** minor; a decision a programmer would otherwise make alone.

**Why it is a problem.** A mirror partition is `hashed`. §1.2 says it has per-segment manifests only; §4.1 folds a partition root from them; §4.2 and 05 §3.8 write checkpoints for it. If a `hashed` partition has checkpoints, what does `tree_size` mean once compaction leaves holes, and does the unsealed last segment (which at 2^k = 2^16 and a slow stream can stay open for days) get any commitment at all? If it has none, a job's "checkpoint at the end" is undefined for the partitions most jobs write to.

**Suggestion.** State: a `hashed` partition has segment manifests only; its "checkpoint" at job end is the manifest of the last sealed segment plus an unsigned head offset; records in the open segment are uncommitted until sealed; and `log.checkpoint` rows exist for `logged` partitions only. Or give `hashed` partitions a signed root over segment roots and say that is what `tree_size` counts.

### F-01-13. Multi-process append details: the tree's right edge, the checkpoint signer, and the key holder

**Where:** 01 §4.1 ("Appends in steady state keep the tree's right edge in memory"), 01 §4.2 ("in steady state, at least every N records or T seconds"), 03 §1.4 (pooling, replicas), 20 (several API processes).
**Severity:** minor.

**Why it is a problem.** Several server processes append to the same `logged` partition (serialized by the row lock). "In memory" is per process, so each append must reload the right edge from `log.merkle_node` after taking the lock, and the interior nodes on the right edge are rewritten on every append (O(log n) row updates per edit, fine, but it should be stated so nobody caches them). Checkpoint signing "every N records or T seconds" needs one signer per partition and the private key in that process; nothing says which process or how it is elected.

**Suggestion.** Two sentences in 03 §2.2: the right edge is read under the append lock and only complete subtrees are persisted; checkpoints are signed by the projection worker under an advisory lock per partition, and the worker is the only process that holds the instance key.

### F-01-14. The Postgres search fallback is specified at a scale it is not for, and `term_prefix` is the only index on `view.term` that a full mirror cannot carry

**Where:** 03 §4.3 (`CREATE INDEX term_prefix … -- Optional, small profile only`), 03 §11.6, 22 §6.
**Severity:** minor; sound, sequence differently.

The fallback is right for a small instance and the chapter says so. For the milestone, which is Wikidata-scale, OpenSearch is required from the first load, and the catalogue should say the `term_prefix` index is never created on an instance that holds a full mirror (a partial index per language or a `tenant = ''`-excluded index would be the small-tenant compromise if one is wanted later). No change to the design; a line in the profile table.

### Where the chapters are sound

- 01 §2–§4 (record shape, canonical CBOR, domain tags, RFC 6962 tree, C2SP checkpoints, client signatures): sound, conventional, and verifiable with existing tooling. Build as written.
- 01 §5–§6 (erasure as `[null, leaf]`, compaction keeping leaves, upstream redaction as partial erasure): sound. The MVCC/WAL caveat is the right thing to say.
- 03 §1–§2 (one database, four schemas, grants as the privacy boundary, denormalized header columns with a re-encoding test, `merkle_node`): sound.
- 03 §3 (packed storage): sound and correctly deferred behind `storage measure`; keep it off for the milestone. Its sweep fence is the one piece of genuinely subtle concurrency in the chapter and it is specified well.
- 03 §6.3 (LSN-routed replicas), §8 (blob store), §9.1–§9.4 (keys name versions, `{vis}` segment, single-flight), §10 (HTTP caching, web-tier revalidation): sound.
