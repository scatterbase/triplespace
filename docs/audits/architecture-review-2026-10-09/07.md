# Review: chapters 07 Actors and accounts, 08 Tenants and instances, 09 Security and moderation

## Overall judgement

The three chapters describe a coherent and, in most places, well-reasoned model: actors namespaced by issuer with names kept out of keys, subsidiaries as the only credential-bearing accounts, every moderation action as an ACL record whose retirement is the undo, and instance acts as signed, authority-bearing writes into a guest. Taken as a target architecture for a farm, little of it is wrong. The trouble is that almost none of it is optional on day one, and the chapters do not say so. The log is append-only, so the three things the first commit must get right permanently are decided here and are currently either contradictory or circular: what an actor key looks like in a record (`local:42` in 07, `{slug}:42` in 08, "in the header" in 07 but in the erasable attestation part in 01); who attests offsets 0–2 of the instance `config` partition when neither the primary tenant nor `local:1` exists yet; and whether a single-tenant instance must carry the instance attestation, authority record and signed key-chain copy before it can hold its first entity. A milestone with one public tenant, a Wikidata mirror, local data, Pywikibot and the site UI needs: issuers and actor records, subsidiaries with the bot-password shape, groups and blocks, deletion and hiding as `read` ACLs, and rate limits on `edit`/`create`/`job`. It does not need the farm, farm identity, global groups, templates and locks, tenant moves, OAuth, confidential restrictions, or edit filters, and the chapters should say which of these are "format decided, mechanism deferred" so that the deferral does not become a format mistake.

The second concern is cost where the security model meets scale. The visibility machinery is designed so that a public wiki "pays nothing", and at the request level that is true; but the denormalised form of the visibility set (`read_groups` on every activity row and search document, `{vis}` in every cache key) is invalidated by a single tenant-wide epoch, so one set-membership change or namespace restriction either purges the entire tenant's cache and rewrites every row under the namespace, or, if public entries are keyed without the epoch as the text can be read, leaves pre-restriction public entries reachable. Per-resolution ACL lookups and per-record edit-filter evaluation sit on the ingest path of the core use case with no short-circuit, and a private tenant is defined as one with no query service at all, which forecloses the enterprise customer that would most want restrictions. None of these are unfixable, but each is a decision the chapters make implicitly and should make explicitly.

## Findings

### F-07-1. The instance `config` partition cannot be bootstrapped as written, and single-tenant day one carries the whole prerogative machinery

**Chapter §:** 08 §2.2, §2.4, §7.2, §8.3, §8.4, §8.6; 09 §3.6, §4.6. **Severity:** blocker for the core use case (it is the first record written, and its shape is permanent).

**What the text says.** "offset 0 of it holds the instance's first `key:` record" (08 §2.2). "`instance create` appends the first `primary` record after the instance `key:` and the primary tenant's `tenant:` record" (§7.2). "Every record in an instance partition is attested by … an actor of the primary tenant, for everything else" (01 §1.4, 08 §7.4). Authority for key registration is "The `key:` record in the instance `config`", "attested by the operator who acted, an actor of the primary tenant" (§8.4). "`key:` records additionally need `ts-keys`" held by `owner`, whose first member `local:1` is created by `instance create` (09 §4.6, §3.6). And the tenant's own `config` begins with a copy of the key record that "carr[ies] the instance attestation with the instance `config` record as authority" (08 §2.4, §8.6).

**Why it is a problem.** At offset 0 there is no primary tenant, no `tenant:` record, no `local:1` and no `owner`, so the rule for who attests the key record, and whose `ts-keys` is checked, is unsatisfiable. The chapter never says what the attestation of offsets 0, 1 and 2 is. Worse for the first milestone: the very next record, the tenant's key-chain copy, is a written instance act, so the tag `0x06` preimage, the instance signature, the `authority` field, `verify` level 2's checks and the `ts-prerogative` refusal in the write path must all exist before the first entity can be written into a single-tenant instance. 08 §1.1's promise that a single-tenant instance "never notices any of this" is false for the one path every instance takes.

**Suggestion.** Decide and write down the bootstrap sequence: offsets 0–2 of the instance `config` are attested by `instance:{farm slug}` itself (the one actor that exists before any tenant), signed by the key being registered (self-certifying), with the `tenant:` and `primary:` records citing offset 0 as authority. Then decide whether the tenant key-chain copy of §2.4 is really an instance act on day one or whether a single-tenant instance may write it as an ordinary `config` record attested by `local:1` and upgrade to the signed form at the first rotation. If the signed form stays, say plainly in 08 §1.1 that §8.3 is on the critical path of milestone 1 and sequence it there.

### F-07-2. The actor key's spelling and its place in the record are undecided, and both are permanent

**Chapter §:** 07 §1.1, §2.1, §2.2; 08 §3.1; 03 §4.5; 01 §2.3. **Severity:** blocker (format permanence), small to fix now.

**What the text says.** 07 §1.1: an actor key is "`{issuer}:{id}`, such as `wikidatawiki:12345` or `local:42`. It is what log headers carry." 07 §2.1: "A local user's identity is `local:{id}`", and the password binding is "`(password, 42) → local:42`". 08 §3.1: "An edit on Librarybase is attested by `librarybase:42` … `local` … is no longer an issuer code of its own." 03 §4.5 indexes `WHERE issuer = 'local'`. 01 §2.3 puts the actor key in the attestation part of the body, and 01 §5 erases "the attestation part only" to cut the tie between a record and an account.

**Why it is a problem.** Two spellings cannot both be in the log. If records carry `local:42`, a tenant's bundle is not self-describing and two tenants' records collide the moment they share a store or a reader (08 §4.1's cross-tenant read, §6's move). If records carry `librarybase:42`, the tenant slug is burned into every record forever, and 08 §1.2 only guarantees immutability for the farm slug; nothing says a tenant slug can never change, and §6.1's aliases cover base URIs, not slugs. Separately, "what log headers carry" contradicts the record format: a header key is hashed into the Merkle tree and never erased, so an actor key in the header could never be erased for a vanish or an attestation cut. The attestation part is right; the sentence in 07 is wrong, and a programmer reading 07 first will put the actor in the header.

**Suggestion.** Fix 07 to say the actor key lives in the attestation part (and in the header key only of actor records themselves). Decide the spelling: records carry `{slug}:{id}`; state in 08 §1.2 that a tenant slug, like the farm slug, is permanent once the tenant's first record exists, with `alias` covering hosts only; `local:` is a request-time alias that never enters a record. Fix the 03 index to `issuer = <tenant slug>` (it is per tenant anyway).

### F-07-3. The visibility epoch either purges the whole tenant or leaves public entries reachable; the denormalised visibility set is O(namespace) to maintain

**Chapter §:** 09 §5.1, §5.3, §5.8 case 7; 03 §4.6, §9.4, §9.6, §11.4. **Severity:** design debt that will be expensive later; a correctness blocker before `security.restrictions = any` ships.

**What the text says.** `{vis}` is "a hash of the sorted group names of the visibility set together with the tenant's visibility epoch, `-` for the empty set". "On a namespace, set or tenant it bumps the tenant's visibility epoch … so that every entry under the enclosing target lapses at once." "Adding or removing a member is a new version of the record" of a set, and a set is a target whose `read` ACL change bumps the epoch. `view.activity` "gains `read_groups text[]`", per-tenant search documents "carry the visibility set", and the ACL path "run[s] through the same path as erasure, including the inbox purge".

**Why it is a problem.** Read literally, public entries are keyed `-` with no epoch, so a page cached as public before its namespace was restricted stays served from L1/L2 until TTL: exactly the leak §5.8 case 7 tests for. Read the other way, with the epoch inside `-` too, every namespace restriction and every set membership change invalidates every `{vis}`-bearing cache entry of the tenant: on a Wikidata-scale tenant that is a cold cache for one editor adding one page to a confidential set, and shared (tenant-less) keys cannot carry a tenant epoch at all, so the two readings also disagree about shared entries. Independently of caches, `read_groups` on `view.activity`, the search documents and the inbox rows are materialised per row, so a namespace or set change is a rewrite of every activity row, search document and inbox row under the target, and a confidential restriction with an expiry (allowed, §5.2) silently leaves `read_groups` stale when it lapses, because nothing re-runs the projection at expiry.

**Suggestion.** Make three decisions. (1) Public entries carry the epoch (`-{epoch}`) for tenant-specific keys and no epoch for shared keys, which are public at source by construction; say so. (2) Narrow what bumps the tenant epoch to `namespace` and `tenant` ACLs, and have `set` changes bump the generation of the members touched (sets are explicit ID lists, so this is O(changed members), not O(tenant)). (3) Replace stored `read_groups` with a stored *reference* to the enclosures (namespace, set IDs) and evaluate groups at serving time from `view.acl` in L0, or accept the rewrite and state the budget and the expiry re-projection. Either way, write the test for "entry cached under ∅ before a namespace restriction is not served after it".

### F-07-4. "Private" conflates "hidden from the public" with "hidden from other tenants", and a private tenant has no query service

**Chapter §:** 09 §1.2; 08 §4.3, §9.1; 09 §4.7. **Severity:** design debt that will be expensive later.

**What the text says.** 09 §1.2: "a hosting instance gives each tenant a restriction on the tenant itself (§4.7), and from then on the tenants cannot see each other". 08 §4.3: a tenant whose `tenant` ACL restricts `read` "cannot take a code … has no graphs in any query store", and §9.1: "A private tenant … has no query service in version 1." 09 §4.7 adds no stream, no dump, no sitemap, `noindex` everywhere.

**Why it is a problem.** The hosting preset is `isolated`, whose tenants are public wikis; they already cannot see each other except through provider opt-in, so the tenant restriction 09 §1.2 recommends buys nothing and costs each of them its SPARQL endpoint, its dumps and its provider code. The sentence appears to be a leftover from before 08 §4.2's reader lists existed. More seriously, the customers who want restrictions (the enterprise preset; a research wiki wanting a semantic layer for its own agents) are exactly the ones told that restriction means no SPARQL. The invariant does not require this: a `store`-isolated embedded store per private tenant, queried only by that tenant's own principals after `read` on the tenant has been evaluated, is inside the model, and 08 §9.1 already builds the per-tenant store for other reasons.

**Suggestion.** Delete the recommendation in 09 §1.2 or restate it as "a hosting instance needs no tenant restriction". Resolve 0059 Q1 now in the direction the model allows: a private tenant with `query.isolation = store` has a query service for principals that satisfy its `tenant` ACL, with the dataset computed as for a public tenant; what it still lacks is a public endpoint, a stream and a dump. Leave finer-than-tenant confidentiality out of the store (those targets are absent from the deltas, as §5.4 already has it).

### F-07-5. A single-tenant instance materialises both the shared row and its own overlay for every entity it touches

**Chapter §:** 08 §10.5; 03 §7, §6.2 ("Tenant overlays"). **Severity:** design debt for the core use case; cheap to decide now, expensive to change later.

**What the text says.** "A row with the empty-string tenant is the shared row for a mirrored entity … A tenant that has local assertions about the entity … gets its own `(tenant, id)` row." "A record in a shared partition re-runs [resolution] for the shared row and for every tenant that holds an overlay row for the key." The stream computes overlay deltas "against the state *that tenant's stream last showed*".

**Why it is a problem.** The core use case is one tenant attaching local data (citations, corrections, links) to a large share of the Wikidata mirror. With one tenant, every such entity exists twice in `view.entity`, `view.term`, `view.identifier`, `view.entity_ref` and `view.statement_assertion`, and every Wikidata sync of a touched entity resolves twice, once for a shared row nobody reads. The shared/overlay split is a farm optimisation paid by the instance that has no farm. It also means the stream for the only tenant is a filtered merge of two delta streams from the first day. Whether the split survives a real second tenant is a separate question (the overlay recomputation on every shared change is per tenant per touched entity, which is fine until a second tenant touches the same large fraction), but the first tenant should not be the one validating it.

**Suggestion.** State a single-tenant materialisation mode: when the instance has one tenant, the tenant's rows are the only rows (`tenant = ''` is unused), the stream is one stream, and creating a second tenant triggers a projection rebuild into the shared/overlay shape. Rebuilds are already a first-class operation (03 §6.1), so this costs nothing in the log; it only needs to be said so that the first milestone is not built around the split.

### F-07-6. Registry files are copied into `config` records at creation, with no upgrade path for the catalogues

**Chapter §:** 09 §2.1, §2.2, §3.1, §3.2; 08 §5.1, §5.3; 07 §5.3, §8.1. **Severity:** design debt that will be expensive later.

**What the text says.** "The defaults above ship in `docs/registry/groups.toml` and are written to `config` when an instance is created." Presets "ship in `docs/registry/tenancy.toml` and are what `instance create --tenancy {preset}` writes". Grants are "registry data (`docs/registry/grants.toml`)" and preferences likewise. "`owner` … holds every permission, including any added later."

**Why it is a problem.** The catalogue in §2.2 is ninety-odd permissions and will grow with every ADR; each group's permission list is a `config` record per tenant, written once. When release N+1 adds `ts-foo` with default `sysop`, every existing tenant's `sysop` record is stale, and nothing in the chapters says who writes the new one, with what attestation, or how a tenant's local changes to `sysop` are merged with the shipped default (only `owner` is exempt by construction). The same applies to tenancy presets, grants, `tag` prefixes, rate-limit rows and the preference registry. This is the MediaWiki `$wgGroupPermissions`-in-LocalSettings problem reinvented in an append-only log, where the fix is a record per tenant per upgrade.

**Suggestion.** Decide that a group record stores *deltas against a named registry version* (`base = groups.toml@v3`, `add = [...]`, `remove = [...]`), evaluated by overlaying the current registry, so that a registry change reaches every tenant without a write; or decide that upgrades write provision records (08 §8.1) attested by the instance into every tenant, and add that to the §8.6 table. Either is fine; the absence of either is not.

### F-07-7. "As of the record's time" joins across partitions have no defined order and no history table

**Chapter §:** 09 §6.4; 07 §4.4, §4.6; 08 §7.1, §8.4; 03 §4.5. **Severity:** missing decision a programmer will make alone, and make differently on rebuild.

**What the text says.** Autopatrol: "The projection decides this from the membership records in `actors` as of the record's `appended_at`, so a rebuild reaches the same answer." Transfer: "the metadata graph emits `prov:actedOnBehalfOf` for the operator as of each revision's time, since actor records are ordered." Instance rights: "look up which tenant held the role at that record's offset in the instance `config`." But `view.membership` and `view.actor` hold only the current state ("`actor.groups` lists every current membership row"), partitions are independent sequences, and 01 §2.5 says IDs are stored in headers precisely because replay "would change whenever projections were rebuilt in a different interleaving". Vanishing "erases its memberships with everything else keyed to it".

**Why it is a problem.** "As of `appended_at`" compares a record in `local` with records in `actors` by wall-clock microseconds written by different transactions; two appends in the same microsecond, or a clock step, flip the answer. A rebuild that replays `local` before `actors` (the order in 03 §6.1 is by projection, not by interleaved time) has no memberships at all when it decides autopatrol, unless it keeps a membership history table that no chapter defines. And once a vanished administrator's membership records are erased, their past autopatrols become unreconstructible, so the "same answer" guarantee is false after the first vanish.

**Suggestion.** Either store the decision in the record (the write path already knows the actor's groups; put `autopatrolled: true` and the operator key into the attestation part, as the consumer tag already is), which makes rebuilds trivially stable and survives erasure of the membership history; or define a `view.membership_history` with validity intervals, a cross-partition ordering rule (`appended_at`, then partition ID, then offset), and say that erased memberships count as never held. The first is cheaper and more honest; the primary-at-offset lookup for instance rights can stay as it is because the instance `config` is one partition.

### F-07-8. Edit filters evaluate every record of a bulk ingest and write a hit record per match

**Chapter §:** 09 §7.1, §7.4, §7.5; 07 §6.3. **Severity:** design debt for the core use case (ingest).

**What the text says.** A filter "is evaluated against every candidate write in the tenant's `local` and `pages` partitions, in the appending transaction"; its scope is "by default all … and whether it sees job writes". "Every enabled filter evaluates every write, and every match is a hit." "A hit is a record … in the tenant `log` partition." The change-set context includes `values_added` in normalized form, `ops`, term text by language, and `rate`, "the actor's current counts in each rate-limit class".

**Why it is a problem.** Local bulk ingest is the core workload (0000 §2), and nothing exempts it: with the default scope, a ten-million-record job builds a full context per record (normalising every value, reading twenty rate counters from Valkey) and runs every enabled filter in the appending transaction. A `tag`-only filter that matches broadly then writes one hit record per matched record into the tenant `log`, doubling the log; `hit_retention` erases the parts later but the headers stay forever, and the activity rows of kind `log` for them are feed rows. The mirror exemption shows the authors saw the cost; the local-partition job case is the same cost one partition over.

**Suggestion.** Default the per-filter scope to exclude job writes (`jobs = false`), with a filter opting in; let a job submitted with `abusefilter-bypass` skip the stage; aggregate hits for job writes into one hit record per (filter, job) with a count and the first N coordinates, as the job's rejects already are; and make `rate` lazily computed like `added_links`.

### F-07-9. ACL evaluation on the resolution path has no short-circuit at Wikidata scale, and the property fan-out is unbounded

**Chapter §:** 09 §4.2, §4.4; 03 §9.6. **Severity:** design debt that will be expensive later.

**What the text says.** "on the read side the resolution projection asks `view.acl` for the entity's GUIDs and properties in one query, and the public form of the resolved view simply lacks what a read ACL hides"; "the common case, no row, is one indexed miss". A `property` read ACL "bumps every entity the property appears on … which is the one moderation action with a fan-out."

**Why it is a problem.** One indexed miss per resolution is one extra query per entity per resolution. A full Wikidata mirror resolves a hundred million entities on bootstrap and millions per day on sync, and 03 §6.2 says overlay rows re-resolve on every shared change; the per-entity ACL query becomes the largest query count in the system for a feature no public wiki uses. The property fan-out on `P31` is a hundred million generation bumps, cache deletes and search re-sends from one `action=protect`, with no budget, and 03 §6.2's synchronous budget applies to writes, not to this projection.

**Suggestion.** Keep a per-tenant counter of live `statement` and `property` read ACLs in `view.tenant` beside the epoch, read in L0, and skip the lookup entirely while it is zero; shared-row resolution (no tenant) never looks. Put the property fan-out under the projection worker with a stated budget and have the UI say "N entities updating", as the referrer fan-out already does; or refuse a `read` ACL on a property above a configured assertion count and point at the `override` mechanism.

### F-07-10. Rate-limit counting on every read request is a synchronous round-trip the design does not need

**Chapter §:** 07 §6.2, §6.3. **Severity:** minor, but on the hot path.

**What the text says.** `read`: "API requests of any kind, by key or session … 5,000 / 50,000 per minute"; counters are "`rl:{class}:{key}` keys … in Valkey … the key being the actor key or, for anonymous requests, the IP"; `stream`/`atom` have "5 / 20 concurrent" limits.

**Why it is a problem.** An INCR to Valkey per API read, keyed by IP for anonymous traffic, is a network round-trip in front of every response that an L0 hit would otherwise serve in microseconds, and per-IP limits on anonymous reads behind a CDN or carrier NAT limit the wrong thing. "Concurrent" streams cannot be counted correctly across an API pool without shared state the small profile does not have, so that row is a limit that is stated but unenforceable there.

**Suggestion.** Count `read` only for authenticated principals and only past a local, per-process threshold (count in process, promote to Valkey when the local count exceeds a fraction of the limit); exempt responses served from L0/L1; mark the concurrent-stream rows as per-process in the small profile.

### F-07-11. Subsidiary approval is stated three ways, and the Pywikibot path depends on which one is true

**Chapter §:** 07 §4.2, §4.3; 09 §2.2 (`createaccount`), §3.1; 07 §5.3 vs 09 §8.11. **Severity:** minor, but it is on the acceptance test of the first milestone.

**What the text says.** 07 §4.3: "A new subsidiary created by hand is a member of `user` like any registered account … is not pending." 07 §4.2 and 09 §2.2: "A subsidiary a new user creates is pending until approved." 09 §3.1: "`user` is every registered local account, except a subsidiary with status `pending`". Also 09 §8.11 requires "the `read` grant" for MCP, which 07 §5.3's grant table does not have (it has `basic`).

**Why it is a problem.** "A new user" is undefined (not autoconfirmed? first subsidiary?), and the two rules cannot both hold for a hand-made subsidiary. A fresh account on the first milestone creating a bot for Pywikibot either edits immediately at `user` rate (07 §4.3) or is refused with `oauth-pending` until a bureaucrat acts (07 §4.2), and the `job` row for `user` is `0`, so a hand-made subsidiary cannot submit a bulk job at all until flagged `bot`; the instance's owner is the bureaucrat in milestone 1, which is fine, but the chapter should say that the WCD-style ingest account is created flagged.

**Suggestion.** Pick one: hand-made subsidiaries are never pending; pending is an OAuth-only status; delete the "new user" sentences. Rename the MCP requirement to `basic`. Note in 07 §4.1 that `instance create` puts the sync subsidiaries in `bot`.

### F-07-12. `autoconfirmed` is computed from an edit count the view does not hold

**Chapter §:** 09 §3.1, §3.4; 03 §4.5; 09 §7.2 (`user_editcount`). **Severity:** minor missing decision.

**What the text says.** "`autoconfirmed` is granted automatically once an account meets an age and edit-count threshold set in `site` configuration", it is the semi-protection group of every ACL, `user_editcount` is a filter variable, and `view.actor` has `groups text[]` listing "every current membership row" and `last_active`, but no edit count.

**Why it is a problem.** Every ACL check against `autoconfirmed`, every `meta=userinfo`, every filter evaluation needs the count; computing it is a `COUNT(*)` over `view.activity` per request unless someone adds a column, and the chapters leave that programmer alone to decide whether it counts job writes, erased records, posts or mirror syncs, which MediaWiki clients and bots will observe.

**Suggestion.** Add `editcount` and `created_at` to `view.actor`, maintained by the activity projection, define what counts (local `edit` rows, erased ones included, job rows excluded), and state that `autoconfirmed` is an implicit group computed from them, never a membership record, so the as-of problem of F-07-7 does not apply to it.

## Where the chapters are sound

- 07 §1–§3 (issuers, actor records, surrogates, linking, vanishing): sound. For milestone 1, actors for the Wikidata mirror are deferrable, since JSON-dump states carry no actor (§1.4); only the `provider` actor for OpenAlex and the local actors are needed.
- 07 §4–§5 (subsidiaries, keys, bot-password shape): sound and a good design. It is the minimum of milestone 1 since no primary account can script; build it before OAuth, which is deferrable wholesale (§7) as are signing keys (§5.4).
- 07 §8 (preferences, portability): sound; the table-comment portability classes are a nice trick. Defer the bundle and the move extract.
- 08 §3.5–§3.7, §5, §6, §8: the farm, presets, moves and prerogatives are sound as design, and should be sequenced after the first tenant exists, subject to F-07-1's bootstrap decision.
- 09 §4.1–§4.3, §6: moderation as retired ACL records with no archive table is sound and simpler than MediaWiki; it is needed on day one (delete, hide), and the record format should be fixed then, including `read_kind`, even if confidential restrictions are refused with `ts-policy` until later.
- 09 §5.4 (flow rules) and §5.8 (privacy test): sound; the include-may-not-widen rule is the right one. Build the `visibility(target)` hook and the `{vis}` segment on day one so the invariant is not retrofitted, but see F-07-3 before relying on the epoch.
