# Review: 02 Graphs, RDF and the query service; 06 Statements and properties

**Overall judgement.** Chapter 02 is coherent as a description of *what RDF Triplespace emits* (graph names, IRIs, vocabulary, what each kind of thing emits) and that part will survive contact with code. Where it will hurt is everything downstream of "the delta is computed when the view changes": the update stream, the `rdf_delta` table and the query service are designed as if the resolved view were one graph per instance, but the tenant chapters make it one graph *per tenant*, and the shared quad store of §7 therefore holds one copy of Wikidata's resolved triples (and one set of per-entity provenance triples) per tenant that mirrors Wikidata, which undoes the "forty tenants share one copy" claim that justifies the shared store at all. Beneath that sit three decisions a programmer would otherwise make alone and get wrong: how a consumer reading `seq > cursor` avoids missing a row from a transaction that committed late; what a `view` rebuild does to `rdf_delta` (the text says both "rebuilt from the log" and "cannot be recomputed"); and that the renderer's exact output is a permanent wire contract for every consumer, because `DELETE DATA` only works if the bytes match. None of this blocks the first milestone, which needs dumps and no stream, no quad store and no second tenant; all of it should be decided before the stream ships, because the stream's contract is "the dump kept current" and that is not a thing you can fix after consumers hold cursors.

Chapter 06 is mostly sound: roles, resolvers, sitelink normalization and page statements are small, well-bounded mechanisms. Two things in it fight the core use case. The constraint projection is specified as a full check of every statement of every mirrored entity, re-run on each mirror sync and fully re-scanned whenever a constraint statement changes upstream, which at Wikidata scale is the workload WikibaseQualityConstraints deliberately does *not* do; and the shared-row rule of §2.4 cannot be implemented as written because the roles the checker needs (`constraint` → P2302 and the rest) are tenant configuration and the shared row has no tenant. The single permanent trap in this group is not in either chapter's own text but in what both assume: "the statement itself is canonical Wikibase JSON", whose `unit`, `globe` and `calendarmodel` fields are full IRIs under a concept base, so the base URI of every local unit item is written into the log on the first quantity statement and stays there through every alias and move. Decide the stored form of those three fields before the first local record is appended.

### F-02-1. The shared quad store holds one resolved graph and one metadata graph per tenant, so Wikidata is copied per tenant after all

- **Where:** 02 §7.2 ("holds every tenant's graphs under their names"), §7.3 ("every tenant's resolved graph and metadata graph, each in its own named graph … forty tenants mirroring Wikidata share one copy of Wikidata"), §6.1 (`full`), 08 §9.1 ("the resolved graph is the default graph, so a query written for the Wikibase-compatible dump runs unchanged"), §2.1 (document nodes per tenant base).
- **Severity:** blocker for any farm with a second Wikidata-mirroring tenant; irrelevant to milestone 1.
- **What the text says:** the `full` form stores each provider's source graph once and each tenant's `resolved` and `metadata` graphs under `{tenant base}/graph/resolved` and `…/metadata`; a tenant's dataset makes its own `resolved` graph the default graph so that Wikidata-shaped queries run unchanged.
- **Why it is a problem:** for a tenant that mirrors Wikidata, its `resolved` graph *is* the resolved view of all of Wikidata (the concept IRIs are upstream's, so for untouched entities the triples are byte-identical to `mirror/wikidata`), plus its overlay. Making it the default graph requires it to be materialized in full. Forty tenants means forty copies of ~16 billion triples next to the one shared `mirror/wikidata`, not one. The metadata graph adds, per tenant, `data:WDQ…` document nodes with `pav:importedFrom`, `pav:hasCurrentVersion`, `schema:about` for every mirrored entity (§2.1, §5.6): ~5 × 10^8 triples per tenant, with tenant-specific IRIs that cannot be shared. The same multiplication applies to a provider tenant's entities read by other tenants (08 §10.5: "under the reading tenant's rewriting"). The stream side has the same shape: a shared `rdf_delta` row for `resolved` is stored once, but is emitted per tenant inside `GRAPH <{tenant base}/graph/resolved>`, so it is "one row read by a thousand streams" only on disk, and the resolved triples of a shared row cannot contain the document-node triples that differ per base.
- **Also underspecified:** which host serves the instance-wide `full` stream that §7.2 loads the shared store from. §6.4's routes are under `{base}` (a tenant), and 08 §10.5 says the farm base serves only `mirror/{provider}` and "there is no resolved view at the farm base".
- **Suggestion:** decide one of: (a) the shared store holds, per tenant, only an **overlay** resolved graph (entities the tenant has touched) and the per-tenant dataset is `default = mirror/* ∪ overlay` with the service rewriting queries so overlay entities shadow their mirror form (not expressible through the protocol dataset; needs a rewriting layer or a store-side feature); (b) the instance has **one** shared resolved graph (tenant `''`, computed under instance defaults, exactly as `view.entity` already does) and tenants' overlay graphs are small named graphs, and 08 §9.1's "runs unchanged" promise is kept only for tenants with no overlay; or (c) `store` isolation is the only form for Wikidata-mirroring tenants and the shared `dataset` form is for tenants that share no large provider. Whatever is chosen, state the per-tenant document-node triples' home explicitly (they cannot be in a shared row) and define the instance-level `full` stream's host, or drop the "loaded once from the `full` dump" sentence. For milestone 1, write "single tenant; the resolved graph is one graph" and defer the rest to the ADR that introduces the second tenant.

### F-02-2. `seq` as the cursor is not safe under concurrent commits

- **Where:** 03 §4.11 (`seq bigint GENERATED ALWAYS AS IDENTITY`, "monotonic in the order deltas were produced, which is the order projections applied them"; "Consumers apply events in `seq` order and never see two events for one entity out of order"), 02 §6.4 (`Last-Event-ID` resumes), §7.2 (embedded worker applies "after each delta batch commits").
- **Severity:** blocker for stream correctness once there is more than one writer (there is: interactive edits, the sync job's batches, and the worker running the queued fan-out remainder, 03 §6.2).
- **Why it is a problem:** an identity value is allocated at insert time, not commit time. Transaction A takes `seq` 99 and commits late; B takes 100 and commits first. A consumer that reads `seq > 98`, sees 100, and advances its cursor to 100 never sees 99. With a per-entity guarantee on top ("never two events for one entity out of order") you also need per-entity serialization between the sync worker and interactive writes, which nothing in 03 §6.2 provides (the append lock is per partition and is released before the queued remainder runs).
- **Suggestion:** make the decision explicit in 02 §6.2/03 §4.11. Options: serve only rows below the oldest in-flight transaction's `seq` (track with `pg_current_snapshot()` / a `txid` column, the pattern every Postgres-backed outbox uses); or route every `rdf_delta` insert through a single sequencer (the projection worker) so insert order is commit order; or make the cursor `(commit LSN, seq)`. Say which, because the choice also decides whether the stream can be served from a replica.

### F-02-3. What a rebuild does to `rdf_delta` is specified twice, incompatibly, and the cost of the stated answer is a second Wikidata in Postgres

- **Where:** 03 §4.11 ("The table is a projection, rebuilt from the log with every other `view` table … reproduces the same *final* state, but not the same sequence"), 02 §6.2 ("the resolved view at a past time cannot be rebuilt in general … The delta is therefore stored, not recomputed"), §6.2 ("Bootstrap mode produces no deltas"), §7.3 (a rebuild "empties the embedded store, which is then reloaded from a fresh `full` dump").
- **Severity:** design debt that becomes an outage the first time anyone runs a rebuild on a Wikidata mirror.
- **Why it is a problem:** replaying a `latest` mirror partition from offset 0 through the delta projection emits one insert-only delta per entity: the whole of Wikidata's RDF, lz4-compressed, into a table whose purpose is a 30-day window. It is also pointless, since §7.3 says consumers reload from a dump after a rebuild anyway. The two sentences cannot both hold.
- **Suggestion:** state that `rdf_delta` is **truncated**, not replayed, by a rebuild: the epoch increments, delta production restarts at the rebuild's head, and consumers reload from the post-rebuild dump (which is exactly the bootstrap rule). Then say what "a fresh `full` dump" costs and how long the service is `available: false` (F-02-4).

### F-02-4. Dumps at Wikidata scale: consistency with the cursor, production cost, and the embedded backend as default

- **Where:** 02 §4.1 ("produced as N-Quads from `view` and `log` … No intermediate quad store is needed"), §6.1 ("at every cursor, the same set of triples the dump would contain if it were taken then"), §6.4 ("Every dump is stamped with the cursor it was taken at"), §7.2 ("Embedded is the default … sized like the `full` dump"), §7.3 (reload after rebuild).
- **Severity:** design debt that is expensive later; it is the first thing a Wikidata-scale deployment hits.
- **Why it is a problem:** (1) "The set the dump would contain at cursor c" requires the dump to be a point-in-time snapshot of `view.entity` plus the record bodies it points at (`resolved_kind = source`). A Postgres snapshot held across a multi-hour scan of 10^8 rows while sync keeps writing stalls vacuum on the largest tables; the alternative, a dump that is not at one cursor, breaks the contract. Neither is chosen. (2) Producing the dump is a full read of the mirror partition (decompress, parse, render) — Wikidata's own takes days across many workers; nothing says it is parallel, resumable or run from a replica. (3) An embedded Oxigraph "sized like the `full` dump" is not a Wikidata-scale option; a rebuild that "reloads from a fresh `full` dump" into Oxigraph is a multi-day outage of every scope, sprint and validation projection that depends on the service.
- **Suggestion:** decide: dumps are taken from a replica under `pg_export_snapshot()` with parallel workers sharing the snapshot (stated), or dumps are taken from the quad store at its own cursor (which makes the store an input to the dump, contradicting §4.1). Say in §7.2 that `embedded` is the small-profile backend and that the Wikidata profile is `remote` with QLever, and put that row in 00 §2.8's profile table. Add a sentence on dump parallelism and resumption.

### F-02-5. The renderer's exact bytes are a permanent wire contract and nothing versions them

- **Where:** 02 §6.1 (the contract), §6.2 ("Each side is rendered to triples … the delta is the set difference"), §6.4 ("`DELETE DATA` and `INSERT DATA` are set operations"), 03 §4.11 (epoch bumps only on rebuild).
- **Severity:** design debt; silent, cumulative, and unfixable after the fact.
- **Why it is a problem:** `DELETE DATA` removes a triple only if the consumer's store holds it byte-for-byte: the same lexical form of every decimal, date, coordinate and language tag, the same skolem IRI, the same `wdtn:` normalization. Any change to `scatter-wikibase-rdf` or `oxrdf` that alters a lexical form (a bug fix in `%.14G` emulation, a change of unit conversion table, a new normalizer for a resolver, F-06-5) means every later delete of an older triple misses and the stale triple lives in every consumer forever. The old-state side of a delta is rendered by the *current* renderer from the old JSON, so the instance itself will not notice.
- **Suggestion:** give the stream a **rendering version** as part of the epoch (`{epoch}` is "a number in `ops` that a rebuild increments"; let a renderer change increment it too, which forces consumers to reload), and record it in `manifest.json`. Pin the lexical forms in `wikibase-compat.md` as a test fixture the renderer must reproduce byte-for-byte. Decide now whether normalizer configuration changes bump it (they must).

### F-02-6. The skolem IRI is a cross-instance contract whose inputs are not fixed, and one of its inputs is rewritten by the resolved view

- **Where:** 02 §4.3 (`https://scatter.red/genid/{H(statement id ‖ snak role ‖ property ‖ index)}`; "The statement ID in the hash is upstream's for a mirrored statement and the tenant's for a local one"; "the same on … every instance"), 04 §4.9 (the resolved view rewrites the statement GUID's entity part to the canonical ID), 04 §4.8 (a fused statement "takes its ID and IRI from the highest-ranked graph").
- **Severity:** design debt; permanent once a dump ships.
- **Why it is a problem:** `H`, the separator, the encoding of "index" and what "index" counts (qualifier position? reference position? position among same-property snaks?) are unnamed, yet the IRI is published and claimed stable across instances. Worse, it is unclear which statement ID is hashed: the text says upstream's, but the resolved view's statement node is `s:{canonical}-{uuid}` and a fused statement's ID flips when a local member appears or is suppressed, so either the skolem and its statement node disagree about the statement's identity or the skolem changes on every canonical change. References are shared by hash across statements (`ref:` nodes), so a somevalue snak inside a reference gets a different skolem under each statement that cites the reference, giving one `ref:` node several `prv:` objects for one unknown value.
- **Suggestion:** fix the hash function and the byte layout in `wikibase-compat.md` (it is a wire format); hash the **UUID** part only, never the entity part, so canonical rewriting and fusion leave it unchanged; for reference snaks hash the reference hash instead of the statement ID. State what "index" is.

### F-02-7. Cluster and canonical changes are whole-entity rewrites in RDF, multiplied by referrers

- **Where:** 02 §6.2 ("A cluster change re-resolves every referrer and produces one delta per referrer"), 04 §4.4 (a local member is canonical; the canonical changes when membership changes), 04 §4.9 (statement node IRIs follow the canonical ID).
- **Severity:** design debt that is expensive; a known cost the chapter should state rather than describe as "a few triples".
- **Why it is a problem:** when a tenant links a local item to `WDQ5` (human) or `WDQ30`, the canonical ID becomes the local one, every statement node of the cluster's entity changes IRI, every value `wd:Q5` in every referrer's `wdt:`/`ps:`/`pq:`/`pr:` triple becomes `{base}/entity/Q…`, and every one of those referrers gets an overlay row and a delta. For a tenant, one `same-as` to a widely-referenced item is O(referrers) overlay rows (millions) and O(referrers × statements) delta triples, in the 30-day table, per tenant. The consumer-side cost (QLever applying millions of deletes and inserts) is also unstated.
- **Suggestion:** this is mostly 04's problem, but 02 should stop saying "a few triples" and name the fan-out; and consider whether the resolved view's RDF should rewrite *values* to the canonical IRI at all when the canonical is local, since `owl:sameAs` in redirect form already lets a consumer follow it. If the rewrite stays, say in 02 §6.2 that cluster deltas are produced by the queued remainder, not synchronously, and that the stream's "one transaction = one event" rule therefore does not make a cluster change atomic for a consumer.

### F-02-8. A tenant's provider list and overlay lifecycle have no reload semantics

- **Where:** 08 §9.1 ("The dataset is computed from the tenant's provider policy at each request, so a tenant that drops a provider stops seeing it at once"), 08 §10.5 (overlay deltas computed "against the state that tenant's stream last showed"), 03 §4.11 (one instance-wide epoch).
- **Severity:** minor for the store (the dataset handles it); design debt for the stream.
- **Why it is a problem:** a tenant that opts in to Wikidata after the fact needs its external consumers to insert all of Wikidata; no delta exists and the epoch is instance-wide, so there is no way to tell *that tenant's* consumers to reload without telling everyone's. Dropping a provider is the same in reverse. The overlay rule handles entity-level transitions but not provider-level ones.
- **Suggestion:** per-tenant epoch (`ops.tenant_epoch`), bumped by a provider-list change, a `store`/`dataset` isolation change, and a base-URI alias; the cursor stays `{epoch}:{seq}` with the tenant's epoch.

### F-02-9. Erasure purge of `rdf_delta` cannot find metadata-only rows, and `internal` graphs leak into the metadata graph by definition

- **Where:** 02 §6.3 ("found through `rdf_delta_entity`"), 03 §4.11 (`entity_id … NULL for a metadata-only event`), 02 §1.1 (`internal`: "served by the API but never exported"), §1.2 (`log`, `actors` are `internal`), §5.2 ("Log events are projected into the metadata graph only"), §6.1 (`full` carries "revision, actor and event nodes").
- **Severity:** minor, but it touches erasure, which is the one place "minor" becomes legal.
- **Why it is a problem:** a hidden or erased comment, actor name or summary sits in the `inserted` side of an earlier metadata delta whose `entity_id` is NULL; the sixth erasure step cannot reach it through the entity index, and there is no index on `(partition, offset)`. Separately, `actors` and `log` are `internal` ("never exported") yet their projections — actor nodes with `sioc:name`, log events — are in the full dump and the `full` stream. The export policy of a source graph and the export of its projection need one rule.
- **Suggestion:** index `rdf_delta (partition, "offset")` and purge by record coordinates; define `internal` as "its records are never exported; what the metadata projection derives from them follows the metadata graph's policy", and list which actor fields the metadata graph may carry (names are personal data under 07's vanish).

### F-06-1. The constraint projection is specified as full, synchronous checking of a Wikidata-scale mirror

- **Where:** 06 §2.2 ("checks every statement of a changed entity against the constraints on its properties"; "Mirrored data is checked as local data is"; "A change to a constraint itself re-checks every statement using the property … a full scan of one property"; `type` "checks `P31`/`P279` chains"; "Bootstrap runs the constraint projection last"), 03 §6.2 (the entity's own checks are inside the synchronous budget).
- **Severity:** design debt that is expensive later; it is what Wikidata itself cannot afford.
- **Why it is a problem:** Wikidata has ~1.6 × 10^9 statements and thousands of constraint statements, and P2302 statements on busy properties change daily; a mirror sync of one edit to P31's constraints triggers "a full scan of one property" over 10^8 statements. `type` and `value type` depend on the P279 hierarchy transitively; a P279 edit near the top invalidates results for every instance of every subclass, and the reverse-index re-check in §2.2 only covers direct referrers. Checking every mirrored entity on every sync multiplies the per-entity sync cost by the number of constraints on its properties; WBQC avoids this by checking on demand and caching per entity, and by not running SPARQL-type checks at all. The violation table at this scale is 10^8 rows per tenant that diverges (F-06-2).
- **Suggestion:** make the projection's scope a setting with a sane default: `constraints.scope = local` (local-graph statements and statements on entities a tenant has touched) by default, with `all` as an opt-in that is batch-only; make constraint-statement changes on mirrored properties enqueue a batch, never a synchronous or sync-path scan; decide that `type` is checked at display time with the L0 class cache, or that P279 changes do not invalidate (document the staleness), rather than pretending the reverse index covers it. For milestone 1, ship constraint checking for local statements only.

### F-06-2. Shared-row violations need roles, and roles are tenant configuration

- **Where:** 06 §2.4 ("violations on shared rows are computed once for the instance"), 06 §1 ("A role binding is tenant configuration, a `config` record of kind `role`"), 23 §2.2 (`role`: scope Tenant), 06 §2.1 ("A role that a tenant has not bound is a constraint type it cannot check").
- **Severity:** contradiction; it cannot be implemented as written.
- **Why it is a problem:** the checker finds constraints by the `constraint` role and interprets them by the per-type and per-parameter roles. The shared row (`tenant = ''`) has no `config` partition and so no roles; "computed once for the instance" has no vocabulary to compute with. The same hole exists for every other instance-scope consumer of roles: the adapter's "local targets named by role" (06 §1.2, 04 §4.6) writes OpenAlex mirror records — instance-scope, shared by every tenant — with predicates that are *one tenant's* local property IDs, which are tenant-relative (04 §2.3). On a farm, whose `P12` is in the shared OpenAlex partition?
- **Suggestion:** add an instance-scope `role` record (23 §2.2: scope "Tenant, with an instance record for shared rows"), computed-once rows use the instance bindings, and a tenant whose bindings differ from the instance's gets overlay rows for everything the difference touches (say so: on a Wikidata mirror that is "everything", so in practice a tenant on a farm does not rebind the constraint roles). For adapters, decide that an instance-scope mirror may map only onto provider (`WDP`) properties or onto properties the *instance* owns (a primary-tenant or instance property namespace), never onto a tenant's local property; 04 §4.6's "otherwise onto a local property" needs that qualifier.

### F-06-3. Shared view + tenant overlay silently requires every tenant to share the instance's reconciliation order, normalizers and roles

- **Where:** 06 §3.1 ("registering a resolver for a role sets the normalizer for every property bound to it"), 06 §2.4, 04 §4.4 ("The tenant's `reconcile` record sets the order of the providers"), 23 §2.3 (`reconcile` is tenant configuration), 03 §4.1/§7 ("the row with `tenant = ''` is the shared row computed from the shared source graphs").
- **Severity:** design debt that decides whether a second tenant works; one sentence fixes the spec, but the sentence must be written.
- **Why it is a problem:** the shared resolved row of a {`WDQ`, `OAW`} cluster depends on provider order; the shared `view.identifier` row depends on the DOI normalizer; the shared `constraint_violation` row depends on the roles. All three are tenant configuration. Two tenants with different `reconcile` orders cannot share a row, and the fallback — overlay rows for every affected entity — is every clustered or identifier-bearing entity in Wikidata. The chapters never say which configuration the shared row is computed under.
- **Suggestion:** state in 03 §7 and 06 §2.4/§3.1: shared rows are computed under the **instance's** `reconcile`, normalizers and roles; a tenant may diverge only for its own local graph's statements (the overlay), and the tenancy presets forbid diverging on shared-provider ordering and normalizers. Then F-06-2's instance-scope `role` record is the same decision.

### F-06-4. `unit`, `globe` and `calendarmodel` are base-URI IRIs inside canonical Wikibase JSON, and the log is append-only

- **Where:** 06 §0 ("The statement itself is canonical Wikibase JSON"), 08 §6.1 ("Projections emit every IRI from the current template; nothing is rewritten in the log"), wikibase-compat.md §4 (`"unit": "http://localhost:8080/entity/Q3"`, `"globe": "http://www.wikidata.org/entity/Q2"`, `calendarmodel` IRIs), 04 §4.7 (entity values compare by canonical ID; quantity compares by "amount, unit and bounds").
- **Severity:** blocker in the "format mistake is permanent" sense: it must be decided before the first local quantity statement is appended.
- **Why it is a problem:** canonical Wikibase JSON carries a quantity's unit, a coordinate's globe and a time's calendar as full concept IRIs. For a local unit item that IRI contains the tenant's base; after an alias (08 §6.1) every record written before it holds the old base, contradicting "nothing is rewritten in the log … emit from the current template", which only works if the log stores IDs. For a mirrored unit (`WDQ11573`, metre) the JSON holds Wikidata's IRI, which is fine as a concept IRI but means `entity_ref`, cluster rewriting and "entity values compare by canonical ID" must reverse-match IRI templates to find the entity, and the chapters never say whether units/globes/calendars are entity references at all (they are not "entity values" in Wikibase's datatype sense, and 04 §4.7 treats `unit` as part of a literal key). A tenant that clusters local `Q7` with `WDQ11573` gets two fusion keys for one unit depending on which graph wrote the statement.
- **Suggestion:** decide the **stored** form: either (a) the log stores Wikibase JSON with these three fields as entity IDs in prefixed form (`"unit": "WDQ11573"`, `"unit": "Q7"`), and the projection expands them through the current template on output — then the content hash of a mirror `put` is over the rewritten form (the adapter already rewrites IDs, so this is consistent), and 06 must say "canonical Wikibase JSON with units, globes and calendars as IDs"; or (b) the log stores IRIs verbatim and 08 §6.1 is amended to say base changes are not transparent for these fields. (a) is right; it also makes units participate in `entity_ref` and in canonical rewriting, which the resolved view needs.

### F-06-5. Changing a normalizer has no path, and the current design lets it happen at runtime

- **Where:** 06 §3.1 ("a resolver declares its case rule"; a resolver is a `config` record written with `ts-config`), 04 §4.7 ("A property can override its data type's normalizer"), 04 §4.8 (fusion key is over canonical forms), 03 §4.3 (`view.identifier` keyed by `value_key`).
- **Severity:** design debt; expensive the first time someone registers a resolver for a property that already has 40 million values.
- **Why it is a problem:** registering a DOI resolver after P356 is populated changes the normalizer of P356's values, therefore every `value_key` in `view.identifier`, every fusion key of every DOI-bearing statement (so fused statements split or merge, and their resolved IDs change), every match-key check, and by F-02-5 the `wdtn:` triples of every affected entity in every consumer. Nothing says this is a batch job, what its progress looks like, whether writes are refused meanwhile, or that it bumps the stream's epoch.
- **Suggestion:** a normalizer change is a `config` write that **enqueues a per-property rebuild job** (the same shape as the constraint rescan), is reported on the property page, and bumps the rendering version (F-02-5); and `value_key` rows carry the normalizer version so a half-rebuilt index is detectable. Alternatively, forbid changing a normalizer on a property that has values and require a new property; say which.

### F-06-6. Sitelink uniqueness is enforced across the resolved view, so a mirror sync can collide with a local link

- **Where:** 06 §4.2 ("A normalized URL belongs to at most one item. Writing it on a second item is the same error"), §4.5 (per-host rule only: "Where two graphs give one host different URLs for the same entity, the local graph wins"), 03 §4.3 (`url_key text PRIMARY KEY` with the tenant column).
- **Severity:** design debt; a missing decision that will surface as a projection failure on a sync batch.
- **Why it is a problem:** the per-URL rule across *different* entities in different graphs is not covered by §4.5, which only reconciles one entity's links per host. Wikidata moving `enwiki:Douglas Adams` to another item while a local item holds the same URL (or the reverse: a local editor adding a URL Wikidata's item already holds) is a primary-key conflict inside the sitelink projection, and a failing projection step in a sync batch is a stuck mirror. Whether a local write may claim a URL a mirrored item holds is also unstated; the intended answer ("use `same-as`") is in §4.2's last paragraph but not as a rule.
- **Suggestion:** add a row to §4.5: per URL across entities, local wins and the mirrored link is dropped from the resolved view (listed for maintenance with the stranded links of §4.4); a local write that collides with a mirrored link is refused with a message naming the item and suggesting `same-as`. Say the projection never fails on a sitelink conflict.

### F-06-7. Role bindings are typed as properties but several roles bind items

- **Where:** 06 §1 and 23 §2.2 (`role`: "The properties bound to a role"), 06 §2.1 ("one role per constraint type": Q21502404 …), §1.2 (`subject-page`, `subject-thread` "the items that stand for…"), §2.1 `constraint-status` values Q21502408/Q62026391.
- **Severity:** minor; a programmer will notice, but will have to choose the record shape alone, and the record is in the `config` partition, where the shape is permanent.
- **Suggestion:** define the `role` record as binding a role to one or more **entity IDs** of any type, with the role catalogue stating the expected type.

---

**Sound as written, and sequencing notes.** 02 §1 (graph registry and IRIs), §2 (nodes), §3 (vocabulary), §5 (what each thing emits), §4.2/§4.4 are sound; the only thing I would change is §2.1's sentence that log events live "in the metadata graph only" should also say which fields of actor nodes it carries (F-02-9). 06 §3 (resolvers) and §4.1–4.3 (sitelink normalization, aliases) are sound and cheap; §5 (page statements) is sound, with one note that statement node IRIs for pages (`s:123-uuid`) will confuse tools that parse an entity ID out of `wds:` IRIs — accept it, but say it in wikibase-compat.md.

For the first milestone: build the Wikibase-compatible dump and the local-graph source dump (02 §4.1) and nothing else from 02 §6–7; constraints for local statements only (F-06-1); one tenant, one resolved graph (F-02-1). Before the stream ships, decide F-02-2, F-02-3, F-02-5 and F-02-6. Before the first local quantity statement, decide F-06-4.
