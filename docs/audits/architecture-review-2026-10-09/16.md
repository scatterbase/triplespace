# Review: chapters 16 (logs, feeds, notifications), 17 (federation, publication), 18 (API)

## Overall judgement

Chapter 18 is, for the most part, servable from the `view` schema of 03 without per-request O(entities) work: `wbgetentities`, `prop=info`, `wbsearchentities`, `list=recentchanges`, `list=logevents`, `list=usercontribs`, contributions, history and the watchlist all reduce to primary-key lookups on `view.entity`/`view.entity_source` or to indexed range scans on `view.activity`, and the "materialize only where it differs" rule plus the tenant overlay keeps the Wikidata-scale mirror from being copied per tenant or per request. Chapter 16's feed model (one row shape, feeds as target sets over `view.activity`, the watch set and inbox as private state, addressing as a projection) is sound and is the right shape to build first. Chapter 17 is almost entirely jobs and read-side publication: nothing in it, apart from the `evidence` field of an inbound post's attestation and the verification metadata inside a mirror record, touches the core write path, and all of it can be deferred past the first milestone without leaving a hole in the log format.

Where it will hurt is in the two places chapter 18 inherits rather than decides. First, **the Wikibase write modules are specified only as additive deltas over the compatibility contract, but on a multi-source entity the contract has no answer**: what `wbeditentity` with the full `claims` list (which is what WikidataIntegrator sends), `wbsetclaimvalue` on a GUID a mirror graph owns, `clear=true`, or `wbremoveclaims` *means* as a local-graph change set is not written down anywhere, and the conflict rule the chapter points at (01 §7, strict rejection, base checked across the mirror partitions) both contradicts the contract it says it builds on (Wikibase patches around a stale `baserevid`) and produces spurious `editconflict`s on any entity Wikidata is actively editing. Both are blockers for "the Action API that Pywikibot and WikidataIntegrator use" and neither is a large design: they are decisions that have to be made before the first write module exists. Second, the chapters assume per-revision entity state that 03 does not store, so every old-revision read and every entity diff is a replay of the key's local record chain. Beyond those, the stream cursor is not resumable as specified (which 17 §1.2 depends on), and the default mirrored Wikidata log is a second Wikidata-scale partition the first milestone does not need.

### F-16-1. The Wikibase write modules have no defined mapping onto change-set operations for a multi-source entity

**Chapter §:** 18 §2.1, §2.3 (`wbeditentity`, "The statement modules"), §4; with 05 §2.5, §3.2 and 04 §4.9.
**Severity:** blocker for the core use case.

**What the text says.** 18 §2.3 lists `wbeditentity` as changed only in that "`sitelinks` entries may carry `url`… `new=lexeme`… Terms on `M`", and the statement modules only as working "On lexeme and part IDs, and on `M` IDs". 18 §4 says "Routes that write on an entity's or page's behalf map to the same change sets". 05 §3.2 defines the local-graph operations as `add`, `remove`, `override` ("Overrides the rank or a term of an assertion from another graph, or suppresses it"). 04 §4.9 says "API writes all resolve through [the UUID]". 05 §2.5 says a correction is "a rank override, an added statement, a suppression".

**Why it is a problem.** The chapter never says what a Wikibase write *is* when the entity the client fetched is the resolved view of several graphs. The cases a bot hits on day one:

- **WikidataIntegrator and Pywikibot's `editEntity` send the whole entity**: the full `claims` list as they fetched it, GUIDs included, plus their additions. Wikibase merges that. If Triplespace merges it as `add` operations, every WDI write copies every mirrored statement of the entity into the local graph, which is exactly the "stale-copy problem" 05 and 04 §4.9 reject. The write path must diff the submitted JSON against the resolved view and emit only the delta, and an unchanged mirrored statement must be a no-op. Nothing says so.
- **A changed value on a mirror-owned GUID** (`wbsetclaimvalue`, `wbsetclaim`, a modified entry in `wbeditentity`'s `claims`): `override` can change rank or a term, not a value. The only representable outcome is suppress-plus-add-with-new-GUID, which changes the GUID the client holds, or a refusal. There is a refusal code for projected page statements (`ts-derived-statement`); there is none for mirrored statements.
- **`wbremoveclaims` on a mirror-owned GUID** presumably becomes `override{suppress}`; **`clear=true`** on a foreign or fused entity presumably removes local assertions only; **`wbsetaliases` with `remove`** on a mirrored alias; **`wbsetsitelink`** replacing a mirrored sitelink. Each needs one sentence.
- **The response.** Wikibase returns the full stored entity with `lastrevid`. After a local write to a fused entity the response must be the re-resolved view with the client-visible (canonical-rewritten) GUIDs, which the synchronous budget of 03 §6.2 makes possible but which the chapter does not state.

**Suggestion.** Add a section to 18 §2, "Wikibase writes against the resolved view", that fixes: (1) every `wb*` write is first diffed against the entity's resolved view for the tenant; unchanged content is dropped before a change set is built; (2) a table from each module and submitted shape to the operation it becomes, by whether the touched GUID/term/sitelink is local-owned or mirror-owned (local: `add`/`remove`; mirror: `override` for rank, term and suppression; value change on a mirror GUID: either `ts-foreign-statement` refusal or suppress-and-add with the new GUID returned in `claim`, chosen once); (3) `clear` clears local assertions only; (4) the response is the re-resolved entity. This is the acceptance test for the milestone, more than `Project` pages are.

### F-16-2. `baserevid` semantics contradict the compatibility contract and create spurious conflicts under a live mirror

**Chapter §:** 18 §1.3, §1.5; 01 §2.5, §7; `mediawiki-compat.md` "baserevid and conflict handling"; 03 §4.2.
**Severity:** blocker for the core use case.

**What the text says.** 18 §1.5: "write modules map `baserevid` to base offsets… and an `editconflict` error includes the current revision's ID". 01 §7: "The log rejects the change set if a newer record for the key exists in the partition… For a write to a foreign entity, `baserevid` is decoded to a partition and offset, and the check runs against the newest record for the key across the source partitions, not only the local one." 01 §2.5: "`lastrevid` of an entity is the revision ID of its newest record in any source partition, chosen by append time." The contract 18 §8 says it builds on: "If the entity has changed since then, Wikibase tries to **patch** the client's change onto the latest revision… A patch that cannot be applied fails with an edit-conflict error." 03 §4.2's DDL comments `local_revid` as "lastrevid for the Action API".

**Why it is a problem.** Three things, all on the bot path:

1. Pywikibot sends `baserevid` from the entity it fetched; so does WikidataIntegrator. On a `full` mirror following Wikidata's stream, the newest record for `WDQ42` across the source partitions advances every time Wikidata edits Q42. A local write that only adds a local assertion is rejected as `editconflict` although nothing it could conflict with has changed: the mirror partition is not something a local write can conflict with. For popular items (and bots work popular items) the conflict rate equals Wikidata's edit rate on them. Clients expect patching, so they do not retry; they fail.
2. Strict rejection versus the contract's patching is a behavioural difference a client cannot discover. Statement modules that touch disjoint GUIDs never conflict in Wikibase.
3. `lastrevid` "chosen by append time" is not monotonic and not from one space: a mirror `put` gives `WD<<40|R`, a later local `add` gives a small local number, the next `put` a large one again. 03's `local_revid` column says the opposite (lastrevid is the local revid). The two cannot both be implemented.

**Suggestion.** Decide, in 18 §1.5 and fold into 01 §7: `lastrevid` is the latest **local** revision ID when the key has any local record, else the ranged ID of its newest mirror record (which is what 03's column already assumes). The base check is **per source graph**: a `baserevid` that decodes to the local partition is checked against the local partition's latest offset for the key only; one that decodes to a mirror partition asserts only that the key still has no local record (`local_offset IS NULL`), and a mirror advancing is never a conflict. Adopt Wikibase's patch rule for the Action API: a stale base is accepted when the change set touches no GUID, term or sitelink that a later local record touched, with `wikibase-conflict-patched`; otherwise `editconflict`. Keep `editconflict` (not `nosuchrevid`) for a compacted base. Also define inbound `maxlag` (nowhere in 18): the larger of replica lag and the tenant's local-partition projection lag in seconds, so WDI's and Pywikibot's `maxlag=5` throttles them during a bulk load.

### F-16-3. No per-revision entity state exists, so old-revision reads and entity diffs replay the record chain

**Chapter §:** 18 §2.3 (`prop=revisions` "`rvprop=content` returns the serialization", `action=compare` "For entities, a diff of the canonical JSON of the local graph's assertions"), §5.1 ("'Before' is the source graph's state just before the record"), §5.2; 03 §4.2 ("A local entity that has been edited with `add` or `remove` is materialized… since no record holds its state"), §4.4 (`record_statement` only).
**Severity:** design debt that will be expensive later.

**Why it is a problem.** The local partition holds change sets, not states, and `view` holds only the current resolved JSON. `prop=revisions&rvprop=content&revids=`, `action=compare&fromrev=`, `oldid=`, `Special:PermanentLink`, `GET /entity/{id}/compare`, the before/after block of `GET /entity/{id}/changes`, and `?as_of=revision` in §5.2 all need the local-graph state at an offset, which can only be obtained by replaying every local record for the key from its last whole-state record (`create`/`adopt`) to that offset: O(revisions of the entity) per request, and an entity a bot edits hourly has thousands. Nothing caches these (03 §9 keys on `resolved_version`, the current state). MediaWiki stores every revision's text for exactly this reason.

**Suggestion.** Decide a snapshot policy now, because it changes what a local record carries and the log is append-only: either (a) every local-graph record about an entity carries the content hash and size of the post-state (hash and size are already computed in the synchronous projection for `size`/`delta`) and a periodic whole-state `snapshot` record every N records per key, so replay is bounded by N; or (b) a `view.entity_revision (tenant, revid) → canonical JSON` projection for the `local` and `pages` partitions only, which is MediaWiki's `text` table at local scale and is cheap because local edits are the small part of a mirror-dominated instance. Say explicitly that mirror states are not reconstructable under `latest` (18 §5.1 already does for the resolved view).

### F-16-4. The activity stream's cursor is ordered by source time and is therefore not resumable

**Chapter §:** 18 §1.3 ("Rows are ordered by (time, partition, offset)… The time is when the event happened at its source… Continuation tokens… encode the last sort key returned"); 16 §4.4 ("a consumer that missed events resumes from its last token"; "A consumer tenant on another instance syncs from a provider tenant this way"); 17 §1.2 ("follows the stream filtered to `source = local`").
**Severity:** blocker for 17 §1; design debt for recent changes.

**Why it is a problem.** A sort key of (source time, partition, offset) is a fine order to *display*, but a consumer that resumes from the last key it saw will never see a row whose key sorts before it and which committed after it: imported page revisions and adopted history keep their original timestamps (18 §1.3), upstream events keep upstream time, forks seed history afterwards (13), and even two local edits can take `time` in one order and commit in the other. The SPARQL Update stream avoids this with a commit-ordered `txn`/`seq` (03 §4.11, 02 §6); the activity stream does not. Since 17 §1.2's verified sync "follows the stream", a reader instance silently misses records.

**Suggestion.** Give the activity stream and `Last-Event-ID` a commit-ordered cursor: per partition the offset is already commit-ordered under the append lock, so the token is a vector of (partition, offset) high-water marks, or a global `seq` assigned at commit as `rdf_delta` has. Keep (time, partition, offset) for paged lists, where MediaWiki's `rccontinue` has the same edge and nobody minds. State in 16 §4.4 that a feed page and a stream page the same rows but order them differently.

### F-16-5. The default mirrored Wikidata log is a second Wikidata-scale partition, and its rows contradict 03's sizing of `view.activity`

**Chapter §:** 16 §1.4 (default mirrored: `create/create`, `import/*`, `contentmodel/*` "Page provenance"; "The backfill covers events whose target lies in a mirrored entity namespace, whether or not the instance holds the entity"), §1.3 ("User titles are resolved to numeric IDs with the issuer's API"), §3.2 ("The activity projection… indexes events from both log graphs"); 03 §4.6 ("`view.activity`… grows with local activity and the number of jobs, never with the mirrors"), §7 ("`view.activity`… per tenant outright").
**Severity:** design debt that will be expensive later; a day-one cost the milestone does not need.

**Why it is a problem.** `create/create` on Wikidata is one event per entity ever created, on the order of 10^8, under `full` history and `hashed` integrity, in a partition that is never compacted; `import/*` and `contentmodel/*` add little and `delete/revision` is needed only for entities the instance holds. That is a second Merkle tree the size of the mirror, loaded by parsing the `pages-logging` dump (two parameter formats), before any of it answers a question the entity's first upstream revision does not. Then 16 §3.2 projects those events into `view.activity`, which 03 says never grows with the mirrors and is per tenant: either every tenant gets a copy of Wikidata's log (O(tenants × events)) or 03 is wrong. Resolving performer names to IDs "with the issuer's API" is one upstream call per distinct name during backfill; the dump carries IDs, the EventStreams feed does not.

**Suggestion.** Make the default mirrored set `delete/delete`, `delete/restore`, `delete/revision`, `delete/event` and `protect/*`, and make "narrow the backfill to entities it holds" the default rather than an option; derive `create/create` and `import/*` from the first upstream revision record when history is backfilled. Decide where provider-log events live in `view`: a shared `tenant = ''` row set in `view.activity` (03 §4.1's sentinel), or a separate per-provider table that `list=logevents&leprovider=` and an entity's history read, and fix 03 §4.6's sentence to match. Note that the local catalogue's own rows are already projections and cost nothing until the record types exist (see F-16-12).

### F-16-6. Provider-ranged revision IDs for entity sources exceed 2^53 and break every JavaScript client, the site UI included

**Chapter §:** 18 §1.3; 01 §2.5 ("Numbers from 2^22 to 2^23 − 1 are never allocated in the registry: each tenant assigns them to its entity sources"; `revid = provider_number << 40 | n`); 19 ("Everything it shows it fetches through the API").
**Severity:** minor in scope, but a permanent trap: IDs are in the hashed header.

**Why it is a problem.** `2^22 << 40 = 2^62`. JSON numbers above 2^53 lose precision in every browser and in Node; `formatversion=2` has no string form for `revid`/`lastrevid`. Registry providers numbered above 2^13 have the same problem. The site UI, Wikidata gadgets and any JS tool will round these IDs. Since the ID is in the hashed header it cannot be reassigned later.

**Suggestion.** Cap the ranged space at 53 bits: provider numbers below 2^13, entity-source numbers from a low reserved band (for example 2^12 to 2^13 − 1), and say so in 01 §2.5 before the first entity source is written.

### F-16-7. Canonical-ID resolution answers a member ID as a redirect, which Pywikibot treats as an error

**Chapter §:** 18 §2.3 `wbgetentities`; 04 §4.4 ("The API resolves a non-canonical member to the canonical entity, as Wikibase resolves a redirect"), §4.9.
**Severity:** design debt that will be expensive later.

**Why it is a problem.** The multi-source core produces clusters constantly: a tenant that converts `WDQ42` to `Q9`, or links an OpenAlex author to a Wikidata item, makes the member non-canonical. Wikibase's redirect shape in `wbgetentities` (`redirects: {from, to}`, entity keyed by the target) makes Pywikibot raise `IsRedirectPageError` on `ItemPage('WDQ42').get()`, and a bot keyed on Wikidata IDs then edits the canonical ID it did not ask for. For a tenant whose point is Wikidata plus local data, every clustered Wikidata item becomes "a redirect" to Wikidata-oriented tooling.

**Suggestion.** Treat the rewrite as presentation, selectable per request: `wbgetentities&ids=WDQ42` returns the resolved entity under the requested ID with a `canonical` field (and GUIDs prefixed with the requested ID, since the UUID is the identity, 04 §4.9), and the Wikibase redirect shape only when the member is a true redirect (a `redirect` operation or an upstream merge). Record the choice in 18 §2.3 and 04 §4.4 together.

### F-16-8. `meta=siteinfo&siprop=triplespace` mixes configuration with live counters

**Chapter §:** 18 §2.2 (`hash_mismatches`, "the instance-wide count"; `page_repos` with `index_as_of`, `event_lag`, `mirrored_pages`); 03 §6.2 (projection lag "reported… in `siprop=triplespace`").
**Severity:** minor.

**Why it is a problem.** `siteinfo` is fetched at session start by every MediaWiki client and by the web tier, so it must be cacheable by the registry's offset; the row ties it to counts over the largest tables and to queue state. Either the counters are computed per request or the configuration is served stale.

**Suggestion.** Keep `siprop=triplespace` a function of the tenant's configuration (cache key: registry offset, tenant, visibility), and move `hash_mismatches`, lags and set sizes to `GET /version`, `GET /provider/{code}/mirror` and `GET /repo/{name}`, which already exist and already carry such numbers. Maintain the counts in `site_stats`, never by `COUNT(*)`.

### F-16-9. The `private.watch` DDL cannot serve the `watch` addressing rule it is used for

**Chapter §:** 16 §4.3 (DDL: `PRIMARY KEY (actor_key, target_kind, target_id)`, one index on `expires`); §5.2 ("`watch`: A change reaches a target it watches with `notify` set"); 03 §4.6 ("`private.watch` is small per account and never scanned across accounts").
**Severity:** minor, but the kind of DDL that becomes a trap.

**Why it is a problem.** The addressing projection runs for every activity row and must find every account with `notify` on that row's target (and its cluster and talk-page pairing). With the key leading on `actor_key` there is no way to do that except a scan across accounts, which 03 forbids. The same lookup backs DiscussionTools-style subscriptions on busy threads.

**Suggestion.** Add `CREATE INDEX watch_target ON private.watch (target_kind, target_id) WHERE notify`, and say that the addressing projection reads it under the notifier's role. Separately, the watchlist's sync rows "read per target from its mirror records" are O(watch size) lookups per load; bound them by indexing `view.entity_source (synced_at)` or by a `period` cut on `synced_at` before the per-target read.

### F-16-10. `private.upstream_grant` stores hashes of tokens the instance must present

**Chapter §:** 17 §3.2 ("`private.upstream_grant (actor_key, wiki, scopes text[], access_hash, refresh_hash, …)`"); §4.4 (a bot password is "encrypted at rest").
**Severity:** minor; a programmer would hit it on the first push.

**Why it is a problem.** The instance is the OAuth *client* here: it must send the access token to Wikidata and the refresh token to the token endpoint. A hash cannot be sent. The adjacent `publication_credential` row gets it right.

**Suggestion.** `access_token`, `refresh_token` encrypted at rest with the same key handling as `publication_credential`; keep hashes only where the instance is the *server* (0025's token tables).

### F-16-11. Verified federation as specified cannot bootstrap at scale, and its metadata placement fights the `put` skip rule

**Chapter §:** 17 §1.1 (the local-graph dump carries "the record coordinates of each entity's newest record"), §1.2 ("For each record it mirrors, the adapter fetches the record with its header… every record is verified, always"; "The provider's header… and the checkpoint tree size… are stored in the mirror record's content part"; "the `delete/statement` event on the stream"); 05 §3.2 (`put` "is skipped when… the content hash is unchanged"); 16 §2.3 (no `delete/statement` row).
**Severity:** design debt; defer explicitly.

**Why it is a problem.** The state dump carries states and coordinates, not the canonical record bytes the leaf hash commits to, so bootstrapping a verified mirror of N entities is N `GET /record/{partition}/{offset}` calls plus proofs: impractical for a Triplespace provider of any size, and the stream it then follows carries activity rows, not records, so steady state is also one fetch per record. Putting `verified_at_size` inside the hashed content part means a reconciliation that re-verifies an unchanged entity against a newer checkpoint changes its content hash and writes a `put` the skip rule should have dropped. `delete/statement` is cited as the event that tells a reader to drop a hidden statement, but the catalogue in 16 §2.3 has no such event, and a statement `read` ACL (09 §4.2) is not listed as projecting to any event.

**Suggestion.** Bootstrap verified sync from the export bundle of 01 §8 (records plus manifests), not from the state dump, and make the stream optionally carry record bodies for `source = local`. Keep the provider header in the content part (it is stable) and `verified_at_size` in `entity_source` only. Add a `delete/statement` (or fold it into `delete/revision` with a `statement` parameter) to 16 §2.3, or drop the sentence. For the first milestone, register the second instance with `trust = stream` and build verification when a second Triplespace instance exists.

### F-16-12. The log-event catalogue's day-one cost is small, with one permanent rule to state

**Chapter §:** 16 §2.1, §2.3; 01 §2.5 ("a log ID to every record… that projects as a log event"); 03 §2.3 (`log.log_id` "taken for every record that projects as a log event… in the appending transaction").
**Severity:** minor; sound if stated.

**What holds.** Because every local event is a projection of a record (§2.1), the forty-odd rows of §2.3 cost nothing until their record types exist; a milestone that has entities, pages, jobs, ACLs and actor records needs `create`, `delete/*`, `protect/*`, `job/*`, `newusers/*`, `rights/*`, `block/*`, `erase/erase` and nothing else, provided the projection is a registry keyed by payload type and not one match over the whole table.

**The trap.** Whether a record takes a `logid` is decided at append from the catalogue and frozen in the hashed header. A later decision that some existing record type should project as an event cannot be retrofitted: those records have no log ID, and `activity_logid` is unique. State the rule positively, so it is not re-derived per type: every record in `local`, `pages`, the tenant `log` and the tenant `actors` partition takes a log ID at append, whether or not the current catalogue projects it, and the sequence gap is the price.

### Where the chapters are sound, and sequencing for the first milestone

- **16 §4–§5** (feeds, watch set, inbox, addressing as a projection, channels) are sound; build the page and Atom deliveries and the `everything`, `one target` and `watched` sets first, defer `related` (the join with `feeds.related_limit`), scopes, filter hits, farm-wide feeds and the fediverse channel.
- **17** is sound as deferred work: §1 publication of checkpoints and proofs is read-side over 01's tree and costs nothing to leave for later; §2 ActivityPub, §3 proposals, §4 publications and §5 dataset dumps are jobs and private state with no coupling to the write path beyond the attestation `evidence` field, which is an additive map key.
- **18 §3.2** is a good single index. The minimum for the milestone is: `meta=siteinfo|tokens|userinfo`, `action=login` (bot passwords), `wbgetentities`, `wbsearchentities`, `wbeditentity` and the statement modules (with F-16-1 and F-16-2 decided), `prop=info|revisions`, `list=recentchanges|logevents|usercontribs|allpages`, `action=edit|parse` on `Project` pages, and the REST routes `/activity`, `/entity/{id}/provenance`, `/entity/{id}/history`, `/jobs*`, `/suggest`, `/resolve`. `/sparql`, scopes, the MCP server and the Wikibase REST API mirror can wait, and the chapter already makes them optional on a tenant without a query service.
