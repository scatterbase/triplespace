# Review: chapters 13 (Mirrored pages), 14 (Discussions), 15 (Structured pages)

Reviewer brief: these chapters are beyond the first milestone. The questions asked were whether their mechanisms impose day-one costs on the core (record kinds, projections, `view` tables the entity path must carry), what couples to identity clusters, proposals/merging and the entity write path, and where the chapters contradict themselves or their neighbours.

## Overall judgement

Taken as a whole the three chapters are well separated from the core: almost everything they add is a new partition (`pages/{repo}`, `derived/{source}`), a new payload type (`mirrored-page`, `derivation`, `thread`, `task`), a new content model or a new `view` table, and the core milestone can be built without a single row of them. The things the core *must* settle on day one because these chapters will later depend on them are few and they are all identity decisions that end up in hashed headers and therefore cannot be changed afterwards: the page-ID space (local sequence below 2^40, provider-ranged IDs above it, and, unresolved, where a mirrored entity's page ID sits), the optional fourth part on `scatter:v0/upstream-revision`, and the rule that a server-minted value may be written into a content part. The first is genuinely broken today (F-13-1), the third quietly conflicts with client signatures (F-13-6). Everything else in these chapters can be sequenced after the core with no retrofit beyond adding a lookup to the title resolver and a column or two.

Where the chapters will hurt is not in the core but in their own operating model at the scale they themselves name (MDWiki over English Wikipedia; a scope over a Wikidata `full` mirror). Three patterns recur. First, several "projections" are described as doing things a projection may not do: writing log records (proposal adoption retiring assertions), carrying history-dependent state that a rebuild from offset 0 cannot reproduce (sprint credit), and running arbitrarily expensive per-record work (ShEx validation, scope matching) inside the fan-out budget of the entity projection. Second, instance-scope artefacts (the page bundle, the title index, the foreign-thread number) are keyed by repository *name* and rewritten under *tenant* configuration, which does not survive a second tenant listing the same wiki. Third, the fork design defaults to copying twenty thousand text-bearing revisions per page plus every template's history into the tenant's `log` partition, which at MDWiki's scale is terabytes of Postgres for a feature whose stated purpose is attribution. None of these is a core-milestone blocker; two of them (F-13-1, F-13-2) are decisions that should be made before the first mirror record is written.

## Findings

### F-13-1. Thread attachment by page ID assumes one page-ID space per tenant; mirrored entities do not live in it

**Chapter §:** 14 §1.3, §1.5 (`target {kind: page, id}`, `view.talk_page UNIQUE (target_kind, target_id)`); against 03 §2.3 and 04 §5.3.
**Severity:** blocker for the core use case (it is a header-field decision the mirror ingest fixes permanently; the thread feature only exposes it).

**What the text says.** 14 §1.3: a thread's target is "a page ID: an entity's (0015 §2, carried forward, so a mirrored entity has one), a document page's, or the provider-ranged page ID of a page a repository serves". 03 §2.3: "A mirrored entity's page ID is taken from `log."instance.page_id"` the first time its key is written, since it belongs to no tenant; only a page served by a page repository has a provider-ranged page ID." 04 §5.3: a ranged ID "never collides with a local page ID, which comes from the tenant's sequence below 2^40".

**Why it is a problem.** Three page-ID sequences meet inside one tenant's view: the tenant's own (`Q5`, `Project:Foo`, threads), the instance's (`WDQ42`, `OAW…`), and the ranged one (foreign pages). The first two are both plain integers from 1, so `{kind: page, id: 42}` names a local page *and* a mirrored entity, `view.talk_page`'s unique key collides, `prop=info` returns duplicate `pageid`s on one wiki (which Pywikibot keys on), `view.scope_member.id` "page ID in decimal" and `view.task.subject_id` are ambiguous, and `page_link`/"what links here" from a thread cannot say which it meant. The chapters never notice because each assumes a different answer: 14 that entity page IDs are per-tenant ("carried forward"), 03 that they are instance-wide. Since field 9 is in the hashed header, whichever is chosen is permanent once Wikidata is ingested.

**Suggestion.** Decide now, before the first mirror put: either (a) mirrored entities take a provider-ranged page ID like foreign pages (`provider_number << 40 | instance.page_id`, or `| upstream page ID` where the provider has one, which Wikidata does), so every non-local page ID in a tenant is above 2^40 and 04 §5.3's claim holds for entities too; or (b) `target` in thread records, scope members and tasks becomes `{kind: entity|page|…, id}` with the entity ID as text, and `pageid` for a mirrored entity is derived at the API edge. (a) is one line in 03 §2.3 and makes 14, 15 and 18 consistent as written; (b) touches four table keys. Either way, add a sentence to 04 stating the full page-ID partition of a tenant's view.

### F-13-2. Instance-scope bundles and indexes are keyed by repository name and rewritten under tenant configuration

**Chapter §:** 13 §1.1, §2.2, §2.4, §2.5; 03 §4.12 (`view.foreign_title (repo, ns, title)`, `view.foreign_page (repo, upstream_page_id)`, `fp:{repo}:{ns}:{title}:{revid}`).
**Severity:** design debt that will be expensive later (it is the "shared view + second tenant" question for pages).

**What the text says.** A `page-repo` is "a `config` record of kind `page-repo`, keyed `page-repo:{name}`, in a tenant's config or in the instance config" with per-record `namespaces`, `mode`, `shadowed`, `talk`, `media_hosts`. The title index and the bundle table are "instance scope, shared by every tenant that lists it", keyed by `repo` name. The HTML rewrite (§2.2) maps a wiki link to "the local URL of the same title when its namespace is one the repository serves **here**", images follow "the **tenant's** file policy… the first file repository in `files.repos`", and §2.2 then asserts "the rewritten HTML depends on the repository's configuration and the title index, not on the stack". In `mirror` mode the rewritten HTML is part 4 of an instance-partition record.

**Why it is a problem.** Two tenants can each define `page-repo:enwiki` in their own config with different `namespaces`, and both land in one `view.foreign_title` row set and one `fp:` key: the index is per name, the names are per tenant, and nothing says names are instance-unique. Worse, the rewrite is a function of tenant state (`files.repos`, which namespaces this tenant serves, `media_hosts` of *its* entry) but the artefact it produces is cached and, in mirror mode, *logged* once per instance. The first tenant to fetch decides what the second one serves; a mirror record written with tenant A's link policy is "verifiable" but wrong for tenant B. This is the exact failure mode 03 §7 avoids for entities by splitting shared rows from tenant overlays, and here it is unaddressed.

**Suggestion.** (1) Key instance-scope page artefacts by **provider**, not repository name, and require that an instance has at most one `page-repo` per provider (or define a repository as instance config and let a tenant only *select* it with `pages.repos`; the tenant-level fields that remain are `shadowed`, `talk`, `cache_ttl`). (2) Make the stored rewrite tenant-independent: links to `/wiki/{ns}:{title}` for every namespace in the *repository's* `namespaces`, images to `File:` titles, no `extiw` decision and no file-repository decision at bundle time; the tenant-dependent part (which namespaces this tenant serves, which file repo answers) is a cheap second pass at serve time over a DOM that already carries `data-ts-origin`. Then §2.2's sentence becomes true and the mirror record is the same for every tenant.

### F-13-3. Fork history seeding, as defaulted, writes terabytes of page text into the tenant `log` partition and into a table whose key cannot hold it

**Chapter §:** 13 §3.4 (`fork.max_revisions` default 20,000 with content; text as a fourth part in the tenant's `log`), §3.6 (`fork.dependencies = copy` default, `fork.max_dependencies` 2,000, "with its history seeded by the same job"), §5.13 (talk page and every archive's history seeded too); 01 §2.6 `view.upstream_revision PRIMARY KEY (provider, upstream_revid)`.
**Severity:** design debt that will be expensive later (blocker for the MDWiki-shaped use the chapter is written for).

**What the text says.** "The save never waits for history" is right, but the job it defers writes, per fork: up to 20,000 revisions *with wikitext* for the article, the same for each of up to 2,000 dependency pages not already local, and the whole history of the talk page and every archive subpage. All of it goes "into the tenant's `log` partition, keyed by the fork's page ID", and is served from `view.upstream_revision`, whose primary key is `(provider, upstream_revid)` and which has no tenant column.

**Why it is a problem.** Cost: a mature Wikipedia article has 5–20k revisions averaging tens of KB; `Module:Citation/CS1` and `Template:Infobox` have thousands each. A tenant that forks ten thousand articles (MDWiki) stores on the order of 10^8 text-bearing records, several terabytes, in a Postgres partition that is `full` and `hashed`, to support a History tab that §2.1 says is normally fetched live. The design's own `retain` path for entities (01 §2.6) refuses more than 10,000 entities through the API for this reason; forks have no equivalent brake. Correctness: two tenants on one instance that fork the same article both write `(enwiki, revid)` rows, which the primary key refuses; a fork that is re-followed and later re-forked (§4.5) seeds the same revids under a new page ID into rows that already carry the old one; and `entity_id` as "the page ID in decimal" is per-tenant, so the table cannot say whose page.

**Suggestion.** Default `fork.max_revisions` to metadata-only history (attribution is satisfied by the author list; the licence does not ask for text), with content seeded on request or for the last *N* (e.g. 100) revisions; never seed dependency or archive histories with content; make the cap a per-job budget rather than per page. Give `view.upstream_revision` a `tenant` column and a key that admits page subjects (`(tenant, provider, upstream_revid, entity_id)` or a separate `view.page_upstream_revision`), and decide explicitly whether a seeded revision belongs in the tenant `log` partition (today: log events) or in `pages` beside the fork's own records, since the former gives it a log ID and the latter a revision ID, and the chapter wants it served through `prop=revisions` with a *ranged* revision ID, which is neither.

### F-13-4. Projections that cause log writes: proposal adoption retires assertions, and a rebuild would do it again

**Chapter §:** 14 §5.4 ("the instance **retires** each redundant assertion at once — a `remove` of the local assertion as an instance act"; `view.proposal` "written by the mirror and page-mirror projections when the target changes"); 13 §4.5 (the page-mirror projection "runs the test when the destination page changes"); against 03 §6.1 ("a rebuild truncates the projection's tables and replays from offset 0") and 15 §1.4, §3.5, §6.4 (a projection "writes no record").
**Severity:** design debt that will be expensive later (a correctness trap in the one place a projection is allowed to append).

**What the text says.** Adoption is detected inside the mirror projection, which is a shared, instance-scope projection in step 2/4 of the order; on detection it writes a tenant row and, with `upstream.retire_adopted = true` (the default), appends a `remove` record into the tenant's `local` partition under the instance attestation.

**Why it is a problem.** The chapters elsewhere insist projections derive and never write; this is the exception and it is not fenced. A projection rebuild replays every Wikidata `put`, re-detects every adoption, and re-appends every `remove` unless something makes the append idempotent; the key of a `remove` is the entity, so there is no natural dedupe. The shared mirror projection also now has to read a per-tenant table on every `put` (fine with an index on `target`, but the index is not listed) and to take a tenant's append lock from inside the instance's projection transaction, which inverts the layering 03 §6.2 describes (projections run *after* the append, within it). The same shape recurs more mildly in 15 §4.3 (projections enqueue render refreshes) and 13 §4.5 (`fork.refollow = auto` deletes forks), which are jobs and therefore fine.

**Suggestion.** Make the rule explicit in 03 §6.1: a projection may enqueue work in `ops`, never append. Adoption detection writes `view.proposal.state` and enqueues `(tenant, thread, assertion)` in an `ops` queue; a job appends the `remove` with the proposal thread and upstream revision as an idempotency key in its content part, and the job checks the current resolved state before writing. State that a rebuild re-derives `view.proposal` but never re-runs the retire job (the queue is not a projection target and is not truncated).

### F-13-5. Scope maintenance is called incremental, but the trigger set and the truncation rule cannot be maintained incrementally as written

**Chapter §:** 15 §1.3 (`column`, `pages_of`, `entities_of`), §1.4 ("applies the effect of each write to the scopes it touches, found through the inverted index above and through `page_link`"; "the first `scopes.max_members` are kept… in a deterministic order… so that the prefix kept is stable"; "a truncated scope is still a full operand… computed over the operands' complete sets").
**Severity:** design debt that will be expensive later.

**What the text says.** The inverted index `(tenant, kind, id)` finds the scopes a subject is already in; `page_link` from the scope page finds scopes "that name a property, category or table".

**Why it is a problem.** The first lookup answers "which scopes might lose X", the second "which scopes might gain X" for `statement` and `category` kinds only. Nothing finds a `column` scope when one of its table's row entities changes a value (the scope contains the *values*, not the row; the write is to the row; `page_link` goes scope→table, not entity→scope), nor a `pages_of`/`entities_of` scope when a sitelink pairing changes, nor an `intersection` whose operand is a `column`. The truncation rule is also not incremental: keeping "the first 100,000 in ID order" means that when a member below the cut-off is removed, the next member past it must be pulled in, which for anything but a single `statement` kind is a recomputation; and "computed over the operands' complete sets" is only possible when the operand is a kind with an index to probe (`statement`, `category`), which should be said, since `column` and `query` operands have no complete set anywhere. Finally, every write in the entity projection now consults the scope trigger set, including every `put` of a Wikidata `full` mirror; the chapter says nothing about where that set lives or how it is cached.

**Suggestion.** Replace the two ad hoc lookups with one compiled trigger table written at definition save, `view.scope_trigger (tenant, trigger_kind, key, scope_page_id)` with keys such as `property:P31`, `category:{page}`, `table-row:{page}`, `sitelink`, held in L0 per process and keyed so a mirror `put` that touches no triggered property is one hash probe. Define the truncated set as "the first N found, refilled by a job when it falls below N", not as a stable ID prefix. State per kind whether it is probe-able as an operand, and refuse an `intersection`/`difference` whose non-probe-able operand is truncated. Say explicitly that bootstrap mode skips the scope step and a scope's initial computation is always a job.

### F-13-6. Server-minted values written into content parts break client signatures

**Chapter §:** 14 §1.3 (the talk page ID is "minted… by the first `create`, `move` or `attach` record… and that record carries it in its content part"), §1.4 ("the `create` and `rename` records carry the minted title", with the `(2)` suffix); 13 §5.4 (`n` allocated by the sync job and carried in the `put`'s content); against 01 §2.4 (a client signature is over `H(0x03 ‖ content) ‖ H(0x03 ‖ comment)`, "the canonical bytes of the two parts before the server salts them").
**Severity:** minor today, permanent once records exist.

**Why it is a problem.** The design wants every minted value in the record so that a rebuild reads rather than derives it, and that is right. But a subsidiary that signs a thread `create` signs a content part that does not yet contain `talk` or the suffixed `title`; the server inserts them, and the stored part no longer matches the signature. Either the server refuses every signed thread `create` on a fresh target, or the signature is silently unverifiable. The same applies to any future type where the server fills a content field.

**Suggestion.** Rule in 01 §2.4: the client-signed preimage is over the content part *as submitted*, and server-filled fields live in a declared, unsigned fifth part (or in the attestation map, which is already server-controlled and already carries the job). Chapter 14 then moves `talk` and the minted `title` there, or states that thread records are never client-signed.

### F-13-7. `view.task` credit is a function of replay order, and a rebuild does not preserve it

**Chapter §:** 15 §3.5–3.6 (`resolved_by` is "that record's actor", "read from the record the projection was applying"; `reopened` counter; "the window frames the counting"); against 03 §6.1 ("A rebuild orders partitions by dependency: the `config` partition, then the instance `log`, then mirrors, then tenant partitions").
**Severity:** design debt that will be expensive later.

**Why it is a problem.** Whether a task was resolved by a Wikidata `put` or by a local edit, and how many times it reopened, depends on the interleaving of the mirror partition and the tenant's `local` partition in replay. A rebuild replays all mirror records first, then local ones, so every task that any mirror put ever satisfied is resolved by the put and then reopened or re-resolved by local edits in an order that never happened. The leaderboard after a rebuild is not the leaderboard before it, and the chapter promises the opposite elsewhere ("a rebuild truncates and replays from offset 0"). `view.proposal.adopted_at` and `view.foreign_thread.state` have the same dependence in weaker form.

**Suggestion.** Define resolution by the records' header time, not by projection order: on rebuild the task projection must either replay the relevant partitions merged by time (a merge the activity projection already needs for `view.activity`) or be declared non-rebuildable and recomputed from `view.activity`, which is rebuilt by time. Say which. Drop `reopened` or define it the same way.

### F-13-8. Schema validation and ShEx in the synchronous fan-out of a Wikidata mirror

**Chapter §:** 15 §6.4 ("a subject's own write re-validates the subject against every schema bound to a scope it is in, within the fan-out budget"), §6.3 (depth 2 into referenced nodes, `schemas.max_triples` 10,000); 03 §6.1 (validation "at the end of step 7… within the fan-out budget").
**Severity:** design debt that will be expensive later.

**Why it is a problem.** A scope `P31=Q5` with a schema bound to it puts a ShEx run with up to 10,000 triples and a two-hop walk into the projection pipeline of every `put` of every human the Wikidata sync delivers. The fan-out budget bounds latency of one write (250 ms, then queue), not throughput: the queue grows at the sync rate times validation cost and never drains during a backfill. The chapter already knows this for the initial computation ("as a job") but not for steady state. The same cost shape, smaller, applies to `constraint_violation` re-checks that sprint rules read.

**Suggestion.** Validation never runs in the write path or the fan-out budget; it is a queue with its own worker and a per-tenant rate, and `view.schema_report.checked_at` is honest about lag. Only the **ad hoc** check (`POST /schema/{id}/check`) runs inline. Add a per-tenant cap on bound-schema × scope-size (the product, not each), refused at scope save with the scope notice, so a tenant cannot bind E10 to `Scope:Humans` on a Wikidata mirror without an operator saying yes.

### F-13-9. `view.foreign_page` in proxy mode is coupled to L1 eviction, which cannot notify it

**Chapter §:** 13 §2.4; 03 §4.12 ("In `proxy` mode its rows are the pages whose bundles are in the L1 cache… and a row is dropped when its bundle is evicted; it is the one `view` table that is not a projection of any log").
**Severity:** minor (a trap).

**Why it is a problem.** The L1 cache evicts by LRU and TTL without a callback into Postgres; the table will hold rows whose bundle is gone and miss rows whose bundle is there after a restart. Anything that reads it as an index of what is held (the `on-demand` grace sweep, `last_read`, `Special:Providers`) will be wrong in both directions.

**Suggestion.** In proxy mode, make `view.foreign_page` an *index of what has been fetched*, with its own `expires_at` sweep, and treat the L1 entry as a cache in front of it (miss → refetch), or drop the row in proxy mode and keep the metadata in the L1 value. In mirror mode it is a projection and the problem does not arise.

### F-13-10. Derived graphs are a tenant source that 03 §7's overlay rule does not know about

**Chapter §:** 13 §6.4 ("A subject may be foreign… its statements go on the foreign entity"), §6.6 ("The entity projection finds a subject's derivations through `view.derivation_subject`"); 05 §1.4 (derived graphs between local and mirrors); against 03 §7 (a tenant gets an overlay row when it "has local assertions about the entity, a cluster link touching it, or a correction on it").
**Severity:** minor (underspecification at the one place the multi-source core is touched).

**Why it is a problem.** A derivation naming `WDQ123` makes tenant T's resolved view of `WDQ123` differ from the shared row, so T needs an overlay row; the rule that decides overlay rows does not list derivations. Either the entity projection probes `view.derivation_subject` for every tenant on every shared resolution (an extra lookup per tenant per put at mirror scale) or derivations silently do not reach foreign subjects. Related: the derived statement ID (§6.5) hashes "the subject", which is whichever ID the match key resolved to; when a local item created by extraction is later linked `same-as` a Wikidata item, re-extraction resolves to the other member, the ID changes, and corrections keyed on the old ID become orphans, which §6.6 promises will not happen.

**Suggestion.** Add derivations to 03 §7's overlay triggers, with `view.derivation_subject (tenant, subject)` as the index the projection consults (it already exists; say that this is what it is for). Hash the derived statement ID over the cluster's *canonical* member at extraction time, or over the match key itself, so a later cluster change does not rename statements.

### F-13-11. Foreign-thread numbers are allocated per repository but their page IDs are ranged per provider

**Chapter §:** 13 §5.4 ("`n`, allocated per repository… foreign thread page ID = `number << 40 | 1 << 39 | n`"); 03 §4.8 (`view.foreign_thread PRIMARY KEY (repo, n)`).
**Severity:** minor.

**Why it is a problem.** `number` is the provider's; `n` is per repository name. Two repositories on one provider (allowed as written, see F-13-2) allocate overlapping `n` and therefore identical ranged page IDs for different threads. Also, `n` is minted by the sync job and recorded in the `put`, so uniqueness depends on one writer per repository; nothing says the sync job is single-writer, and a rebuild from two interleaved sync jobs could in principle reproduce a duplicate. Resolving F-13-2 (one repository per provider) removes the first problem; the second wants a sentence.

**Suggestion.** Allocate `n` per provider from a sequence in `ops` held under the repository's sync-job lock, and state that `pages/{repo}` has exactly one writer.

### F-13-12. A tenant cannot add a page repository without an operator editing `providers.toml`

**Chapter §:** 13 §1.1 (`provider`: "the provider registry entry… supplies the provider **number**… A provider that mints no entities has no `code` and no types"), against 05 §6 / 01 §2.5 (entity sources take tenant-assigned numbers 2^22–2^23−1 precisely so a tenant need not touch the registry).
**Severity:** minor (a decision to make).

**Why it is a problem.** The chapter presents `page-repo` as tenant configuration, but the number it needs for ranged page IDs comes from an instance-authoritative file. A farm tenant wanting to read `de.wikipedia.org` is blocked on the operator; if instead page repositories took numbers from the per-tenant range, ranged IDs would differ per tenant and the instance-scope title index and bundles would no longer be shareable, which the chapter relies on.

**Suggestion.** Decide: page repositories are instance-level (operator adds the provider; tenants select; the title index is shared), and say so, retiring "in a tenant's `config`"; or they are tenant-level with tenant numbers and nothing is shared, which costs an index per tenant. The first matches everything else in the chapter.

## Sound, and sequencing notes

- **13 §1.2–1.5 (stack, resolver, frame)** is sound and cheap: the core resolver needs one extra indexed read guarded by `pages.repos` being empty. Build the resolver with the stack signature from the start; everything else in 13 waits.
- **13 §4 (merge)** is sound as a pure crate; nothing couples to the core except the `merge` field on an `edit` content part, which can be added later since it is optional.
- **14 §1–4 (threads, boards, pins)** are sound and self-contained, but note that the design has **no wikitext talk page**: talk namespaces are composite, so the moment the site UI shows a Talk tab the whole thread model (payload type, four tables, comrak, page_link from posts) ships. Either ship milestone 1 without a Talk tab or with `triplespace-talk` resolving to an empty listing. The `thread.max_attachments`/`max_pinned` validations against a fold are fine.
- **14 §5 (proposals)** couples to clusters only through translation (§5.2), which is read-only over `view.cluster` and fine; the write-side coupling is F-13-4.
- **15 §2 (tables)** is the one structured page that is nearly free for the core: a text model plus reads of the resolved view, writes as ordinary change sets. It could be in milestone 1 if a grid is wanted; nothing else in 15 should be.
- **15 §5 (query pages)** is sound; parameter binding by `VALUES` is the right call. **15 §6.1** says a foreign schema's text body "is replaced whole" by a local overlay: the change-set format of 05 §3.2 has no operation for that and should gain one before `WDE` mirroring is attempted.
- The `pages` partition's payload-type list (`page`, `thread`, `task`, `changeset`) and the parts count per type are the only format-level facts from these chapters that the core writes; 01 already carries them. Keep it that way: no new header fields, no new global IDs.
